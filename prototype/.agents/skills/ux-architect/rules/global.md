# ข้อกำหนดและหลักการพื้นฐานส่วนกลางสำหรับ UX Architect

> **ขอบเขต:** ข้อตกลงร่วม ระดับคำสั่ง ลำดับความสำคัญในการตัดสินใจ ข้อกำหนดทางวิศวกรรม และขั้นตอนการทำงานสำหรับกฎ UX ทุกหมวดหมู่
> **วัตถุประสงค์:** สร้างมาตรฐานการตัดสินใจและส่งมอบงาน UI/UX ที่มีความสอดคล้อง เข้าถึงได้ง่าย มีประสิทธิภาพ และเชื่อถือได้ทั้งในมุมมองของ Agent และนักพัฒนา

---

## 1. ข้อตกลงและระดับคำสั่งตามมาตรฐาน RFC 2119

การนำกฎ UX ไปปฏิบัติให้ยึดตามระดับข้อกำหนดต่อไปนี้:

- **MUST / MUST NOT**: ข้อบังคับเด็ดขาดที่ต้องปฏิบัติตามเสมอ เช่น ความถูกต้องของโครงสร้างเชิงความหมาย ลำดับการเข้าถึงด้วยคีย์บอร์ด และความสมบูรณ์ของสถานะ ห้ามละเว้น เว้นแต่มีข้อจำกัดทางเทคนิคหรือความปลอดภัยที่ระบุเหตุผลชัดเจน
- **SHOULD / SHOULD NOT**: แนวทางมาตรฐานที่ควรปฏิบัติตามเป็นค่าเริ่มต้น หากจำเป็นต้องเบี่ยงเบนเนื่องจากบริบทเฉพาะของงานหรือระบบเดิม ต้องมีเหตุผลรองรับ
- **MAY**: ทางเลือกเสริมตามบริบท สามารถเลือกใช้ได้เมื่อเหมาะสมกับงาน
- **AVOID**: รูปแบบที่สร้างปัญหาหรือก่อให้เกิดผลเสียต่อประสบการณ์ใช้งาน ซึ่งต้องตรวจสอบและแก้ไขเมื่อพบ

---

## 2. ลำดับความสำคัญในการตัดสินใจ

เมื่อข้อกำหนดด้านความสวยงามขัดแย้งกับข้อกำหนดด้านการใช้งาน ให้จัดลำดับความสำคัญตามลำดับขั้นต่อไปนี้เสมอ:

1. **การเข้าถึงได้และความถูกต้องเชิงความหมาย**
   - ความสามารถในการใช้งานด้วยคีย์บอร์ด โปรแกรมอ่านหน้าจอ ความคมชัดของสีตามเกณฑ์มาตรฐาน และโครงสร้างเอกสารที่ถูกต้อง มีความสำคัญสูงสุด
2. **พฤติกรรมการใช้งานจริงและความสมบูรณ์ของข้อมูล**
   - สถานะของระบบ การสื่อสารข้อผิดพลาด การปกป้องข้อมูลของผู้ใช้ และความต่อเนื่องในการทำงานจริง
3. **ความสอดคล้องกับระบบเดิมของโปรเจกต์**
   - การยึดตามโทเคน สี ระยะห่าง รูปแบบคอมโพเนนต์ และแบบแผนเดิมที่มีอยู่แล้วในโปรเจกต์
4. **การขัดเกลาความสวยงามทางสายตา**
   - การปรับแต่งสไตล์ เงา เส้นขอบ หรือเอฟเฟกต์ภาพ ต้องไม่ทำลายลำดับขั้นก่อนหน้า

## 3. ข้อกำหนดร่วมทางวิศวกรรม

### โครงสร้างเชิงความหมายมาก่อนการจัดแต่งเสมอ
- คลาสสไตล์หรือ CSS ไม่สามารถทดแทนองค์ประกอบเชิงความหมาย เช่น `<button>`, `<a>`, `<label>`, `<input>`, `<dialog>`, `<fieldset>`, `<legend>`, หรือ `<main>` ได้
- ห้ามใช้แท็ก `<div>` หรือ `<span>` ธรรมดาแทนปุ่มคำสั่งหรือลิงก์นำทาง โดยไม่มีบทบาทและสถานะการเข้าถึงที่ถูกต้อง
- ป้ายกำกับของช่องกรอกข้อมูลต้องเชื่อมโยงกับองค์ประกอบควบคุมทางโค้ดเสมอ ผ่านแอตทริบิวต์ `for` และ `id`

### ความเท่าเทียมกันระหว่าง Tailwind CSS และ Raw CSS
- เมื่อเขียนหรือแปลงโค้ดระหว่าง Tailwind CSS และ Raw CSS ทั้งสองรูปแบบต้องให้ผลลัพธ์ โครงสร้าง ความหมาย ลำดับขั้น และพฤติกรรมการตอบสนองที่เทียบเท่ากันทุกประการ
- ห้ามแก้ปัญหาที่เกิดจากการขาดสถานะหรือตรรกะการทำงานด้วยการใส่คลาสตกแต่งเพียงอย่างเดียว

### การเคารพ Design Tokens เดิม
- ค้นหาและนำโทเคนเดิมของโปรเจกต์มาใช้ก่อนสร้างค่าใหม่เสมอ เช่น ตัวแปรสี สเกลระยะห่าง รัศมีความโค้งมน หรือขนาดตัวอักษร
- ค่าตัวเลข พิกเซล หรือคลาสตัวอย่างในเอกสารกฎ เป็นเพียงจุดเริ่มต้นสำหรับการนำไปประยุกต์ใช้ ไม่ใช่ค่าตายตัวที่ต้องบังคับทับระบบเดิม

### การออกแบบเพื่อรองรับทุกขนาดหน้าจอและเนื้อหาจริง
- ต้องทดสอบทั้งหน้าจอขนาดกะทัดรัด หน้าจอแท็บเล็ต และหน้าจอเดสก์ท็อป
- ต้องทดสอบกับข้อมูลจริงที่มีความยาวไม่แน่นอน เช่น ข้อความยาวเป็นพิเศษ ภาษาที่มีรูปประโยคยาว หรือกรณีที่ไม่มีข้อมูล เพื่อป้องกันการล้นแนวนอนหรือข้อความซ้อนทับกัน

### การรองรับการเข้าถึงและลดการเคลื่อนไหว
- องค์ประกอบที่โต้ตอบได้ทุกชิ้นต้องมีจุดสังเกตโฟกัสของคีย์บอร์ดที่มองเห็นได้ชัดเจน
- ต้องรองรับการตั้งค่าลดการเคลื่อนไหวของผู้ใช้เสมอ โดยปิดหรือลดแอนิเมชันที่ไม่จำเป็นเมื่อตรวจพบความต้องการดังกล่าว
- ห้ามใช้สีเพียงอย่างเดียวในการสื่อสารสถานะ ข้อผิดพลาด หรือความสำเร็จ ต้องมีข้อความหรือสัญลักษณ์ประกอบร่วมด้วยเสมอ

### การแยกหน้าที่อย่างชัดเจน
- **โครงสร้างและความหมาย:** เป็นหน้าที่ของ HTML
- **การจัดวางและการนำเสนอทางสายตา:** เป็นหน้าที่ของ CSS หรือ Utility Classes
- **สถานะ ตรรกะการทำงาน และผลข้างเคียง:** เป็นหน้าที่ของ JavaScript หรือ Backend

## 4. ขั้นตอนการทำงานของ Agent

เมื่อได้รับมอบหมายให้ออกแบบ สร้าง ปรับปรุง หรือตรวจสอบ UI ให้ดำเนินงานตามลำดับขั้นตอนดังนี้:

1. **สำรวจและระบุปัญหา:**
   - ตรวจสอบองค์ประกอบ หน้าจอ หรือโค้ดเทียบกับหมวดหมู่กฎ UX ที่เกี่ยวข้อง
2. **วินิจฉัยบริบทจริง:**
   - อ่านโครงสร้างคอมโพเนนต์เดิม โทเคนที่ใช้งานอยู่ และพฤติกรรมการตอบสนองต่อผู้ใช้ โดยไม่ตัดสินเพียงหน้าตาภายนอก
3. **วางโครงสร้างเชิงความหมายก่อน:**
   - เลือกใช้องค์ประกอบ HTML และความสัมพันธ์ของโหนดให้ถูกต้องก่อนเริ่มเขียนสไตล์
4. **จัดสไตล์และรักษาสถานะ:**
   - นำโทเคนและสไตล์มาประกอบ พร้อมจัดการสถานะที่จำเป็นให้ครบถ้วน เช่น ค่าเริ่มต้น ชี้เมาส์ ได้รับโฟกัส ถูกเลือก กำลังโหลด ว่างเปล่า ข้อผิดพลาด และปิดใช้งาน
5. **ตรวจสอบความสมบูรณ์รอบด้าน:**
   - ตรวจสอบการใช้งานด้วยคีย์บอร์ด ขนาดหน้าจอมือถือและเดสก์ท็อป อัตราส่วนความเปรียบต่างของสี และการลดการเคลื่อนไหว
6. **รายงานผล:**
   - สรุปผลการปรับปรุงโดยอ้างอิงรหัสกฎที่เกี่ยวข้อง พร้อมระบุสิ่งที่เปลี่ยนแปลงและวิธีตรวจรับงาน

---

## 5. รูปแบบมาตรฐานสำหรับการรายงานผลการตรวจสอบ

เมื่อ Agent รายงานข้อเสนอแนะหรือผลการปรับปรุงแก้ไข ให้ใช้รูปแบบกระชับและชัดเจนดังต่อไปนี้:

```text
รหัสกฎ: [เช่น FORM-08, VIS-01, LAY-04]
ตำแหน่ง: [ชื่อคอมโพเนนต์ ไฟล์ หรือหน้าจอ]
ประเด็นที่พบ: [คำอธิบายปัญหาและผลกระทบต่อผู้ใช้]
ก่อนปรับปรุง: [โค้ดเดิมหรือพฤติกรรมเดิม]
หลังปรับปรุง: [โค้ดใหม่หรือพฤติกรรมที่เสนอ]
การตรวจสอบ: [วิธีทดสอบหรือเกณฑ์การยืนยันผล]
```
