# กฎ UX ด้านการออกแบบและพัฒนาแบบฟอร์ม

> **ขอบเขต:** ใช้กฎเหล่านี้เมื่อออกแบบ สร้าง ทบทวน หรือปรับปรุงแบบฟอร์ม ช่องกรอกข้อมูล การตรวจสอบความถูกต้อง และการตอบสนองต่อผู้ใช้
> **ข้อกำหนดส่วนกลาง:** ปฏิบัติตามเกณฑ์ระดับคำสั่ง ลำดับความสำคัญ และขั้นตอนการทำงานใน global.md

---

## FORM-01 — ระยะห่างระหว่างกลุ่มช่องกรอกข้อมูล

**หลักการ:** ป้ายกำกับ ช่องกรอก ข้อความช่วยเหลือ และข้อความแจ้งเตือนที่อยู่ในกลุ่มเดียวกัน ต้องดูชิดกันมากกว่าระยะห่างระหว่างกลุ่ม เพื่อไม่ให้สับสนว่าป้ายกำกับเป็นของช่องใด

### ข้อกำหนด
- **MUST** วางป้ายกำกับให้ใกล้ชิดกับช่องกรอกของตนเองมากกว่าช่องกรอกก่อนหน้า
- **MUST** เว้นระยะห่างระหว่างกลุ่มช่องกรอกข้อมูลให้กว้างพอที่จะเห็นขอบเขตชัดเจน
- **MUST** จัดให้ข้อความแนะนำและข้อความแจ้งข้อผิดพลาดอยู่ภายในกลุ่มของตนเอง
- **SHOULD** ใช้ระบบโทเคนระยะห่างที่สม่ำเสมอ แทนการกำหนดระยะขอบแบบสุ่ม

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **Tailwind CSS** | Spacing ต่างระดับ | ภายในกลุ่ม: `flex flex-col gap-2`; ระหว่างกลุ่ม: `flex flex-col gap-6` |
| **Raw CSS** | Flexbox และ Grid | ภายในกลุ่ม: `display: flex; flex-direction: column; gap: 0.5rem;`; ระหว่างกลุ่ม: `gap: 1.5rem;` |

**การตรวจสอบความถูกต้อง:** เมื่อกวาดสายตามองผ่านฟอร์มอย่างรวดเร็ว สามารถจับคู่ป้ายกำกับกับช่องกรอกข้อมูลได้อย่างถูกต้องทันที

---

## FORM-02 — ปุ่มคัดลอกข้อมูลไปยังคลิปบอร์ด

**หลักการ:** ข้อมูลสำคัญที่ผู้ใช้มักนำไปใช้ต่อ เช่น รหัสอ้างอิง เลขที่บัญชี หรือลิงก์ ควรมีปุ่มคัดลอกที่กดใช้งานได้ทันที

### ข้อกำหนด
- **SHOULD** มีปุ่มคัดลอกวางอยู่ติดกับข้อมูลที่นำไปใช้ต่อได้บ่อย
- **MUST** กำหนดชื่อกำกับการเข้าถึงที่ชัดเจนให้กับปุ่มคัดลอกที่มีเฉพาะไอคอน
- **MUST** คัดลอกค่าข้อมูลจริงที่สมบูรณ์ ไม่ใช่ค่าที่ถูกตัดทอนทางสายตา
- **MUST** แจ้งสถานะความสำเร็จหรือข้อผิดพลาดหลังการคัดลอกจริง ห้ามแสดงว่าคัดลอกแล้วล่วงหน้าก่อนที่คำสั่งจะสำเร็จ
- **SHOULD** เตรียมทางเลือกสำรองเมื่อระบบไม่อนุญาตให้เข้าถึงคลิปบอร์ดอัตโนมัติ

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **Tailwind CSS** | จัดแถวตรงกับข้อมูล | `inline-flex items-center gap-2 rounded-md focus-visible:ring-2 focus-visible:ring-ring focus-visible:outline-hidden` |
| **Raw CSS** | Inline flex พร้อมสถานะโฟกัส | `display: inline-flex; align-items: center; gap: 0.5rem;` |
| **JavaScript** | Clipboard API | ใช้ `navigator.clipboard.writeText(value)` พร้อมดักจับข้อผิดพลาดและปรับปรุงข้อความสถานะ |

**การตรวจสอบความถูกต้อง:** กดปุ่มแล้วค่าที่คัดลอกไปวางตรงกับข้อมูลจริง และมีการแจ้งเตือนสถานะที่รับรู้ได้

## FORM-03 — การจัดฟอร์มแบบหลายคอลัมน์

**หลักการ:** กระแสการอ่านฟอร์มโดยรวมควรไหลจากบนลงล่างเป็นคอลัมน์เดี่ยว อนุญาตให้วางช่องกรอกคู่กันในแถวเดียวกันได้เฉพาะข้อมูลที่เป็นหน่วยเดียวกันอย่างชัดเจน

### ข้อกำหนด
- **MUST** รักษาลำดับการอ่านของฟอร์มหลักให้เป็นแนวตั้งคอลัมน์เดียวเป็นสำคัญ
- **MAY** วางช่องกรอกที่สัมพันธ์กันอย่างแนบแน่นสองถึงสามช่องในแถวเดียวกัน เช่น ชื่อและนามสกุล ส่วนประกอบของวันที่ หรือตำบล อำเภอ และรหัสไปรษณีย์
- **MUST NOT** แบ่งฟอร์มที่ไม่เกี่ยวข้องกันออกเป็นสองคอลัมน์เพียงเพื่อประหยัดความสูงของหน้าจอ
- **SHOULD** ยุบกลับมาเป็นคอลัมน์เดี่ยวบนหน้าจอมือถือ

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **Tailwind CSS** | ฟอร์มแม่เป็น Flex แถวย่อยเป็น Grid | ฟอร์มหลัก: `flex flex-col gap-6`; แถวข้อมูลย่อย: `grid grid-cols-1 gap-4 sm:grid-cols-2` |
| **Raw CSS** | ฟอร์มหลักแนวตั้ง แถวย่อยใช้ Grid | แถวย่อย: `display: grid; grid-template-columns: repeat(2, 1fr); gap: 1rem;` และปรับเป็นหนึ่งคอลัมน์ในมือถือ |

**การตรวจสอบความถูกต้อง:** ผู้ใช้สามารถเลื่อนสายตาจากบนลงล่างได้โดยไม่ต้องกวาดสายตาสลับซ้ายขวาข้ามหัวข้อที่ไม่เกี่ยวข้องกัน

## FORM-04 — ความกว้างของช่องกรอกข้อมูลที่เหมาะสม

**หลักการ:** ความกว้างของช่องกรอกควรสื่อถึงปริมาณและชนิดของข้อมูลที่คาดหวัง ช่วยให้ผู้ใช้ประเมินสิ่งที่ต้องกรอกได้ทันที

### ข้อกำหนด
- **SHOULD** กำหนดความกว้างของช่องที่รับข้อมูลสั้นให้แคบกว่าช่องรับข้อความยาว เช่น รหัสไปรษณีย์ รหัสความปลอดภัย หรือวันหมดอายุ
- **SHOULD** เว้นพื้นที่ให้ช่องอีเมล ชื่อ ที่อยู่ และข้อความทั่วไป มีความกว้างเพียงพอต่อการตรวจสอบสิ่งที่พิมพ์
- **MUST** รองรับการย่อขนาดบนหน้าจอมือถือโดยไม่เกิดการล้นแนวนอน
- **MUST NOT** ยืดทุกช่องให้กว้างเท่ากันทั้งหมดเพียงเพราะความกว้างของหน้าจอยังเหลือ

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **Tailwind CSS** | กำหนด max-width ตามชนิดข้อมูล | ช่องทั่วไป: `w-full max-w-md`; ช่องข้อมูลสั้น: `w-full max-w-32` |
| **Raw CSS** | กำหนด max-width ที่เหมาะสม | `width: 100%; max-width: 8rem; box-sizing: border-box;` |

**การตรวจสอบความถูกต้อง:** ขนาดช่องกรอกสะท้อนความยาวข้อมูลจริง และไม่ตัดทอนข้อความที่กำลังพิมพ์

---

## FORM-05 — การแจ้งผลเชิงบวกโดยไม่ทำให้ผู้ใช้เข้าใจผิด

**หลักการ:** เครื่องหมายถูกสีเขียวอาจทำให้ผู้ใช้เข้าใจผิดว่าข้อมูลถูกต้องสมบูรณ์ ทั้งที่ระบบเพียงแค่ตรวจว่ารูปแบบตัวอักษรถูกต้องเท่านั้น

### ข้อกำหนด
- **MUST NOT** แสดงว่าอีเมลหรือเบอร์โทรศัพท์ถูกต้องปราศจากคำผิด เพียงเพราะพิมพ์ถูกรูปแบบไวยากรณ์
- **SHOULD** แสดงการตอบรับเชิงบวกเฉพาะสิ่งที่ระบบสามารถตรวจสอบความจริงได้ เช่น ชื่อผู้ใช้นี้สามารถใช้ได้ หรือรหัสผ่านผ่านเกณฑ์ครบถ้วน
- **MUST** ระบุสิ่งที่ตรวจสอบผ่านด้วยข้อความที่ชัดเจน เช่น ชื่อผู้ใช้นี้ว่าง ไม่ใช้คำกว้างๆ ว่าถูกต้อง
- **MUST** แยกแยะสถานะให้ชัดเจนเมื่อมีการตรวจสอบแบบอะซิงโครนัส เช่น กำลังตรวจสอบ ตรวจสอบแล้ว รูปแบบไม่ถูกต้อง หรือไม่สามารถตรวจสอบได้
- **MUST NOT** ใช้เพียงเส้นขอบสีเขียวหรือไอคอนโดยไม่มีข้อความอธิบายประกอบ

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **Tailwind CSS** | สีสถานะพร้อมข้อความชัดเจน | `text-emerald-600 dark:text-emerald-400 border-emerald-500` ร่วมกับข้อความระบุผล |
| **Raw CSS** | Selector ตามสถานะข้อมูล | `[data-state="verified"]` พร้อมองค์ประกอบแสดงข้อความสถานะ |

**การตรวจสอบความถูกต้อง:** ข้อความระบุสิ่งที่ตรวจสอบได้จริงอย่างตรงไปตรงมา และไม่รับรองข้อมูลที่ยังไม่ได้ตรวจสอบ

## FORM-06 — ข้อความแจ้งข้อผิดพลาดต้องอยู่ติดกับช่องกรอกข้อมูล

**หลักการ:** ผู้ใช้ต้องการแก้ไขข้อผิดพลาดในจุดที่เกิดขึ้น การวางข้อความแจ้งเตือนไว้ติดกับช่องกรอกช่วยให้แก้ไขได้ทันทีโดยไม่ต้องจำ

### ข้อกำหนด
- **MUST** แสดงข้อความแจ้งข้อผิดพลาดติดกับช่องกรอกข้อมูลที่มีปัญหา ไม่วางรวมกันเฉพาะด้านบนหรือด้านล่างสุดของฟอร์ม
- **MUST** เขียนข้อความแนะนำที่บอกวิธีแก้ไขอย่างชัดเจนและนำไปปฏิบัติได้จริง
- **MUST** เชื่อมโยงช่องกรอกกับข้อความแจ้งเตือนผ่านแอตทริบิวต์ `aria-describedby` และกำหนด `aria-invalid="true"`
- **MUST NOT** พึ่งพาเพียงเส้นขอบสีแดงเพื่อสื่อสารข้อผิดพลาด
- **SHOULD** คงค่าที่ผู้ใช้พิมพ์ไว้เดิม ไม่ล้างค่าทิ้งเมื่อเกิดข้อผิดพลาด

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **Tailwind CSS** | Styling ตามสถานะความถูกต้อง | `aria-invalid:border-destructive text-sm text-destructive` |
| **Raw CSS** | Attribute selector | `input[aria-invalid="true"] { border-color: #e11d48; }` |
| **HTML และ A11y** | ความสัมพันธ์เชิงโค้ด | `<input aria-describedby="email-error" aria-invalid="true">` |

**การตรวจสอบความถูกต้อง:** ข้อความผิดพลาดระบุชัดเจนว่าต้องแก้อย่างไร และโปรแกรมอ่านหน้าจอสามารถอ่านข้อความเตือนเมื่อโฟกัสที่ช่องนั้น

## FORM-07 — ห้ามซ่อนคำแนะนำสำคัญในการกรอกฟอร์ม

**หลักการ:** ข้อกำหนดที่จำเป็นต่อการกรอกข้อมูลควรแสดงให้เห็นตลอดเวลา ผู้ใช้ไม่ควรต้องค้นหาคำแนะนำหลังไอคอนเครื่องหมายคำถามหรือการชี้เมาส์

### ข้อกำหนด
- **MUST** แสดงคำแนะนำที่จำเป็นต่อการกรอกข้อมูลให้เห็นเป็นค่าเริ่มต้น โดยวางไว้ใต้ป้ายกำกับหรือใต้ช่องกรอก
- **MUST NOT** ซ่อนเงื่อนไขสำคัญไว้หลังการชี้เมาส์ ซึ่งผู้ใช้อุปกรณ์หน้าจอสัมผัสไม่สามารถเข้าถึงได้
- **MUST** ตรวจสอบให้ผู้ใช้คีย์บอร์ดและเทคโนโลยีช่วยเหลือสามารถเข้าถึงคำแนะนำได้
- **MAY** ซ่อนเฉพาะคำอธิบายเสริมระดับลึกที่ไม่จำเป็นต่อผู้ใช้ส่วนใหญ่ไว้ในส่วนพับขยายได้

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **Tailwind CSS** | ข้อความแนะนำที่มองเห็นตลอดเวลา | `<p id="hint" class="text-sm text-muted-foreground">...</p>` |
| **Raw CSS** | สไตล์ข้อความแนะนำ | `.field-hint { display: block; font-size: 0.875rem; color: #475569; }` |

**การตรวจสอบความถูกต้อง:** คำแนะนำสำคัญมองเห็นได้ทันทีโดยไม่ต้องใช้เมาส์ชี้ และแสดงผลครบถ้วนบนอุปกรณ์มือถือ

## FORM-08 — ห้ามใช้ Placeholder แทนป้ายกำกับของช่องกรอกข้อมูล

**หลักการ:** ข้อความในช่องกรอกข้อมูลจะหายไปเมื่อเริ่มพิมพ์ ทำให้ผู้ใช้สูญเสียบริบทว่ากำลังกรอกอะไรอยู่และตรวจทานข้อมูลย้อนหลังได้ยาก

### ข้อกำหนด
- **MUST** มีป้ายกำกับที่มองเห็นได้และคงอยู่ตลอดเวลาสำหรับทุกช่องกรอกข้อมูล
- **MUST** เชื่อมโยงป้ายกำกับกับช่องกรอกข้อมูลด้วยแอตทริบิวต์ `for` และ `id`
- **MUST NOT** ใช้แอตทริบิวต์ `placeholder` แทนป้ายกำกับ หรือใช้ซ่อนป้ายกำกับไว้เพื่อความสวยงาม
- **MAY** ใช้ `placeholder` เป็นตัวอย่างรูปแบบข้อมูลสั้นๆ ได้ แต่ต้องไม่ใช่คำแนะนำที่ขาดไม่ได้

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **HTML และ A11y** | Semantic Label คู่กับ Input | `<label for="username">ชื่อผู้ใช้</label><input id="username" name="username">` |
| **Tailwind CSS** | จัดระยะป้ายกำกับ | `block text-sm font-medium text-foreground mb-1.5` |
| **Raw CSS** | กำหนด display บล็อก | `.field-label { display: block; margin-bottom: 0.375rem; font-weight: 500; }` |

**การตรวจสอบความถูกต้อง:** เมื่อพิมพ์ข้อความลงในช่องแล้ว ป้ายกำกับยังคงมองเห็นได้ชัดเจนอยู่ด้านบนหรือด้านข้าง

## FORM-09 — อย่าปิดการทำงานของปุ่มส่งฟอร์มเพียงเพราะยังกรอกไม่ครบ

**หลักการ:** การปิดปุ่มส่งฟอร์มโดยไม่บอกเหตุผลทำให้ผู้ใช้สับสนและไม่รู้ว่าต้องทำอะไรต่อ การเปิดให้กดปุ่มส่งจะช่วยกระตุ้นข้อความแจ้งเตือนข้อผิดพลาดในจุดที่ยังขาดได้

### ข้อกำหนด
- **SHOULD** เปิดให้ปุ่มส่งฟอร์มสามารถกดได้ เพื่อให้ระบบแจ้งเตือนว่ายังขาดข้อมูลช่องใดบ้าง
- **MUST** แสดงข้อความผิดพลาดที่ชัดเจนหลังผู้ใช้พยายามส่งฟอร์มที่ไม่สมบูรณ์
- **MUST NOT** ปิดปุ่มส่งฟอร์มเงียบๆ โดยไม่มีการอธิบายเงื่อนไขที่ยังไม่ผ่าน
- **MAY** ปิดปุ่มส่งฟอร์มได้เฉพาะกรณีที่มีขั้นตอนยืนยันสั้นๆ ชัดเจน เช่น การพิมพ์คำยืนยันก่อนลบข้อมูลสำคัญ
- **MAY** ปิดปุ่มชั่วคราวขณะที่กำลังส่งข้อมูลไปยังเซิร์ฟเวอร์ เพื่อป้องกันการกดส่งซ้ำ

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **Tailwind CSS** | ปุ่มเปิดใช้งานตามปกติ | `bg-primary text-primary-foreground hover:bg-primary/90 focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-ring` |
| **Raw CSS** | สไตล์ปุ่มคำสั่งหลัก | ปุ่มมีสไตล์ตอบสนองพร้อมใช้งาน และใช้ `:disabled` เฉพาะช่วงกำลังส่งข้อมูล |

**การตรวจสอบความถูกต้อง:** เมื่อกดปุ่มส่งฟอร์มในขณะที่ข้อมูลยังไม่ครบ ระบบจะแสดงจุดที่ต้องแก้ไขอย่างชัดเจน

## FORM-10 — การเลือกใช้สวิตช์เปิดปิดเทียบกับเช็กบ็อกซ์

**หลักการ:** สวิตช์เปิดปิดสื่อถึงการเปลี่ยนแปลงที่มีผลทันที ส่วนเช็กบ็อกซ์สื่อถึงการเลือกตัวเลือกที่ต้องกดยืนยันหรือส่งฟอร์มในภายหลัง

### ข้อกำหนด
- **MUST** ใช้สวิตช์เปิดปิดสำหรับการตั้งค่าที่มีผลทันทีหลังการกดสลับ
- **MUST** ใช้เช็กบ็อกซ์สำหรับการเลือกตัวเลือกหรือข้อตกลงที่ต้องกดปุ่มส่งฟอร์มเพื่อบันทึก
- **MUST NOT** ใช้สวิตช์เปิดปิดในฟอร์มที่ต้องกดปุ่มส่งด้านล่างเพื่อบันทึกผล
- **MUST** จัดการสถานะกำลังประมวลผลและสถานะล้มเหลวของการสลับค่าที่มีผลทันที

### แนวทางการนำไปใช้งาน
| การใช้งาน | องค์ประกอบที่ถูกต้อง | บทบาทเชิงความหมาย |
| :--- | :--- | :--- |
| **การตั้งค่าที่มีผลทันที** | สวิตช์สลับค่า | `<button role="switch" aria-checked="true">` หรือ Checkbox ที่กำหนดบทบาทสวิตช์ |
| **การเลือกในแบบฟอร์ม** | เช็กบ็อกซ์ | `<input type="checkbox">` พร้อมป้ายกำกับ |

**การตรวจสอบความถูกต้อง:** ชนิดของตัวเลือกสอดคล้องกับจังหวะเวลาที่ข้อมูลถูกบันทึกจริงในระบบ

## FORM-11 — หลีกเลี่ยงการตัดข้อความที่พิมพ์หรือวางทิ้งอย่างกะทันหัน

**หลักการ:** การหยุดรับข้อความกะทันหันหรือตัดข้อความที่คัดลอกมาวางทิ้งโดยไม่แจ้งเตือน สร้างความสับสนและอาจทำลายข้อมูลสำคัญของผู้ใช้

### ข้อกำหนด
- **MUST NOT** ตัดข้อความที่วางลงในช่องทิ้งเงียบๆ โดยไม่มีการแจ้งขีดจำกัด
- **SHOULD** รับข้อความที่เกินเข้ามา แล้วแสดงข้อความแจ้งเตือนจำนวนที่เกินพร้อมวิธีแก้ไข
- **MUST** แจ้งขีดจำกัดความยาวสูงสุดให้ทราบล่วงหน้าก่อนหรือขณะพิมพ์
- **MUST** คงข้อความส่วนที่เกินไว้เพื่อให้ผู้ใช้แก้ไขหรือตัดทอนได้ด้วยตนเอง

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **Tailwind CSS** | แจ้งเตือนเมื่อเกินขีดจำกัด | ข้อความเตือน: `text-destructive text-sm`; ช่องกรอก: `aria-invalid:border-destructive` |
| **JavaScript** | ตรวจสอบความยาว | ตรวจความยาวข้อความและแสดงผลส่วนต่าง แทนการใช้ `maxlength` ตัดข้อความทิ้งทันที |

**การตรวจสอบความถูกต้อง:** เมื่อวางข้อความที่ยาวเกินขีดจำกัด ข้อความไม่สูญหายและมีตัวเลขระบุว่าต้องตัดออกกี่ตัวอักษร

## FORM-12 — การจัดการจำนวนตัวอักษรเกินในกล่องข้อความหลายบรรทัด

**หลักการ:** เมื่อข้อความเกินขีดจำกัด ต้องระบุว่าเกินไปเท่าใดและเปิดโอกาสให้แก้ไขได้สะดวก

### ข้อกำหนด
- **MUST** แสดงข้อความเตือนอย่างชัดเจนเมื่อข้อความเกินจำนวนสูงสุดที่กำหนด
- **SHOULD** แสดงตัวนับจำนวนตัวอักษรที่เหลืออยู่หรือตัวเลขที่เกิน และอัปเดตตามการพิมพ์จริง
- **MUST** วางตัวนับในตำแหน่งที่มองเห็นได้ชัดเจนและไม่ถูกบดบัง เช่น ด้านล่างของกล่องข้อความ
- **MUST NOT** พึ่งพาเพียงแถบความคืบหน้าหรือสีแดงโดยไม่มีตัวเลขหรือข้อความอธิบาย
- **MUST** คงเนื้อหาทั้งหมดไว้ให้ผู้ใช้แก้ไขได้

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **Tailwind CSS** | วางตัวนับด้านล่าง | `<div class="flex justify-between text-sm text-muted-foreground mt-1"><span>คำแนะนำ</span><span>120/100</span></div>` |
| **JavaScript** | คำนวณความยาว | คำนวณความยาวและปรับปรุงข้อความสถานะใน DOM อย่างต่อเนื่อง |

**การตรวจสอบความถูกต้อง:** ตัวเลขนับจำนวนอัปเดตแบบเรียลไทม์ และแจ้งเตือนชัดเจนเมื่อจำนวนเกินเกณฑ์

## FORM-13 — การเปิดเผยข้อมูลตัวเลือกเพิ่มเติมตามลำดับขั้น

**หลักการ:** แสดงเฉพาะช่องกรอกข้อมูลที่จำเป็นก่อน และเปิดเผยตัวเลือกขั้นสูงเมื่อผู้ใช้ต้องการ เพื่อลดความซับซ้อนของหน้าจอ

### ข้อกำหนด
- **SHOULD** ซ่อนตัวเลือกขั้นสูงหรือฟิลด์ที่ไม่ค่อยได้ใช้ไว้เป็นค่าเริ่มต้น
- **MUST** มีปุ่มเปิดปิดที่ชัดเจนพร้อมป้ายกำกับ เช่น ตัวเลือกเพิ่มเติม หรือการตั้งค่าขั้นสูง
- **MUST** คงค่าข้อมูลที่กรอกไว้ในส่วนที่ซ่อน แม้ผู้ใช้จะพับส่วนนั้นเก็บไป เว้นแต่ผู้ใช้ตั้งใจล้างค่า
- **MUST** กำหนดสถานะการขยายผ่าน `aria-expanded` ให้ถูกต้องบนปุ่มเปิดปิด

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **HTML และ A11y** | ใช้ Details หรือ Button พร้อมสถานะ | `<details><summary>ตัวเลือกเพิ่มเติม</summary>...</details>` หรือ `<button aria-expanded="false">` |
| **Tailwind CSS** | ควบคุมการแสดงผล | ส่วนที่ซ่อนใช้คลาส `hidden` หรือสลับด้วยเงื่อนไขของสถานะในคอมโพเนนต์ |

**การตรวจสอบความถูกต้อง:** ช่องกรอกข้อมูลที่ซ่อนอยู่ไม่ถูกโฟกัสด้วยการกด Tab จนกว่าจะถูกเปิดออกมา

## FORM-14 — แสดงกฎข้อกำหนดรหัสผ่านอย่างชัดเจน

**หลักการ:** ผู้ใช้ควรทราบเงื่อนไขความปลอดภัยของรหัสผ่านตั้งแต่ก่อนเริ่มพิมพ์ และเห็นความคืบหน้าของเงื่อนไขที่ผ่านแล้วแบบเรียลไทม์

### ข้อกำหนด
- **MUST** แสดงรายการเงื่อนไขของรหัสผ่านติดกับช่องกรอกก่อนการส่งฟอร์ม
- **MUST** อัปเดตสถานะของแต่ละเงื่อนไขขณะที่ผู้ใช้กำลังพิมพ์
- **MUST** สื่อสารสถานะด้วยข้อความและสัญลักษณ์คู่กัน ไม่ใช้สีเขียวหรือแดงเพียงอย่างเดียว
- **MUST NOT** รอให้ผู้ใช้กดส่งฟอร์มก่อนจึงจะแจ้งว่ารหัสผ่านไม่ผ่านเกณฑ์ใด
- **SHOULD** ตรวจสอบให้เงื่อนไขที่แสดงตรงกับนโยบายความปลอดภัยที่ระบบตรวจสอบจริง

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **Tailwind CSS** | รายการเงื่อนไขพร้อมไอคอน | เงื่อนไขที่ผ่าน: `text-emerald-600 dark:text-emerald-400`; เงื่อนไขที่ยังไม่ผ่าน: `text-muted-foreground` พร้อมสัญลักษณ์ระบุ |
| **Raw CSS** | Selector ตามเงื่อนไข | `.password-rule[data-met="true"] { color: #047857; }` |

**การตรวจสอบความถูกต้อง:** เมื่อพิมพ์รหัสผ่าน เงื่อนไขที่ตรงตามเกณฑ์จะเปลี่ยนสถานะให้เห็นทันที

## FORM-15 — ใช้ข้อความบนปุ่มส่งฟอร์มที่ระบุผลลัพธ์ชัดเจน

**หลักการ:** ข้อความบนปุ่มส่งฟอร์มควรบอกการกระทำและผลลัพธ์ที่แท้จริง แทนคำกว้างๆ เชิงเทคนิค

### ข้อกำหนด
- **MUST** ใช้ข้อความบนปุ่มที่ระบุผลลัพธ์ชัดเจน เช่น สร้างบัญชี บันทึกการเปลี่ยนแปลง ส่งคำเชิญ หรือชำระเงิน 500 บาท
- **SHOULD** ระบุข้อมูลสำคัญประกอบ เช่น จำนวนเงินที่ต้องชำระ เพื่อความมั่นใจของผู้ใช้
- **MUST NOT** ใช้คำกว้างๆ เช่น ตกลง ดำเนินการ หรือส่งข้อมูล เมื่อสามารถระบุการกระทำที่ชัดเจนได้
- **MUST** ตรวจสอบให้ชื่อของปุ่มตรงกับสิ่งที่ระบบจะทำจริง

### แนวทางการนำไปใช้งาน
| หลีกเลี่ยง | แนะนำให้ใช้ |
| :--- | :--- |
| `ตกลง` / `Submit` | `สร้างบัญชีผู้ใช้` |
| `ดำเนินการ` / `Proceed` | `บันทึกข้อมูลส่วนตัว` |
| `ส่ง` / `Send` | `ส่งคำสั่งซื้อ (ชำระ 1,200 บาท)` |

**การตรวจสอบความถูกต้อง:** อ่านข้อความบนปุ่มแล้วทราบได้ทันทีว่าจะเกิดอะไรขึ้นเมื่อกด

## FORM-16 — เลื่อนหน้าจอไปยังช่องกรอกข้อมูลที่ไม่ถูกต้องช่องแรก

**หลักการ:** ในแบบฟอร์มขนาดยาว ข้อความแจ้งเตือนข้อผิดพลาดอาจอยู่นอกระยะการมองเห็น การเลื่อนหน้าจอไปยังจุดที่ผิดพลาดช่วยให้ผู้ใช้แก้ไขได้ทันที

### ข้อกำหนด
- **MUST** เลื่อนหน้าจอไปยังช่องที่ไม่ถูกต้องช่องแรกเมื่อผู้ใช้พยายามส่งฟอร์ม
- **MUST** ย้ายโฟกัสของคีย์บอร์ดไปยังช่องกรอกข้อมูลที่มีปัญหานั้นด้วย
- **SHOULD** ใช้การเลื่อนหน้าจอแบบนุ่มนวลเพื่อช่วยให้เข้าใจทิศทาง แต่ต้องปิดการเคลื่อนไหวเมื่อผู้ใช้เปิดโหมดลดการเคลื่อนไหว
- **MUST** หากช่องที่ผิดพลาดอยู่ในส่วนพับเก็บ ต้องขยายส่วนนั้นออกมาก่อนทำการเลื่อนหน้าจอ

### แนวทางการนำไปใช้งาน
| สแต็ก หรือ บริบท | รูปแบบที่แนะนำ | ตัวอย่างคลาส โค้ด หรือ โครงสร้าง |
| :--- | :--- | :--- |
| **Tailwind CSS** | กำหนดระยะเผื่อแถบด้านบน | `scroll-mt-24` ประจำแต่ละช่องกรอก |
| **Raw CSS** | Scroll margin | `scroll-margin-top: 6rem;` |
| **JavaScript** | เลื่อนหน้าจอและย้ายโฟกัส | `firstInvalid.focus({ preventScroll: true }); firstInvalid.scrollIntoView({ behavior: reduceMotion ? 'auto' : 'smooth', block: 'center' });` |

**การตรวจสอบความถูกต้อง:** เมื่อส่งฟอร์มที่ไม่ผ่าน หน้าจอจะเลื่อนและย้ายโฟกัสไปยังช่องที่มีปัญหาช่องแรกทันที

## FORM-17 — ช่วยให้ผู้ใช้กรอกฟอร์มได้ถูกต้องตั้งแต่ครั้งแรก

**หลักการ:** การป้องกันไม่ให้เกิดข้อผิดพลาด ดีกว่าการให้ผู้ใช้ตามแก้ไขข้อผิดพลาดหลังการส่งฟอร์ม

### ข้อกำหนด
- **SHOULD** ตัดช่องกรอกที่ไม่จำเป็นออกเพื่อลดภาระของผู้ใช้
- **SHOULD** กรอกข้อมูลเริ่มต้นให้อัตโนมัติในส่วนที่ระบบทราบแน่ชัดและอนุญาตให้แก้ไขได้
- **SHOULD** กำหนดชนิดของ Input, Autocomplete, และ Inputmode ให้ตรงกับชนิดข้อมูล เพื่อเรียกคีย์บอร์ดที่เหมาะสมบนมือถือ
- **MUST** ให้ผู้ใช้มีสิทธิตรวจทานและแก้ไขค่าที่ระบบคาดเดาให้อัตโนมัติเสมอ

### แนวทางการนำไปใช้งาน
| ชนิดข้อมูล | แอตทริบิวต์ที่แนะนำ |
| :--- | :--- |
| **อีเมล** | `type="email" autocomplete="email"` |
| **เบอร์โทรศัพท์** | `type="tel" autocomplete="tel"` |
| **รหัสยืนยันตัวเลข** | `inputmode="numeric" autocomplete="one-time-code"` |
| **รหัสไปรษณีย์** | `autocomplete="postal-code"` |

**การตรวจสอบความถูกต้อง:** คีย์บอร์ดบนอุปกรณ์มือถือแสดงปุ่มที่ตรงกับประเภทข้อมูล เช่น แป้นตัวเลขสำหรับเบอร์โทรศัพท์

## รูปแบบโครงสร้างพื้นฐานสำหรับแบบฟอร์ม

### โครงสร้าง Semantic HTML และการเข้าถึง

```html
<form class="form-container">
  <div class="form-field">
    <label for="user-email" class="field-label">อีเมล</label>
    <input
      id="user-email"
      name="email"
      type="email"
      autocomplete="email"
      aria-describedby="email-hint email-error"
      aria-invalid="false"
      class="field-input"
    />
    <p id="email-hint" class="field-hint">เราจะส่งใบเสร็จรับเงินไปยังที่อยู่อีเมลนี้</p>
    <p id="email-error" class="field-error" hidden></p>
  </div>
  <button type="submit" class="submit-button">
    บันทึกข้อมูล
  </button>
</form>
```

## รายการตรวจสอบก่อนส่งมอบงาน

- [ ] **FORM-01:** ระยะห่างแยกกลุ่มช่องกรอกชัดเจน ป้ายกำกับอยู่ชิดกับช่องของตนเอง
- [ ] **FORM-02:** ปุ่มคัดลอกทำงานได้จริง คัดลอกค่าสมบูรณ์ และมีข้อความแจ้งสถานะ
- [ ] **FORM-03:** ลำดับการอ่านเป็นคอลัมน์เดี่ยว ช่องที่วางคู่กันสัมพันธ์กันอย่างแท้จริง
- [ ] **FORM-04:** ความกว้างของช่องกรอกสื่อถึงความยาวข้อมูลที่คาดหวัง
- [ ] **FORM-05:** การแจ้งผลเชิงบวกระบุเฉพาะสิ่งที่ตรวจสอบได้จริง ไม่รับรองว่าปราศจากคำผิด
- [ ] **FORM-06:** ข้อความแจ้งข้อผิดพลาดวางติดกับช่องกรอก และเชื่อมโยงผ่าน ARIA
- [ ] **FORM-07:** คำแนะนำสำคัญมองเห็นได้ตลอดเวลา ไม่ถูกซ่อนหลังการชี้เมาส์
- [ ] **FORM-08:** ทุกช่องมีป้ายกำกับที่มองเห็นได้ ไม่ใช้ Placeholder แทนป้ายกำกับ
- [ ] **FORM-09:** ปุ่มส่งฟอร์มไม่ถูกปิดการทำงานอย่างไร้เหตุผล และแจ้งเตือนเมื่อข้อมูลไม่ครบ
- [ ] **FORM-10:** สวิตช์ใช้กับการตั้งค่าที่มีผลทันที เช็กบ็อกซ์ใช้กับตัวเลือกในฟอร์ม
- [ ] **FORM-11:** ไม่ตัดข้อความที่พิมพ์หรือวางทิ้ง และคงข้อมูลไว้ให้แก้ไข
- [ ] **FORM-12:** จำนวนตัวอักษรเกินแสดงอย่างชัดเจน พร้อมตัวนับที่มองเห็นได้
- [ ] **FORM-13:** ส่วนพับขยายเปิดเผยตามลำดับขั้น และไม่ทำลายข้อมูลที่กรอกไว้
- [ ] **FORM-14:** กฎเกณฑ์รหัสผ่านแสดงล่วงหน้าและอัปเดตสถานะแบบเรียลไทม์
- [ ] **FORM-15:** ข้อความบนปุ่มส่งฟอร์มระบุการกระทำและผลลัพธ์ที่ชัดเจน
- [ ] **FORM-16:** ส่งฟอร์มไม่ผ่านแล้วเลื่อนหน้าจอพร้อมย้ายโฟกัสไปยังช่องแรกที่มีปัญหา
- [ ] **FORM-17:** กำหนดชนิดของ Input และ Autocomplete เพื่อช่วยลดข้อผิดพลาด
