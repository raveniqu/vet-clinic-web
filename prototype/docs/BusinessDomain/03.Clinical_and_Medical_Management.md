# Domain 03: การบริหารจัดการงานตรวจรักษาและเวชระเบียนสัตว์ (Clinical & Medical Management)

Domain นี้เป็นหนึ่งในโดเมนหลักที่มีความสำคัญที่สุดของระบบบริหารจัดการคลินิกสัตวแพทย์ เพราะเป็นส่วนที่รับผิดชอบการบันทึกข้อมูลทางการแพทย์ การตรวจร่างกาย การประเมินอาการ การวินิจฉัยโรค การวางแผนการรักษา การสั่งการรักษา และการจัดเก็บเวชระเบียนของสัตว์เลี้ยงแต่ละตัว

หากมองในมุมของการพัฒนาระบบบริหารจัดการคลินิกสัตวแพทย์ (Veterinary Clinic ERP) Domain นี้ถือเป็นศูนย์กลางของข้อมูลทางคลินิก (Clinical Data) และเป็นส่วนที่เชื่อมโยงข้อมูลจากการเข้ารับบริการจริงไปสู่กระบวนการรักษาและการติดตามผล

ตัวอย่างเช่น

ลูกค้าชื่อคุณสมชายพาสุนัขชื่อเจ้าดำมาที่คลินิก เนื่องจากมีอาการเบื่ออาหารและอาเจียน

เมื่อเจ้าดำเข้าสู่กระบวนการตรวจรักษา ระบบจะต้องสามารถดำเนินการได้ตั้งแต่

1. รับข้อมูลการเข้ารับบริการจากระบบนัดหมายและคิว
2. เปิดรายการตรวจรักษาของเจ้าดำ
3. ตรวจสอบประวัติสุขภาพเดิม
4. ตรวจสอบประวัติการแพ้ยาและโรคประจำตัว
5. บันทึกอาการสำคัญและประวัติการเจ็บป่วย
6. บันทึกผลการตรวจร่างกายและสัญญาณชีพ
7. บันทึกผลการประเมินและการวินิจฉัยของสัตวแพทย์
8. วางแผนการรักษา
9. สั่งยาและส่งรายการไปยังระบบเภสัชกรรม
10. สั่งตรวจเลือดหรือการตรวจวินิจฉัยเพิ่มเติม
11. บันทึกผลการรักษาและคำแนะนำ
12. นัดติดตามผลการรักษา
13. จัดเก็บเวชระเบียนเพื่อใช้ในการรักษาครั้งต่อไป

ดังนั้น Domain นี้ไม่ได้เป็นเพียงระบบบันทึกอาการหรือประวัติการรักษา แต่เป็นระบบที่ช่วยสนับสนุนการดำเนินงานทางการแพทย์ตลอดวงจรการตรวจรักษา

เนื้อหาต่อไปนี้เป็นข้อเสนอการออกแบบ Business Domain สำหรับระบบ ERP ของคลินิกสัตวแพทย์ทั่วไป โดยยึดแนวทางการแบ่งขอบเขตข้อมูลให้สอดคล้องกับ Domain 01 และ Domain 02 ที่ได้ออกแบบไว้ก่อนหน้า

## 1. วัตถุประสงค์หลักของโดเมน

การบริหารจัดการงานตรวจรักษาและเวชระเบียนสัตว์มีวัตถุประสงค์สำคัญ 15 ประการ

1. จัดเก็บเวชระเบียนสัตว์เลี้ยงอย่างเป็นระบบ
2. บันทึกประวัติการเจ็บป่วยและการเข้ารับบริการแต่ละครั้ง
3. สนับสนุนการตรวจร่างกายและการประเมินสุขภาพสัตว์
4. บันทึกอาการสำคัญและประวัติการเจ็บป่วยจากเจ้าของสัตว์
5. บันทึกผลการวินิจฉัยโรคโดยสัตวแพทย์
6. จัดเก็บรายการปัญหาสุขภาพของสัตว์แต่ละตัว
7. วางแผนและติดตามการรักษา
8. บริหารรายการสั่งยาและคำสั่งทางการแพทย์
9. เชื่อมโยงการตรวจทางห้องปฏิบัติการและการวินิจฉัยด้วยภาพ
10. บันทึกการทำหัตถการและการรักษาที่เกิดขึ้นจริง
11. จัดเก็บประวัติการได้รับวัคซีนและการรักษา
12. สนับสนุนการตัดสินใจของสัตวแพทย์
13. จัดทำเอกสารทางการแพทย์และคำแนะนำสำหรับเจ้าของสัตว์
14. ติดตามผลการรักษาและประเมินผลลัพธ์
15. ควบคุมคุณภาพ ความถูกต้อง และความปลอดภัยของเวชระเบียน

เป้าหมายสูงสุด: ทำให้คลินิกมีข้อมูลทางการแพทย์ที่ถูกต้อง ครบถ้วน ตรวจสอบย้อนหลังได้ และสามารถใช้ข้อมูลดังกล่าวประกอบการดูแลสัตว์เลี้ยงอย่างต่อเนื่องตลอดช่วงชีวิต

## 2. โครงสร้างองค์ประกอบภายในโดเมน

ผมแนะนำให้แบ่ง Domain นี้ออกเป็น 21 กลุ่มความสามารถทางธุรกิจหลัก เพื่อให้ครอบคลุมการทำงานของคลินิกสัตวแพทย์ทั่วไป และสามารถนำไปออกแบบกระบวนการทำงาน ระบบซอฟต์แวร์ และฐานข้อมูลได้อย่างเป็นระบบ

| 2     | การบริหารเวชระเบียนสัตว์           | จัดเก็บและเรียกดูประวัติทางการแพทย์     |
| 3     | การบันทึกประวัติการเจ็บป่วย        | บันทึกอาการและข้อมูลจากเจ้าของสัตว์     |
| 4     | การตรวจร่างกายและสัญญาณชีพ         | บันทึกผลตรวจร่างกายและค่าทางกายภาพ      |
| 5     | การประเมินและวินิจฉัยโรค           | บันทึกข้อสรุปทางการแพทย์                |
| 6     | การบริหารรายการปัญหาสุขภาพ         | ติดตามปัญหาสุขภาพของสัตว์แต่ละตัว       |

| 8     | การบริหารคำสั่งทางการแพทย์         | จัดการคำสั่งตรวจและคำสั่งรักษา          |
| 9     | การสั่งยาและใบสั่งยา               | บันทึกคำสั่งใช้ยาและรายละเอียดการใช้    |
| 10    | การบริหารคำสั่งตรวจวินิจฉัย        | ส่งคำสั่งตรวจเลือดและตรวจภาพวินิจฉัย    |
| 11    | การบริหารบันทึกทางคลินิก           | จัดเก็บบันทึกการตรวจและการรักษา         |
| 12    | การบริหารวัคซีนและการให้วัคซีน     | วางแผนและบันทึกการให้วัคซีนจริง         |
| 13    | การบริหารข้อมูลแพ้ยาและข้อควรระวัง | ตรวจสอบความเสี่ยงก่อนรักษา              |
| 14    | การสนับสนุนการตัดสินใจทางคลินิก    | แจ้งเตือนและช่วยตรวจสอบความเสี่ยง       |
| 15    | การปรึกษาและส่งต่อทางการแพทย์      | จัดการการปรึกษาและส่งต่อสัตวแพทย์       |
| 16    | การติดตามผลการรักษา                | ติดตามอาการและประเมินผลหลังรักษา        |
| 17    | การสรุปผลและจำหน่ายสัตว์กลับ       | บันทึกผลการรักษาและคำแนะนำ              |
| 18    | การจัดทำเอกสารทางการแพทย์          | ใบรับรองและเอกสารประกอบการรักษา         |

ทั้ง 21 กลุ่มนี้จะทำงานร่วมกัน แต่ไม่ได้หมายความว่าทุกกระบวนการต้องอยู่ในหน้าจอเดียวหรือใช้ตารางฐานข้อมูลเดียวกัน

# 3. รายละเอียดกลุ่มความสามารถทางธุรกิจ

## 3.1 การบริหารรายการตรวจรักษา (Clinical Encounter Management)

เป็นกระบวนการสร้างและบริหารรายการตรวจรักษาของสัตว์เลี้ยงแต่ละครั้ง ตั้งแต่เริ่มเข้าสู่กระบวนการตรวจรักษาจนถึงการสิ้นสุดการตรวจในครั้งนั้น

รายการตรวจรักษาแต่ละครั้งควรเป็นเหตุการณ์ทางการแพทย์ที่แยกจากกัน แม้ว่าสัตว์เลี้ยงตัวเดิมจะกลับมารักษาหลายครั้งก็ตาม

วัตถุประสงค์

- สร้างรายการตรวจรักษาที่มีรหัสอ้างอิงเฉพาะ
- เชื่อมโยงสัตว์เลี้ยงกับการตรวจรักษาแต่ละครั้ง
- ระบุสัตวแพทย์ผู้รับผิดชอบ
- เชื่อมโยงการตรวจรักษากับการนัดหมายหรือการเข้ารับบริการแบบไม่ได้นัด
- ติดตามสถานะของการตรวจรักษา
- รักษาประวัติการตรวจรักษาในแต่ละครั้ง

ข้อมูลที่ควรจัดเก็บ

| รายการข้อมูล          | รายละเอียด                            |
| --------------------- | ------------------------------------- |
| รหัสรายการตรวจรักษา   | รหัสประจำรายการตรวจ                   |
| รหัสสัตว์เลี้ยง       | สัตว์ที่เข้ารับการตรวจ                |
| รหัสลูกค้า            | เจ้าของหรือผู้เกี่ยวข้อง              |
| รหัสการเข้ารับบริการ  | เชื่อมโยงกับระบบ Appointment          |
| รหัสนัดหมาย           | กรณีมีการนัดหมายล่วงหน้า              |
| สาขา                  | สาขาที่ให้บริการ                      |
| วันที่ตรวจรักษา       | วันที่เข้ารับการตรวจ                  |
| เวลาเริ่มต้น          | เวลาเริ่มกระบวนการตรวจ                |
| เวลาสิ้นสุด           | เวลาสิ้นสุดกระบวนการ                  |
| สัตวแพทย์ผู้รับผิดชอบ | ผู้รับผิดชอบหลัก                      |
| ประเภทการตรวจ         | ตรวจทั่วไป ตรวจติดตาม หรือฉุกเฉิน     |
| อาการสำคัญ            | เหตุผลหลักที่เข้ารับการตรวจ           |
| สถานะ                 | รอตรวจ กำลังตรวจ รอสรุป หรือเสร็จสิ้น |

กระบวนการทำงาน

1. สัตว์เลี้ยงเข้าสู่กระบวนการตรวจรักษาจากระบบคิว
2. ระบบตรวจสอบข้อมูลสัตว์เลี้ยง
3. ระบบค้นหาประวัติการรักษาเดิม
4. สัตวแพทย์หรือผู้ช่วยเปิดรายการตรวจรักษา
5. ระบบสร้างรหัสรายการตรวจรักษา
6. ระบุสัตวแพทย์ผู้รับผิดชอบ
7. บันทึกข้อมูลอาการและผลตรวจ
8. บันทึกการวินิจฉัยและแผนการรักษา
9. บันทึกคำสั่งทางการแพทย์
10. สรุปผลการตรวจรักษา
11. เปลี่ยนสถานะรายการตรวจรักษาตามขั้นตอนจริง
12. เก็บข้อมูลไว้ในประวัติทางการแพทย์ของสัตว์

กฎทางธุรกิจ

- รายการตรวจรักษาแต่ละครั้งต้องมีรหัสไม่ซ้ำกัน
- รายการตรวจรักษาต้องอ้างอิงสัตว์เลี้ยงที่ถูกต้อง
- สัตว์เลี้ยงหนึ่งตัวสามารถมีรายการตรวจรักษาได้หลายรายการ
- การตรวจรักษาหนึ่งครั้งอาจมีสัตวแพทย์มากกว่าหนึ่งคนเข้าร่วม
- ต้องรองรับกรณีฉุกเฉินที่ไม่มีนัดหมายล่วงหน้า
- ต้องไม่สร้างรายการตรวจรักษาซ้ำโดยไม่ได้ตั้งใจ
- ต้องเก็บวันเวลาและผู้ดำเนินการในเหตุการณ์สำคัญ
- การปิดรายการตรวจรักษาต้องไม่ทำให้ข้อมูลที่ยังไม่สมบูรณ์สูญหาย

ตัวอย่างสถานการณ์

เจ้าดำเข้ารับบริการวันที่ 10 พฤศจิกายน เนื่องจากมีอาการอาเจียน ระบบสร้างรายการตรวจรักษา `ENC-000001`

ต่อมาเจ้าดำกลับมาตรวจติดตามวันที่ 13 พฤศจิกายน ระบบจะสร้างรายการใหม่เป็น `ENC-000002` โดยเชื่อมโยงกับสัตว์เลี้ยงตัวเดิม แต่ไม่เขียนทับรายการตรวจครั้งแรก

หลักการสำคัญคือ สัตว์เลี้ยงหนึ่งตัวมีเวชระเบียนต่อเนื่อง แต่การเข้ารับบริการแต่ละครั้งต้องมีรายการตรวจรักษาแยกกัน

## 3.2 การบริหารเวชระเบียนสัตว์ (Medical Record Management)

เป็นการจัดเก็บและบริหารข้อมูลทางการแพทย์ทั้งหมดที่เกิดขึ้นกับสัตว์เลี้ยง เพื่อให้สัตวแพทย์สามารถเรียกดูประวัติย้อนหลังและใช้ประกอบการตรวจรักษาในครั้งต่อไป

เวชระเบียนเป็นข้อมูลสำคัญที่ต้องมีความต่อเนื่อง ไม่ควรจำกัดอยู่เพียงข้อมูลการตรวจครั้งล่าสุด

ข้อมูลที่ควรจัดเก็บ

1. ประวัติการเข้ารับบริการ
2. ประวัติการเจ็บป่วย
3. ประวัติการตรวจร่างกาย
4. ประวัติสัญญาณชีพ
5. ประวัติการวินิจฉัยโรค
6. ประวัติรายการปัญหาสุขภาพ
7. ประวัติแผนการรักษา
8. ประวัติการสั่งยา
9. ประวัติการให้ยา
10. ประวัติการตรวจทางห้องปฏิบัติการ
11. ประวัติการวินิจฉัยด้วยภาพ
12. ประวัติการทำหัตถการ
13. ประวัติการให้วัคซีน
14. ประวัติการแพ้ยา
15. ประวัติการติดตามผลการรักษา
16. เอกสารและภาพประกอบทางการแพทย์

ความสามารถของระบบ

- แสดงเวชระเบียนสัตว์แบบเรียงตามวันเวลา
- ค้นหาประวัติการตรวจตามช่วงวันที่
- แสดงประวัติการวินิจฉัย
- แสดงประวัติการใช้ยา
- แสดงผลตรวจทางห้องปฏิบัติการ
- แสดงภาพวินิจฉัยที่เกี่ยวข้อง
- แสดงประวัติการรักษาในแต่ละครั้ง
- แสดงสัตวแพทย์ผู้ตรวจและผู้รับผิดชอบ
- แนบเอกสารและภาพประกอบ
- พิมพ์หรือส่งออกเวชระเบียนตามสิทธิ์
- ตรวจสอบประวัติการแก้ไขข้อมูล

กฎทางธุรกิจ

- สัตว์เลี้ยงแต่ละตัวต้องมีเวชระเบียนของตนเอง
- เวชระเบียนต้องเชื่อมโยงกับรายการตรวจรักษา
- ต้องเก็บข้อมูลตามลำดับเวลา
- ห้ามลบประวัติการรักษาที่เกิดขึ้นจริงโดยไม่มีเหตุผลและหลักฐาน
- ต้องแยกข้อมูลที่เจ้าของแจ้งออกจากข้อมูลที่สัตวแพทย์ตรวจพบ
- ต้องระบุผู้บันทึกและวันเวลาที่บันทึก
- ต้องกำหนดสิทธิ์การเข้าถึงข้อมูลทางการแพทย์
- ต้องสามารถตรวจสอบข้อมูลย้อนหลังได้

ข้อสำคัญคือ ไม่ควรนำข้อมูลทั้งหมดไปเก็บไว้ในตาราง `pets` ของ Domain Customer & Pet Management แต่ควรเก็บไว้ใน Domain Clinical & Medical แล้วเชื่อมโยงด้วยรหัสสัตว์เลี้ยง

## 3.3 การบันทึกประวัติการเจ็บป่วย (Medical History & Anamnesis)

เป็นกระบวนการรวบรวมข้อมูลเกี่ยวกับอาการเจ็บป่วยของสัตว์ โดยอาศัยข้อมูลจากเจ้าของสัตว์ ประวัติสุขภาพเดิม และข้อมูลที่เกี่ยวข้องกับอาการปัจจุบัน

ข้อมูลส่วนนี้มีความสำคัญ เพราะเป็นข้อมูลพื้นฐานที่ช่วยให้สัตวแพทย์เข้าใจปัญหาก่อนทำการตรวจร่างกายและวินิจฉัย

ข้อมูลที่ควรจัดเก็บ

| รายการข้อมูล            | รายละเอียด                         |
| ----------------------- | ---------------------------------- |
| อาการสำคัญ              | ปัญหาหลักที่นำสัตว์มาพบสัตวแพทย์   |
| วันที่เริ่มมีอาการ      | วันเริ่มต้นที่เจ้าของสังเกตพบ      |
| ระยะเวลาที่มีอาการ      | จำนวนวันหรือช่วงเวลาที่เกิดอาการ   |
| ลักษณะอาการ             | รายละเอียดอาการที่พบ               |
| ความถี่ของอาการ         | เกิดขึ้นบ่อยเพียงใด                |
| ความรุนแรง              | ระดับตามข้อมูลที่ประเมิน           |
| การเปลี่ยนแปลง          | อาการดีขึ้นหรือแย่ลง               |
| ประวัติการรักษาก่อนหน้า | การรักษาจากคลินิกนี้หรือที่อื่น    |
| ประวัติการใช้ยา         | ยาที่เคยได้รับหรือกำลังใช้อยู่     |
| ประวัติอาหาร            | ประเภทอาหารและการเปลี่ยนแปลง       |
| ประวัติการขับถ่าย       | ลักษณะและความผิดปกติ               |
| ประวัติพฤติกรรม         | การเปลี่ยนแปลงพฤติกรรม             |
| ข้อมูลจากเจ้าของ        | ผู้ให้ข้อมูลและวันเวลาที่ให้ข้อมูล |

แนวทางการบันทึก

สามารถใช้แนวทางการบันทึกประวัติและผลการตรวจแบบมีโครงสร้าง เช่น

- อาการที่เจ้าของแจ้ง
- ประวัติที่เกี่ยวข้องกับอาการปัจจุบัน
- ประวัติสุขภาพเดิม
- ประวัติการใช้ยา
- ประวัติการแพ้
- ข้อมูลเพิ่มเติมที่สัตวแพทย์ต้องการสอบถาม

ความสามารถของระบบ

- บันทึกอาการสำคัญ
- บันทึกอาการตามหมวดหมู่
- บันทึกข้อมูลแบบข้อความอิสระ
- ใช้แม่แบบคำถามตามประเภทอาการ
- เชื่อมโยงกับประวัติการรักษาเดิม
- ระบุผู้ให้ข้อมูล
- ระบุแหล่งที่มาของข้อมูล
- คัดลอกข้อมูลที่เกี่ยวข้องจากการตรวจครั้งก่อนโดยไม่ทำให้กลายเป็นข้อมูลใหม่ที่ยืนยันแล้ว

กฎทางธุรกิจ

- ต้องแยกข้อมูลที่เจ้าของแจ้งออกจากข้อค้นพบของสัตวแพทย์
- ต้องไม่ถือว่าข้อมูลจากเจ้าของเป็นการวินิจฉัยโรค
- ต้องสามารถบันทึกข้อมูลที่ไม่ทราบหรือไม่สามารถยืนยันได้
- การแก้ไขข้อมูลสำคัญต้องตรวจสอบย้อนหลังได้
- ต้องบันทึกวันเวลาและผู้ให้ข้อมูล

ตัวอย่างเช่น เจ้าของแจ้งว่าเจ้าดำอาเจียนวันละ 3 ครั้ง ข้อมูลนี้เป็นประวัติที่เจ้าของแจ้ง ไม่ใช่ข้อสรุปว่าเจ้าดำเป็นโรคระบบทางเดินอาหารชนิดใดชนิดหนึ่ง

## 3.4 การตรวจร่างกายและสัญญาณชีพ (Physical Examination & Vital Signs)

เป็นกระบวนการบันทึกผลการตรวจร่างกายของสัตว์เลี้ยงโดยสัตวแพทย์หรือบุคลากรที่ได้รับมอบหมายตามขอบเขตหน้าที่

ข้อมูลจากการตรวจร่างกายเป็นข้อมูลสำคัญที่ใช้ประกอบการประเมินและวินิจฉัยโรค

| อัตราการเต้นหัวใจ               | จำนวนครั้งต่อนาที        |

7. เปรียบเทียบค่าปัจจุบันกับค่าครั้งก่อน
8. บันทึกผลตรวจแยกตามระบบร่างกาย
9. แนบภาพประกอบการตรวจ

- การตรวจแต่ละครั้งต้องมีวันเวลา
- ต้องระบุผู้ตรวจหรือผู้บันทึก
- ต้องจัดเก็บค่าที่ตรวจได้จริง ไม่ควรเขียนทับค่าเดิม
- ต้องรองรับหน่วยวัดที่แตกต่างกันตามประเภทข้อมูล
- ต้องแยกค่าที่วัดได้ออกจากค่าที่คาดการณ์
- ต้องรองรับกรณีที่ไม่ได้ตรวจบางรายการ
- ต้องสามารถระบุได้ว่าค่าที่บันทึกมาจากอุปกรณ์หรือการกรอกด้วยมือ

ข้อควรระวัง: ไม่ควรเก็บน้ำหนักหรืออุณหภูมิไว้เพียงช่องเดียวในตารางข้อมูลสัตว์เลี้ยง เพราะเป็นข้อมูลที่เปลี่ยนแปลงตามเวลา ควรเก็บเป็นประวัติการตรวจวัดแต่ละครั้ง

## 3.5 การประเมินและวินิจฉัยโรค (Clinical Assessment & Diagnosis)

เป็นกระบวนการที่สัตวแพทย์นำข้อมูลจากประวัติการเจ็บป่วย ผลตรวจร่างกาย และผลตรวจเพิ่มเติมมาประเมินเพื่อกำหนดข้อวินิจฉัยทางการแพทย์

ถือเป็นหนึ่งในความสามารถที่สำคัญที่สุดของ Domain นี้

ประเภทของข้อมูลการวินิจฉัย

1. การวินิจฉัยเบื้องต้น
2. การวินิจฉัยแยกโรค
3. การวินิจฉัยที่ยืนยันแล้ว
4. การวินิจฉัยตามอาการ
5. การวินิจฉัยโรคประจำตัว
6. การวินิจฉัยภาวะแทรกซ้อน
7. การประเมินผลหลังการรักษา

ข้อมูลที่ควรจัดเก็บ

| รายการข้อมูล         | รายละเอียด                      |

| รหัสรายการตรวจรักษา  | การตรวจรักษาที่เกี่ยวข้อง       |

| ชื่อโรค              | ชื่อโรคหรือภาวะ                 |
| ประเภทการวินิจฉัย    | เบื้องต้น แยกโรค หรือยืนยันแล้ว |

ความสามารถของระบบ

- บันทึกการวินิจฉัยได้หลายรายการต่อการตรวจหนึ่งครั้ง
- เลือกโรคจากรายการมาตรฐาน
- บันทึกคำอธิบายเพิ่มเติม
- ระบุสถานะการวินิจฉัย
- บันทึกการวินิจฉัยแยกโรค
- เชื่อมโยงกับผลตรวจทางห้องปฏิบัติการ
- เชื่อมโยงกับผลวินิจฉัยด้วยภาพ
- แสดงประวัติการวินิจฉัยย้อนหลัง
- แก้ไขสถานะการวินิจฉัยโดยเก็บประวัติ

กฎทางธุรกิจ

- การวินิจฉัยต้องมีสัตวแพทย์ผู้รับผิดชอบ
- ต้องแยกการวินิจฉัยเบื้องต้นออกจากการวินิจฉัยที่ยืนยันแล้ว
- ต้องรองรับกรณีที่ยังไม่สามารถระบุโรคได้
- ต้องไม่บังคับให้ทุกการตรวจรักษาต้องมีรหัสโรคที่ยืนยันแล้ว
- ต้องบันทึกเหตุผลหรือข้อมูลประกอบตามความเหมาะสม
- การแก้ไขข้อวินิจฉัยต้องตรวจสอบย้อนหลังได้

ตัวอย่างเช่น เจ้าดำมีอาการอาเจียนและเบื่ออาหาร สัตวแพทย์อาจบันทึกการวินิจฉัยเบื้องต้นและรายการโรคที่ต้องพิจารณาเพิ่มเติม ก่อนจะมีผลตรวจที่ช่วยยืนยันข้อวินิจฉัยในภายหลัง

ข้อสำคัญ: ระบบ ERP ควรเป็นเครื่องมือจัดเก็บและสนับสนุนการทำงานของสัตวแพทย์ ไม่ควรตัดสินหรือยืนยันโรคแทนสัตวแพทย์โดยอัตโนมัติ

## 3.6 การบริหารรายการปัญหาสุขภาพ (Problem List Management)

เป็นการรวบรวมปัญหาสุขภาพที่สัตว์เลี้ยงกำลังมีหรือเคยมี เพื่อให้สัตวแพทย์สามารถติดตามปัญหาแต่ละรายการได้อย่างต่อเนื่อง

แตกต่างจากการบันทึกการวินิจฉัยในแต่ละครั้ง เพราะรายการปัญหาสุขภาพเป็นภาพรวมของปัญหาที่ต้องติดตามในระยะยาว

ตัวอย่างรายการปัญหา

- โรคไตเรื้อรัง
- ภาวะน้ำหนักเกิน
- โรคผิวหนังเรื้อรัง
- ภาวะข้อเสื่อม
- ประวัติแพ้ยาบางชนิด
- ภาวะผิดปกติที่อยู่ระหว่างการติดตาม

ข้อมูลที่ควรจัดเก็บ

- รหัสรายการปัญหา
- รหัสสัตว์เลี้ยง
- รหัสการวินิจฉัยที่เกี่ยวข้อง
- ชื่อปัญหา
- รายละเอียดปัญหา
- วันที่เริ่มพบ
- วันที่สิ้นสุด
- ระดับความสำคัญ
- สถานะปัจจุบัน
- ผู้รับผิดชอบ
- แผนการติดตาม
- หมายเหตุ

สถานะที่ควรรองรับ

- ปัญหาที่กำลังดำเนินอยู่
- ปัญหาที่อยู่ระหว่างการติดตาม
- ปัญหาที่ควบคุมได้
- ปัญหาที่สิ้นสุดแล้ว
- ปัญหาที่รอการยืนยัน

ความสามารถของระบบ

- เพิ่มรายการปัญหาสุขภาพ
- เชื่อมโยงกับการวินิจฉัย
- แสดงรายการปัญหาปัจจุบัน
- แสดงรายการปัญหาที่สิ้นสุดแล้ว
- กำหนดระดับความสำคัญ
- บันทึกการเปลี่ยนแปลงสถานะ
- แจ้งเตือนปัญหาสำคัญก่อนเริ่มการรักษา

กฎทางธุรกิจ

- รายการปัญหาต้องอ้างอิงสัตว์เลี้ยง
- ต้องระบุแหล่งที่มาของปัญหา
- ต้องแยกปัญหาที่สงสัยออกจากปัญหาที่ได้รับการยืนยัน
- การปิดปัญหาต้องมีเหตุผล
- ต้องไม่ลบประวัติปัญหาที่สิ้นสุดแล้ว

## 3.7 การวางแผนการรักษา (Treatment Planning)

เป็นกระบวนการกำหนดแนวทางการรักษาสัตว์เลี้ยงตามผลการประเมินและการวินิจฉัยของสัตวแพทย์

แผนการรักษาอาจประกอบด้วยหลายกิจกรรม เช่น การให้ยา การทำหัตถการ การตรวจเพิ่มเติม การปรับอาหาร และการนัดติดตามผล

ข้อมูลที่ควรจัดเก็บ

| รายการข้อมูล        | รายละเอียด                         |
| ------------------- | ---------------------------------- |
| รหัสแผนการรักษา     | รหัสประจำแผน                       |
| รหัสรายการตรวจรักษา | การตรวจรักษาที่เกี่ยวข้อง          |
| เป้าหมายการรักษา    | ผลลัพธ์ที่ต้องการ                  |
| ปัญหาสุขภาพ         | ปัญหาที่ต้องรักษา                  |
| แนวทางการรักษา      | รายละเอียดวิธีการรักษา             |
| รายการยา            | ยาที่เกี่ยวข้อง                    |
| รายการหัตถการ       | หัตถการที่ต้องดำเนินการ            |
| รายการตรวจเพิ่มเติม | การตรวจที่จำเป็น                   |
| ระยะเวลาการรักษา    | ระยะเวลาที่คาดการณ์                |
| วันติดตามผล         | วันที่ต้องประเมินซ้ำ               |
| สัตวแพทย์ผู้วางแผน  | ผู้รับผิดชอบ                       |
| สถานะ               | ร่าง อนุมัติ ดำเนินการ หรือสิ้นสุด |

ความสามารถของระบบ

- สร้างแผนการรักษา
- กำหนดเป้าหมายการรักษา
- แบ่งแผนเป็นกิจกรรมย่อย
- กำหนดระยะเวลาการรักษา
- เชื่อมโยงกับรายการยา
- เชื่อมโยงกับรายการตรวจเพิ่มเติม
- เชื่อมโยงกับหัตถการ
- กำหนดวันติดตามผล
- เปรียบเทียบแผนที่วางไว้กับการรักษาที่เกิดขึ้นจริง

กฎทางธุรกิจ

- แผนการรักษาต้องเชื่อมโยงกับรายการตรวจรักษาหรือปัญหาสุขภาพ
- ต้องมีผู้รับผิดชอบในการวางแผน
- ต้องรองรับการเปลี่ยนแปลงแผนการรักษา
- ต้องเก็บประวัติแผนเดิมและแผนใหม่
- ต้องแยกแผนการรักษาออกจากรายการที่ดำเนินการจริง
- การเปลี่ยนแผนต้องไม่ทำให้ประวัติการรักษาที่เกิดขึ้นจริงสูญหาย

ตัวอย่างเช่น สัตวแพทย์วางแผนรักษาเจ้าดำโดยให้ยา ตรวจเลือด และนัดติดตามผลในอีก 3 วัน ระบบจะต้องแยกให้ได้ว่าอะไรคือแผนที่กำหนดไว้ และอะไรคือกิจกรรมที่ดำเนินการเสร็จแล้วจริง

## 3.8 การบริหารคำสั่งทางการแพทย์ (Clinical Orders Management)

เป็นการบริหารรายการคำสั่งที่สัตวแพทย์กำหนดเพื่อให้เกิดการดำเนินงานทางการแพทย์ เช่น สั่งยา สั่งตรวจทางห้องปฏิบัติการ สั่งตรวจภาพวินิจฉัย หรือสั่งทำหัตถการ

กลุ่มนี้ทำหน้าที่เป็นจุดเชื่อมระหว่างการตัดสินใจทางการแพทย์กับ Domain ที่รับผิดชอบการดำเนินงานจริง

ประเภทคำสั่งทางการแพทย์

1. คำสั่งใช้ยา
2. คำสั่งตรวจเลือด
3. คำสั่งตรวจปัสสาวะ
4. คำสั่งตรวจอุจจาระ
5. คำสั่งเอกซเรย์
6. คำสั่งอัลตราซาวนด์
7. คำสั่งทำหัตถการ
8. คำสั่งให้สารน้ำ
9. คำสั่งติดตามสัญญาณชีพ
10. คำสั่งการดูแลอื่น ๆ

ข้อมูลที่ควรจัดเก็บ

- รหัสคำสั่ง
- ประเภทคำสั่ง
- รหัสรายการตรวจรักษา
- รหัสแผนการรักษา
- รายละเอียดคำสั่ง
- วันที่และเวลาที่สั่ง
- ผู้สั่ง
- ระดับความเร่งด่วน
- สถานะคำสั่ง
- ผู้รับคำสั่ง
- วันที่และเวลาที่ดำเนินการ
- ผลการดำเนินการ

สถานะที่ควรรองรับ

- ร่าง
- รออนุมัติ
- สั่งแล้ว
- รับคำสั่งแล้ว
- กำลังดำเนินการ
- ดำเนินการเสร็จ
- ยกเลิก
- ไม่สามารถดำเนินการได้

กฎทางธุรกิจ

- คำสั่งทางการแพทย์ต้องมีผู้สั่งที่ได้รับอนุญาต
- ต้องเชื่อมโยงกับรายการตรวจรักษาที่ถูกต้อง
- ต้องมีประวัติการเปลี่ยนแปลง
- ต้องแยกคำสั่งออกจากผลการดำเนินงานจริง
- การยกเลิกคำสั่งต้องมีเหตุผล
- ต้องป้องกันการดำเนินการคำสั่งเดิมซ้ำโดยไม่ตั้งใจ

ข้อสำคัญคือ Domain Clinical เป็นเจ้าของข้อมูลการตัดสินใจและคำสั่งทางการแพทย์ ส่วน Domain ที่รับผิดชอบงานปลายทางจะเป็นเจ้าของข้อมูลการปฏิบัติงานจริง

ตัวอย่างเช่น Clinical สั่งตรวจเลือด แต่ Laboratory เป็นผู้รับผิดชอบการรับสิ่งส่งตรวจ การตรวจวิเคราะห์ และผลตรวจ

## 3.9 การสั่งยาและใบสั่งยา (Medication Ordering & Prescription Management)

เป็นกระบวนการที่สัตวแพทย์กำหนดรายการยาและวิธีใช้ยาให้สัตว์เลี้ยง โดยบันทึกเป็นคำสั่งทางการแพทย์เพื่อส่งต่อไปยังระบบเภสัชกรรม

ต้องแยกให้ชัดเจนระหว่างการสั่งยาและการจ่ายยา

- Clinical รับผิดชอบการตัดสินใจและสั่งใช้ยา
- Pharmacy รับผิดชอบการจัดการคลังยา การตรวจสอบยา การจ่ายยา และข้อมูลการจ่ายจริง

ข้อมูลที่ควรจัดเก็บ

| รายการข้อมูล        | รายละเอียด                       |
| ------------------- | -------------------------------- |
| รหัสใบสั่งยา        | รหัสรายการสั่งยา                 |
| รหัสสัตว์เลี้ยง     | สัตว์ที่ได้รับคำสั่งยา           |
| รหัสรายการตรวจรักษา | การตรวจรักษาที่เกี่ยวข้อง        |
| รหัสยา              | อ้างอิงรายการยาจาก Pharmacy      |
| ชื่อยา              | ชื่อยาที่สั่ง                    |
| ความแรง             | ความเข้มข้นของยา                 |
| รูปแบบยา            | เม็ด น้ำ ยาฉีด หรือรูปแบบอื่น    |
| ขนาดยา              | ปริมาณยาที่กำหนด                 |
| หน่วย               | หน่วยของขนาดยา                   |
| วิธีใช้             | ช่องทางหรือวิธีการให้ยา          |
| ความถี่             | ความถี่ในการให้ยา                |
| ระยะเวลา            | ระยะเวลาที่ต้องใช้ยา             |
| จำนวน               | ปริมาณยาที่สั่ง                  |
| คำแนะนำ             | ข้อควรระวังและคำแนะนำ            |
| ผู้สั่งยา           | สัตวแพทย์ผู้สั่ง                 |
| สถานะ               | ร่าง สั่งแล้ว ยกเลิก หรือสิ้นสุด |

ความสามารถของระบบ

- เลือกรายการยาจากฐานข้อมูลกลาง
- บันทึกขนาดยา
- บันทึกวิธีใช้ยา
- บันทึกความถี่และระยะเวลาการใช้
- บันทึกคำแนะนำเพิ่มเติม
- ตรวจสอบประวัติการแพ้ยา
- ตรวจสอบคำสั่งยาที่อาจซ้ำซ้อน
- ส่งใบสั่งยาไปยังระบบ Pharmacy
- ตรวจสอบสถานะการรับคำสั่งและการจ่ายยา
- พิมพ์ใบสั่งยา

กฎทางธุรกิจ

- การสั่งยาต้องมีสัตวแพทย์ผู้รับผิดชอบ
- ต้องอ้างอิงรายการยาจากแหล่งข้อมูลกลาง
- ต้องบันทึกขนาดยาและหน่วยให้ชัดเจน
- ต้องตรวจสอบประวัติการแพ้ยาก่อนยืนยันคำสั่ง
- ต้องรองรับการแก้ไขหรือยกเลิกคำสั่ง
- ต้องเก็บประวัติคำสั่งเดิม
- ต้องไม่ถือว่าการสั่งยาเท่ากับการจ่ายยาแล้ว
- ต้องไม่ถือว่าการจ่ายยาเท่ากับสัตว์ได้รับยาแล้ว

ข้อสุดท้ายมีความสำคัญมาก เพราะการจ่ายยากลับบ้านกับการให้ยาภายในคลินิกเป็นคนละเหตุการณ์ และอาจต้องมีการบันทึกข้อมูลการให้ยาจริงแยกต่างหาก

## 3.10 การบริหารคำสั่งตรวจวินิจฉัย (Diagnostic Orders Management)

เป็นการสร้างและส่งคำสั่งตรวจเพิ่มเติม เพื่อให้สัตวแพทย์มีข้อมูลประกอบการประเมินและวินิจฉัยโรค

ประเภทการตรวจ

- ตรวจความสมบูรณ์ของเม็ดเลือด
- ตรวจค่าทางชีวเคมีในเลือด
- ตรวจปัสสาวะ
- ตรวจอุจจาระ
- ตรวจหาเชื้อ
- ตรวจเอกซเรย์
- ตรวจอัลตราซาวนด์
- ตรวจวินิจฉัยด้วยภาพประเภทอื่น

ข้อมูลที่ควรจัดเก็บ

- รหัสคำสั่งตรวจ
- รหัสรายการตรวจรักษา
- ประเภทการตรวจ
- รายการตรวจ
- เหตุผลในการตรวจ
- ข้อมูลทางคลินิกที่เกี่ยวข้อง
- ระดับความเร่งด่วน
- วันที่สั่งตรวจ
- ผู้สั่งตรวจ
- สถานะคำสั่ง
- ผลตรวจที่ได้รับ
- วันที่ได้รับผล

ความสามารถของระบบ

- เลือกรายการตรวจ
- สร้างคำสั่งตรวจหลายรายการ
- ระบุเหตุผลในการตรวจ
- ระบุระดับความเร่งด่วน
- ส่งคำสั่งไปยัง Laboratory หรือ Diagnostic Imaging
- ติดตามสถานะการตรวจ
- แสดงผลตรวจที่ได้รับกลับมา
- เชื่อมโยงผลตรวจกับการวินิจฉัย
- แจ้งเตือนเมื่อผลตรวจพร้อมหรือมีรายการค้าง

กฎทางธุรกิจ

- คำสั่งตรวจต้องเชื่อมโยงกับรายการตรวจรักษา
- ต้องระบุผู้สั่งตรวจ
- ต้องแยกคำสั่งตรวจกับผลตรวจ
- ต้องสามารถยกเลิกคำสั่งได้ตามเงื่อนไข
- ต้องเก็บประวัติการเปลี่ยนแปลง
- ต้องรองรับผลตรวจจากสถานพยาบาลภายนอก
- ต้องไม่สร้างผลตรวจขึ้นเองจากคำสั่งตรวจที่ยังไม่มีผลจริง

การกำหนดขอบเขตข้อมูล

Clinical เป็นเจ้าของคำสั่งตรวจและการนำผลไปใช้ประกอบการวินิจฉัย ส่วน Laboratory & Diagnostic Imaging เป็นเจ้าของกระบวนการตรวจวิเคราะห์ ผลตรวจ และข้อมูลภาพวินิจฉัย

## 3.11 การบริหารบันทึกทางคลินิก (Clinical Notes Management)

เป็นการจัดเก็บบันทึกทางการแพทย์ที่เกิดขึ้นระหว่างการตรวจรักษา เพื่อให้มีรายละเอียดครบถ้วนและสามารถตรวจสอบย้อนหลังได้

แนวทางที่แนะนำคือใช้รูปแบบการบันทึกที่มีโครงสร้าง เช่น SOAP ซึ่งประกอบด้วย

- ข้อมูลจากเจ้าของหรืออาการที่แจ้ง (Subjective)
- ข้อมูลจากการตรวจร่างกายและผลตรวจ (Objective)
- การประเมินและวินิจฉัย (Assessment)
- แผนการรักษา (Plan)

ข้อมูลที่ควรจัดเก็บ

1. รหัสบันทึกทางคลินิก
2. รหัสรายการตรวจรักษา
3. ประเภทบันทึก
4. รายละเอียดบันทึก
5. วันที่และเวลาที่บันทึก
6. ผู้บันทึก
7. ผู้ตรวจสอบ
8. สถานะบันทึก
9. เวลาที่รับรองบันทึก
10. เอกสารหรือไฟล์ประกอบ

ความสามารถของระบบ

- บันทึกข้อมูลแบบข้อความ
- ใช้แม่แบบการบันทึก
- บันทึกแบบ SOAP
- บันทึกข้อความแยกตามหัวข้อ
- แนบรูปภาพ
- แนบเอกสาร
- บันทึกการเปลี่ยนแปลง
- แสดงประวัติบันทึก
- รองรับการบันทึกฉบับร่าง
- รองรับการรับรองบันทึกโดยสัตวแพทย์

กฎทางธุรกิจ

- บันทึกต้องเชื่อมโยงกับรายการตรวจรักษา
- ต้องระบุผู้บันทึก
- ต้องมีวันและเวลา
- ต้องแยกบันทึกฉบับร่างออกจากบันทึกที่รับรองแล้ว
- บันทึกที่รับรองแล้วไม่ควรถูกแก้ไขโดยเขียนทับ
- หากจำเป็นต้องแก้ไข ต้องใช้กระบวนการเพิ่มเติมบันทึกหรือแก้ไขพร้อมเหตุผล
- ต้องรักษาข้อมูลเดิมไว้สำหรับการตรวจสอบ

ตัวอย่างเช่น สัตวแพทย์บันทึกผลตรวจและรับรองเวชระเบียนแล้ว หากพบว่าพิมพ์ข้อมูลผิดภายหลัง ระบบควรรองรับการเพิ่มบันทึกแก้ไขโดยแสดงว่าใครเป็นผู้แก้ไข แก้ไขเมื่อใด และแก้ไขด้วยเหตุผลใด

## 3.12 การบริหารวัคซีนและการให้วัคซีน (Vaccination Management)

เป็นการบริหารแผนการให้วัคซีนและบันทึกการให้วัคซีนจริงแก่สัตว์เลี้ยง

แม้ Domain Customer & Pet Management จะมีการแสดงประวัติวัคซีน แต่แหล่งข้อมูลหลักของการให้วัคซีนจริงควรอยู่ในระบบทางคลินิกตามหลัก Data Ownership ที่กำหนดไว้ก่อนหน้า

ข้อมูลที่ควรจัดเก็บ

- รหัสรายการวัคซีน
- รหัสสัตว์เลี้ยง
- รหัสรายการตรวจรักษา
- ชื่อวัคซีน
- ประเภทวัคซีน
- โรคที่ป้องกัน
- วันที่ให้วัคซีน
- หมายเลขล็อต
- วันหมดอายุ
- ผู้ผลิต
- ปริมาณที่ให้
- วิธีการให้
- ตำแหน่งที่ให้
- ผู้ให้วัคซีน
- สัตวแพทย์ผู้รับผิดชอบ
- ปฏิกิริยาหลังได้รับวัคซีน
- วันที่แนะนำให้ติดตามหรือให้ครั้งถัดไป

ความสามารถของระบบ

- บันทึกแผนการให้วัคซีน
- บันทึกการให้วัคซีนจริง
- ตรวจสอบประวัติวัคซีน
- บันทึกหมายเลขล็อต
- ตรวจสอบวันหมดอายุ
- สร้างใบรับรองวัคซีน
- แจ้งเตือนกำหนดวัคซีนครั้งต่อไป
- บันทึกปฏิกิริยาหลังได้รับวัคซีน
- เชื่อมโยงกับระบบ Pharmacy เพื่ออ้างอิงวัคซีนที่ใช้จริง

กฎทางธุรกิจ

- ต้องแยกวัคซีนที่วางแผนไว้กับวัคซีนที่ได้รับจริง
- การบันทึกว่าได้รับวัคซีนแล้วต้องมีเหตุการณ์การให้วัคซีนจริง
- ต้องระบุผู้ให้วัคซีน
- ต้องระบุวันที่และหมายเลขล็อตเมื่อมีข้อมูล
- ต้องรองรับประวัติวัคซีนจากสถานพยาบาลอื่น
- วันกำหนดครั้งถัดไปต้องเป็นไปตามแผนที่สัตวแพทย์กำหนด
- การแก้ไขประวัติวัคซีนต้องตรวจสอบย้อนหลังได้

## 3.13 การบริหารข้อมูลแพ้ยาและข้อควรระวัง (Allergy & Medical Alerts Management)

เป็นการบริหารข้อมูลที่มีผลต่อความปลอดภัยของสัตว์เลี้ยงก่อนและระหว่างการตรวจรักษา

ข้อมูลนี้อาจมาจากเจ้าของแจ้ง ประวัติเดิม หรือผลการประเมินของสัตวแพทย์ จึงต้องระบุแหล่งที่มาและระดับความน่าเชื่อถือให้ชัดเจน

ประเภทข้อมูลที่ควรจัดเก็บ

1. ประวัติแพ้ยา
2. ประวัติแพ้อาหาร
3. ประวัติแพ้วัคซีน
4. ประวัติแพ้สารเคมี
5. ประวัติแพ้สารอื่น
6. โรคประจำตัว
7. ภาวะสุขภาพที่ต้องเฝ้าระวัง
8. ประวัติอาการไม่พึงประสงค์จากการรักษา
9. ข้อควรระวังในการใช้ยา
10. ข้อควรระวังในการทำหัตถการ

ข้อมูลที่ควรจัดเก็บ

| รายการข้อมูล        | รายละเอียด                        |
| ------------------- | --------------------------------- |
| รหัสข้อมูลแจ้งเตือน | รหัสประจำรายการ                   |
| รหัสสัตว์เลี้ยง     | สัตว์ที่เกี่ยวข้อง                |
| ประเภทข้อมูล        | แพ้ยา โรคประจำตัว หรือข้อควรระวัง |
| ชื่อยา/สาร/โรค      | รายละเอียดที่เกี่ยวข้อง           |
| อาการ               | อาการที่เคยพบ                     |
| ระดับความรุนแรง     | ตามการประเมิน                     |
| แหล่งข้อมูล         | เจ้าของแจ้งหรือสัตวแพทย์ตรวจพบ    |
| สถานะ               | สงสัย ยืนยัน หรือยุติแล้ว         |
| วันที่เริ่มต้น      | วันที่เริ่มพบ                     |
| ผู้บันทึก           | ผู้บันทึกข้อมูล                   |
| ผู้ยืนยัน           | ผู้ตรวจสอบข้อมูล                  |
| หมายเหตุ            | รายละเอียดเพิ่มเติม               |

ความสามารถของระบบ

- แสดงคำเตือนแพ้ยาอย่างชัดเจน
- แสดงโรคประจำตัวก่อนเริ่มตรวจรักษา
- ตรวจสอบคำสั่งยาที่อาจเกี่ยวข้องกับประวัติแพ้
- แสดงข้อควรระวังก่อนทำหัตถการ
- บันทึกสถานะการยืนยันข้อมูล
- บันทึกประวัติการแก้ไข
- แจ้งเตือนเมื่อมีข้อมูลความเสี่ยงใหม่

กฎทางธุรกิจ

- ข้อมูลแพ้ยาต้องแสดงในจุดที่สัตวแพทย์เห็นได้ง่าย
- ต้องระบุแหล่งที่มาของข้อมูล
- ต้องแยกข้อมูลที่สงสัยออกจากข้อมูลที่ยืนยันแล้ว
- ต้องไม่ลบประวัติแพ้ยาเดิมโดยไม่มีหลักฐาน
- การยกเลิกสถานะแพ้ยาต้องมีผู้รับผิดชอบ
- ระบบแจ้งเตือนต้องไม่ตัดสินใจแทนสัตวแพทย์

ข้อควรระวังด้านการออกแบบ: Domain Customer & Pet Management สามารถแสดงข้อมูลแพ้ยาและโรคประจำตัวเพื่อให้เรียกดูได้สะดวก แต่ข้อมูลทางการแพทย์ที่เป็นแหล่งข้อมูลหลักและการเปลี่ยนแปลงสถานะควรบริหารโดย Domain Clinical & Medical

## 3.14 การสนับสนุนการตัดสินใจทางคลินิก (Clinical Decision Support)

เป็นความสามารถที่ช่วยให้สัตวแพทย์ได้รับข้อมูลและคำเตือนที่เกี่ยวข้องในระหว่างการตรวจรักษา

ระบบไม่ได้ทำหน้าที่วินิจฉัยแทนสัตวแพทย์ แต่ช่วยตรวจสอบข้อมูลที่เกี่ยวข้องและลดโอกาสเกิดความผิดพลาด

ตัวอย่างความสามารถ

- แจ้งเตือนประวัติแพ้ยา
- แจ้งเตือนโรคประจำตัว
- ตรวจสอบคำสั่งยาที่อาจซ้ำซ้อน
- ตรวจสอบความครบถ้วนของคำสั่งยา
- แจ้งเตือนข้อมูลที่จำเป็นก่อนทำหัตถการ
- แจ้งเตือนผลตรวจที่ยังไม่รับทราบ
- แจ้งเตือนผลตรวจที่มีค่าผิดปกติตามเกณฑ์ที่กำหนด
- แสดงประวัติการรักษาที่เกี่ยวข้อง
- แสดงข้อควรระวังตามข้อมูลสัตว์เลี้ยง

ข้อมูลที่ควรจัดเก็บ

- รหัสการแจ้งเตือน
- รหัสรายการตรวจรักษา
- ประเภทการแจ้งเตือน
- รายละเอียดคำเตือน
- ระดับความสำคัญ
- แหล่งที่มาของข้อมูล
- วันที่และเวลาที่แจ้ง
- ผู้รับการแจ้งเตือน
- ผลการตอบสนอง
- เหตุผลที่ยืนยันหรือข้ามคำเตือน

กฎทางธุรกิจ

- ต้องแสดงแหล่งที่มาของคำเตือน
- ต้องไม่แสดงคำเตือนที่ไม่มีข้อมูลรองรับ
- คำเตือนที่มีความเสี่ยงสูงควรมีขั้นตอนรับทราบ
- ต้องบันทึกการตอบสนองต่อคำเตือนที่สำคัญ
- ระบบไม่ควรตัดสินใจทางการแพทย์แทนสัตวแพทย์
- ต้องสามารถปรับเกณฑ์การแจ้งเตือนตามนโยบายและหลักวิชาชีพ

## 3.15 การปรึกษาและส่งต่อทางการแพทย์ (Clinical Consultation & Referral)

เป็นกระบวนการที่สัตวแพทย์ต้องการปรึกษาผู้เชี่ยวชาญหรือส่งต่อสัตว์เลี้ยงไปยังสถานพยาบาลอื่นเพื่อรับการตรวจรักษาที่เหมาะสม

สถานการณ์ที่อาจเกิดขึ้น

- ต้องการสัตวแพทย์เฉพาะทาง
- ต้องการเครื่องมือวินิจฉัยที่คลินิกไม่มี
- ต้องการการรักษาที่เกินขีดความสามารถของคลินิก
- ต้องการความเห็นจากสัตวแพทย์อีกคน
- ต้องการส่งต่อเพื่อดูแลผู้ป่วยฉุกเฉิน
- ต้องการส่งต่อเพื่อผ่าตัดหรือรักษาเฉพาะทาง

ข้อมูลที่ควรจัดเก็บ

- รหัสการส่งต่อ
- รหัสสัตว์เลี้ยง
- รหัสรายการตรวจรักษา
- สถานพยาบาลปลายทาง
- เหตุผลในการส่งต่อ
- รายละเอียดปัญหาสุขภาพ
- ข้อมูลการวินิจฉัย
- ผลตรวจที่เกี่ยวข้อง
- การรักษาที่ดำเนินการไปแล้ว
- ระดับความเร่งด่วน
- วันที่ส่งต่อ
- ผู้ส่งต่อ
- ผู้รับผิดชอบปลายทาง
- ผลการส่งต่อ หากได้รับข้อมูลกลับมา

ความสามารถของระบบ

- สร้างรายการส่งต่อ
- บันทึกเหตุผล
- จัดทำเอกสารส่งต่อ
- แนบเวชระเบียนที่เกี่ยวข้อง
- แนบผลตรวจ
- บันทึกข้อมูลสถานพยาบาลปลายทาง
- ติดตามสถานะการส่งต่อ
- บันทึกผลตอบกลับ
- เชื่อมโยงกับประวัติการรักษาเดิม

กฎทางธุรกิจ

- การส่งต่อต้องมีผู้รับผิดชอบ
- ต้องมีเหตุผลในการส่งต่อ
- ต้องมีข้อมูลทางการแพทย์ที่จำเป็น
- การส่งข้อมูลให้บุคคลหรือสถานพยาบาลภายนอกต้องคำนึงถึงสิทธิและฐานการประมวลผลข้อมูลที่เกี่ยวข้อง
- ต้องเก็บประวัติการส่งต่อ
- ต้องแยกการส่งต่อออกจากการปิดรายการตรวจรักษา

## 3.16 การติดตามผลการรักษา (Clinical Follow-up Management)

เป็นกระบวนการติดตามอาการและประเมินผลหลังจากสัตว์เลี้ยงได้รับการรักษา เพื่อให้ทราบว่าการรักษาได้ผลตามเป้าหมายหรือไม่ และจำเป็นต้องปรับแผนการรักษาหรือไม่

ประเภทการติดตาม

1. ติดตามอาการหลังได้รับยา
2. ติดตามผลหลังทำหัตถการ
3. ติดตามผลตรวจทางห้องปฏิบัติการ
4. ติดตามหลังได้รับวัคซีน
5. ติดตามหลังการผ่าตัด
6. ติดตามโรคเรื้อรัง
7. ติดตามหลังออกจากคลินิก
8. ติดตามตามกำหนดนัดหมาย

ข้อมูลที่ควรจัดเก็บ

- รหัสรายการติดตาม
- รหัสสัตว์เลี้ยง
- รหัสรายการตรวจรักษาเดิม
- รหัสแผนการรักษา
- วันที่กำหนดติดตาม
- ประเภทการติดตาม
- อาการที่ต้องติดตาม
- วิธีการติดตาม
- ผู้รับผิดชอบ
- ผลการติดตาม
- วันที่ติดตามจริง
- แนวทางดำเนินการต่อ

ความสามารถของระบบ

- สร้างรายการติดตามผล
- กำหนดวันที่ติดตาม
- กำหนดผู้รับผิดชอบ
- บันทึกผลการติดตาม
- บันทึกข้อมูลจากเจ้าของ
- เชื่อมโยงกับนัดหมายครั้งถัดไป
- แจ้งเตือนรายการติดตามที่ถึงกำหนด
- แสดงรายการติดตามที่ยังไม่เสร็จ
- สร้างรายการตรวจรักษาใหม่เมื่อจำเป็น

กฎทางธุรกิจ

- รายการติดตามต้องอ้างอิงเหตุการณ์การรักษาที่เกี่ยวข้อง
- ต้องระบุวันครบกำหนด
- ต้องบันทึกผลการติดตามจริง
- ต้องรองรับกรณีที่ติดต่อเจ้าของไม่ได้
- ต้องแยกการติดตามทางคลินิกออกจากการแจ้งเตือนทั่วไป
- หากต้องตรวจซ้ำ ต้องสร้างรายการตรวจรักษาใหม่ ไม่ควรนำข้อมูลเดิมมาเขียนทับ

## 3.17 การสรุปผลและจำหน่ายสัตว์กลับ (Clinical Discharge Management)

เป็นกระบวนการสรุปผลการตรวจรักษาและบันทึกข้อมูลก่อนส่งสัตว์เลี้ยงกลับบ้าน หรือส่งต่อไปยังกระบวนการดูแลอื่น

สำหรับคลินิกสัตวแพทย์ทั่วไป กระบวนการนี้มักเกิดขึ้นหลังตรวจรักษาและให้คำแนะนำแก่เจ้าของ

ข้อมูลที่ควรจัดเก็บ

- รหัสสรุปผลการรักษา
- รหัสรายการตรวจรักษา
- สรุปอาการ
- ผลการตรวจ
- ผลการวินิจฉัย
- รายการรักษาที่ดำเนินการ
- รายการยาที่สั่ง
- คำแนะนำการดูแลที่บ้าน
- ข้อควรระวัง
- อาการที่ต้องกลับมาพบสัตวแพทย์
- วันนัดติดตามผล
- วันที่จำหน่าย
- ผู้อนุมัติการจำหน่าย

ความสามารถของระบบ

- สร้างสรุปผลการรักษา
- แสดงรายการรักษาที่ดำเนินการ
- แสดงรายการยาที่สั่ง
- บันทึกคำแนะนำสำหรับเจ้าของ
- บันทึกข้อควรระวัง
- กำหนดวันติดตามผล
- พิมพ์เอกสารสรุปการรักษา
- เชื่อมโยงกับระบบนัดหมาย
- บันทึกสถานะการจำหน่าย

กฎทางธุรกิจ

- ต้องมีข้อมูลสรุปการรักษาตามความเหมาะสม
- ต้องระบุผู้รับผิดชอบ
- ต้องแสดงคำแนะนำที่เจ้าของได้รับ
- ต้องไม่ถือว่าการจำหน่ายสัตว์กลับหมายถึงการชำระเงินเสร็จสิ้น
- ต้องไม่ถือว่าการจำหน่ายสัตว์กลับหมายถึงรายการตรวจรักษาทั้งหมดได้รับการปิดทางธุรการแล้ว
- ต้องรองรับกรณีส่งต่อหรือรับไว้รักษาต่อ

ข้อสำคัญคือ การจำหน่ายสัตว์กลับต้องแยกจากการปิดใบแจ้งหนี้และการรับชำระเงิน เพราะเป็นคนละกระบวนการทางธุรกิจ

## 3.18 การจัดทำเอกสารทางการแพทย์ (Medical Document Management)

เป็นการจัดทำและจัดเก็บเอกสารที่เกิดจากกระบวนการตรวจรักษา เพื่อให้เจ้าของสัตว์และบุคลากรที่เกี่ยวข้องสามารถใช้เป็นหลักฐานหรือประกอบการดำเนินงานได้

ประเภทเอกสาร

1. ใบสรุปผลการรักษา
2. ใบรับรองสุขภาพสัตว์
3. ใบรับรองการได้รับวัคซีน
4. ใบส่งต่อผู้ป่วย
5. ใบแนะนำการดูแลหลังรักษา
6. เอกสารประวัติการรักษา
7. เอกสารประกอบการเคลมประกัน
8. เอกสารรับรองผลการตรวจ
9. เอกสารประกอบการเดินทางของสัตว์
10. เอกสารอื่นตามนโยบายของคลินิก

ข้อมูลที่ควรจัดเก็บ

- รหัสเอกสาร
- ประเภทเอกสาร
- รหัสสัตว์เลี้ยง
- รหัสรายการตรวจรักษา
- หมายเลขเอกสาร
- วันที่ออกเอกสาร
- รายละเอียดเอกสาร
- ผู้จัดทำ
- ผู้รับรอง
- เวอร์ชันเอกสาร
- ไฟล์เอกสาร
- สถานะเอกสาร

ความสามารถของระบบ

- สร้างเอกสารจากข้อมูลเวชระเบียน
- ใช้แม่แบบเอกสาร
- สร้างหมายเลขเอกสาร
- แนบไฟล์
- พิมพ์เอกสาร
- ส่งเอกสารให้เจ้าของตามสิทธิ์
- ตรวจสอบประวัติการออกเอกสาร
- ยกเลิกเอกสารที่ออกผิดพลาดตามกระบวนการ
- ออกเอกสารฉบับใหม่โดยรักษาประวัติฉบับเดิม

กฎทางธุรกิจ

- เอกสารต้องเชื่อมโยงกับข้อมูลต้นทาง
- ต้องระบุผู้จัดทำและผู้รับรองตามประเภทเอกสาร
- เอกสารที่ออกแล้วต้องตรวจสอบย้อนหลังได้
- ต้องป้องกันการแก้ไขเอกสารที่ออกแล้วโดยไม่มีประวัติ
- การออกเอกสารใหม่แทนฉบับเดิมต้องมีเหตุผล
- ต้องกำหนดสิทธิ์ในการดูและดาวน์โหลดเอกสาร

## 3.19 การรับรองและปิดเวชระเบียน (Clinical Sign-off & Record Closure)

เป็นกระบวนการตรวจสอบความครบถ้วนของบันทึกทางการแพทย์ และให้สัตวแพทย์รับรองข้อมูลก่อนปิดรายการตรวจรักษาตามขั้นตอนที่กำหนด

การมีสถานะปิดรายการตรวจรักษาไม่ได้หมายความว่าข้อมูลนั้นจะต้องไม่สามารถตรวจสอบหรือเพิ่มเติมได้อีก แต่การเพิ่มเติมภายหลังต้องดำเนินการอย่างมีหลักฐาน

สถานะที่ควรรองรับ

- ฉบับร่าง
- รอสัตวแพทย์ตรวจสอบ
- รับรองแล้ว
- ปิดรายการตรวจรักษา
- เพิ่มบันทึกภายหลัง
- ยกเลิกตามเงื่อนไข

ข้อมูลที่ควรจัดเก็บ

- รหัสรายการตรวจรักษา
- ผู้จัดทำ
- ผู้ตรวจสอบ
- ผู้รับรอง
- วันที่และเวลารับรอง
- สถานะการรับรอง
- รายการข้อมูลที่ยังไม่ครบ
- เหตุผลในการปิด
- ประวัติการแก้ไขภายหลัง

ความสามารถของระบบ

- ตรวจสอบความครบถ้วนของเวชระเบียน
- แสดงรายการข้อมูลที่ยังไม่สมบูรณ์
- ส่งบันทึกให้สัตวแพทย์รับรอง
- บันทึกผู้รับรอง
- ปิดรายการตรวจรักษา
- รองรับการเพิ่มบันทึกภายหลัง
- แสดงประวัติการรับรองและแก้ไข

กฎทางธุรกิจ

- ต้องกำหนดข้อมูลขั้นต่ำที่จำเป็นต่อการปิดรายการ
- ต้องระบุผู้รับรองตามอำนาจหน้าที่
- ต้องเก็บวันที่และเวลาที่รับรอง
- ห้ามเขียนทับบันทึกที่รับรองแล้วโดยไม่มีประวัติ
- ต้องรองรับการเพิ่มข้อมูลภายหลัง
- ต้องแยกสถานะเวชระเบียนออกจากสถานะการชำระเงิน

## 3.20 การตรวจสอบคุณภาพเวชระเบียน (Medical Record Quality & Governance)

เป็นกระบวนการควบคุมคุณภาพข้อมูลทางการแพทย์ เพื่อให้มั่นใจว่าเวชระเบียนมีความครบถ้วน ถูกต้อง และสามารถตรวจสอบย้อนหลังได้

ขอบเขตการดำเนินงาน

1. ตรวจสอบข้อมูลเวชระเบียนที่ไม่ครบถ้วน
2. ตรวจสอบรายการตรวจรักษาที่ไม่มีผู้รับผิดชอบ
3. ตรวจสอบรายการวินิจฉัยที่ไม่มีรายละเอียดประกอบ
4. ตรวจสอบคำสั่งยาที่ไม่มีข้อมูลสำคัญ
5. ตรวจสอบรายการตรวจที่ยังไม่มีผล
6. ตรวจสอบรายการติดตามที่ค้างอยู่
7. ตรวจสอบการรับรองเวชระเบียน
8. ตรวจสอบประวัติการแก้ไข
9. ตรวจสอบสิทธิ์การเข้าถึง
10. ตรวจสอบความถูกต้องของการเชื่อมโยงข้อมูล
11. ตรวจสอบข้อมูลซ้ำ
12. ควบคุมการเก็บรักษาเวชระเบียน

ความสามารถของระบบ

- ตรวจสอบความครบถ้วนของเวชระเบียน
- สร้างรายงานเวชระเบียนที่ยังไม่รับรอง
- แจ้งเตือนรายการที่ยังไม่สมบูรณ์
- ตรวจสอบผู้บันทึกและผู้แก้ไข
- ตรวจสอบประวัติการเข้าถึง
- ตรวจสอบความสัมพันธ์ระหว่างคำสั่งและผลการดำเนินงาน
- กำหนดสิทธิ์ตามบทบาท
- รองรับการตรวจสอบภายใน

กฎทางธุรกิจ

- ต้องมีประวัติการแก้ไขข้อมูลสำคัญ
- ต้องกำหนดสิทธิ์ตามหน้าที่
- ต้องแยกผู้บันทึก ผู้ตรวจสอบ และผู้รับรองตามความเหมาะสม
- ต้องไม่ลบเวชระเบียนที่มีประวัติการรักษาโดยพลการ
- ต้องกำหนดนโยบายการเก็บรักษาข้อมูล
- ต้องตรวจสอบการเข้าถึงข้อมูลที่มีความสำคัญ
- ต้องรองรับการตรวจสอบย้อนหลัง

## 3.21 การวิเคราะห์และรายงานทางคลินิก (Clinical Analytics & Reporting)

เป็นการนำข้อมูลการตรวจรักษามาวิเคราะห์ เพื่อให้ผู้บริหารและสัตวแพทย์สามารถประเมินรูปแบบการเจ็บป่วย ประสิทธิภาพการรักษา และคุณภาพการให้บริการได้

รายงานที่ควรมี

1. รายงานจำนวนรายการตรวจรักษา
2. รายงานจำนวนสัตว์เลี้ยงที่เข้ารับบริการ
3. รายงานจำนวนผู้ป่วยใหม่และผู้ป่วยเดิม
4. รายงานจำนวนการวินิจฉัยแยกตามโรค
5. รายงานจำนวนผู้ป่วยแยกตามประเภทสัตว์
6. รายงานจำนวนผู้ป่วยแยกตามสายพันธุ์
7. รายงานการวินิจฉัยแยกตามช่วงอายุ
8. รายงานการใช้ยา
9. รายงานการให้วัคซีน
10. รายงานการสั่งตรวจทางห้องปฏิบัติการ
11. รายงานผลตรวจที่ผิดปกติ
12. รายงานการส่งต่อผู้ป่วย
13. รายงานการติดตามผลการรักษา
14. รายงานเวชระเบียนที่ยังไม่รับรอง
15. รายงานการปิดรายการตรวจรักษา
16. รายงานเหตุการณ์ไม่พึงประสงค์ทางคลินิก

ตัวชี้วัดที่ควรใช้

| ตัวชี้วัด                       | วิธีวัด                                                |
| ------------------------------- | ------------------------------------------------------ |
| จำนวนรายการตรวจรักษา            | จำนวนรายการตรวจในช่วงเวลาที่กำหนด                      |
| จำนวนผู้ป่วยใหม่                | จำนวนสัตว์ที่มีการตรวจครั้งแรก                         |
| จำนวนผู้ป่วยกลับมาตรวจ          | จำนวนสัตว์ที่มีการตรวจซ้ำ                              |
| จำนวนการวินิจฉัย                | จำนวนรายการวินิจฉัยตามช่วงเวลา                         |
| อัตราการบันทึกเวชระเบียนครบถ้วน | เวชระเบียนที่ครบถ้วน ÷ เวชระเบียนทั้งหมด               |
| อัตราการรับรองเวชระเบียน        | เวชระเบียนที่รับรองแล้ว ÷ เวชระเบียนที่ต้องรับรอง      |
| ระยะเวลาปิดเวชระเบียน           | เวลาปิดรายการ − เวลาเริ่มตรวจ                          |
| อัตราการติดตามผลสำเร็จ          | รายการติดตามที่ดำเนินการแล้ว ÷ รายการติดตามที่ถึงกำหนด |
| อัตราการตรวจเพิ่มเติม           | รายการตรวจเพิ่มเติม ÷ รายการตรวจรักษาทั้งหมด           |
| อัตราการส่งต่อ                  | รายการส่งต่อ ÷ รายการตรวจรักษาทั้งหมด                  |

ข้อสังเกต: ลำดับนี้เป็นตัวอย่างของกระบวนการทั่วไป ไม่ได้หมายความว่าทุกกรณีต้องดำเนินการครบทุกขั้นตอน เช่น การฉีดวัคซีนอาจไม่ต้องมีคำสั่งตรวจทางห้องปฏิบัติการ

## 4.2 กระบวนการตรวจรักษาฉุกเฉิน

3. บุคลากรดำเนินการคัดกรองเบื้องต้น
4. หากมีความจำเป็น ให้ส่งต่อสัตวแพทย์ทันที
5. สัตวแพทย์เปิดรายการตรวจรักษาฉุกเฉิน
6. บันทึกข้อมูลอาการและสัญญาณชีพ
7. ประเมินสถานการณ์และกำหนดแนวทางดูแล
8. บันทึกคำสั่งทางการแพทย์ที่จำเป็น
9. ดำเนินการรักษาเร่งด่วน
10. บันทึกการรักษาและการตอบสนองของสัตว์
11. พิจารณาการตรวจเพิ่มเติม
12. พิจารณาการรับไว้ดูแลต่อหรือส่งต่อสถานพยาบาลอื่น

ข้อควรระวัง: ระบบ Clinical ต้องรองรับการบันทึกข้อมูลย้อนหลังในกรณีฉุกเฉินที่บุคลากรจำเป็นต้องให้ความช่วยเหลือก่อน โดยยังคงต้องเก็บวันเวลาและผู้ดำเนินการจริง ไม่ควรบังคับให้กรอกข้อมูลทุกช่องก่อนเริ่มช่วยเหลือสัตว์ป่วย

## 4.3 กระบวนการตรวจติดตามผล

1. สัตวแพทย์สร้างรายการติดตามผลจากการรักษาครั้งก่อน
2. กำหนดวันที่หรือช่วงเวลาที่ต้องติดตาม
3. ระบบสร้างรายการแจ้งเตือนหรือเชื่อมโยงกับการนัดหมาย
4. เจ้าของนำสัตว์กลับมาตรวจ หรือให้ข้อมูลผ่านช่องทางที่คลินิกกำหนด
5. สร้างรายการตรวจรักษาครั้งใหม่เมื่อมีการตรวจจริง
6. ตรวจสอบประวัติการรักษาครั้งก่อน
7. บันทึกอาการปัจจุบัน
8. ตรวจร่างกายและประเมินผล
9. เปรียบเทียบกับผลการรักษาครั้งก่อน
10. ปรับปรุงแผนการรักษา
11. กำหนดการติดตามครั้งต่อไป หรือปิดรายการติดตาม

## 4.4 กระบวนการสั่งยาและจ่ายยา

1. สัตวแพทย์ประเมินและกำหนดรายการยา
2. ตรวจสอบประวัติแพ้ยาและข้อควรระวัง
3. สร้างใบสั่งยา
4. ยืนยันคำสั่งยา
5. ส่งข้อมูลไปยัง Pharmacy
6. เภสัชกรหรือผู้รับผิดชอบตรวจสอบรายการ
7. ตรวจสอบความพร้อมของยา
8. ดำเนินการจ่ายยาหรือเตรียมยา
9. บันทึกปริมาณและรายการยาที่จ่ายจริง
10. ส่งข้อมูลสถานะกลับมายัง Clinical
11. บันทึกคำแนะนำการใช้ยาให้เจ้าของ

หากไม่สามารถจ่ายยาได้ครบตามคำสั่ง ระบบควรแจ้งสถานะให้สัตวแพทย์หรือผู้รับผิดชอบทราบ เพื่อพิจารณาดำเนินการต่อ ไม่ควรถือว่าคำสั่งยาทั้งหมดเสร็จสิ้นโดยอัตโนมัติ

## 4.5 กระบวนการสั่งตรวจและรับผลตรวจ

1. สัตวแพทย์ประเมินความจำเป็นในการตรวจเพิ่มเติม
2. สร้างคำสั่งตรวจ
3. ส่งคำสั่งไปยัง Laboratory หรือ Diagnostic Imaging
4. หน่วยงานปลายทางรับคำสั่ง
5. เก็บตัวอย่างหรือดำเนินการตรวจ
6. บันทึกผลตรวจ
7. ส่งผลตรวจกลับมายัง Clinical
8. ระบบแจ้งสัตวแพทย์เมื่อผลพร้อม
9. สัตวแพทย์ตรวจสอบและรับทราบผล
10. นำผลไปประกอบการวินิจฉัย
11. ปรับปรุงแผนการรักษาตามความเหมาะสม

ต้องแยกสถานะของคำสั่งตรวจออกจากสถานะของผลตรวจ เช่น สั่งตรวจแล้ว แต่ยังไม่ได้รับตัวอย่าง หรือรับตัวอย่างแล้วแต่ยังอยู่ระหว่างวิเคราะห์

## 4.6 กระบวนการจำหน่ายสัตว์กลับบ้าน

1. สัตวแพทย์ประเมินว่าสามารถส่งสัตว์กลับได้หรือไม่
2. ตรวจสอบว่ากิจกรรมการรักษาที่จำเป็นเสร็จสิ้นแล้ว
3. สรุปผลการตรวจรักษา
4. บันทึกรายการยาที่สั่งและรายการยาที่จ่าย
5. บันทึกคำแนะนำการดูแลที่บ้าน
6. ระบุอาการที่เจ้าของควรเฝ้าระวัง
7. กำหนดวันติดตามผล
8. จัดทำเอกสารสรุปการรักษา
9. บันทึกผู้อนุมัติการจำหน่าย
10. ส่งข้อมูลบริการไปยัง Billing & Payment ตามกระบวนการ
11. เปลี่ยนสถานะรายการตรวจรักษา

# 5. โครงสร้างข้อมูลที่ควรมีในฐานข้อมูล

## 6.1 ความสัมพันธ์ระหว่าง Pet กับ Clinical Encounter

ความสัมพันธ์นี้เป็นพื้นฐานของระบบเวชระเบียน

- สัตว์เลี้ยงหนึ่งตัวสามารถเข้ารับการตรวจรักษาได้หลายครั้ง
- การตรวจรักษาแต่ละครั้งต้องอ้างอิงสัตว์เลี้ยงหนึ่งตัว
- การตรวจรักษาแต่ละครั้งอาจมีสัตวแพทย์หลายคนเข้าร่วม
- การตรวจรักษาหนึ่งครั้งอาจมีการวินิจฉัยหลายรายการ
- การตรวจรักษาหนึ่งครั้งอาจมีคำสั่งทางการแพทย์หลายรายการ

ดังนั้น ตาราง `clinical_encounters` ควรมี `pet_id` เป็น Foreign Key เพื่อเชื่อมโยงกับข้อมูลสัตว์เลี้ยงจาก Domain Customer & Pet Management

## 6.2 ความสัมพันธ์ระหว่าง Appointment, Service Registration และ Clinical Encounter

จุดนี้ต้องออกแบบให้สอดคล้องกับ Domain Appointment & Queue Management

ความหมายของข้อมูลแต่ละประเภทคือ

| รายการ               | ความหมาย                         |
| -------------------- | -------------------------------- |
| Appointment          | การจองวันและเวลาในอนาคต          |
| Service Registration | การลงทะเบียนเข้ารับบริการจริง    |
| Queue                | การจัดลำดับรอรับบริการ           |
| Clinical Encounter   | เหตุการณ์การตรวจรักษาทางการแพทย์ |

ตัวอย่าง:

คุณสมชายจองนัดให้เจ้าดำมาตรวจวันที่ 15 พฤศจิกายน เวลา 10:00 น.

เมื่อมาถึงคลินิก ระบบสร้างรายการ Check-in และ Queue

เมื่อเจ้าดำเริ่มเข้าสู่กระบวนการตรวจรักษา ระบบจึงสร้าง Clinical Encounter

ดังนั้น ไม่ควรใช้ `appointment_id` เป็นรหัสหลักของเวชระเบียน เพราะการตรวจรักษาอาจเกิดจาก Walk-in หรืออาจเกิดขึ้นหลายครั้งภายใต้การเข้ารับบริการที่มีความซับซ้อน

แนวทางที่เหมาะสมคือให้ Clinical Encounter มีรหัสของตนเอง และเก็บรหัสการเข้ารับบริการหรือนัดหมายเป็นข้อมูลอ้างอิงตามกรณี

## 6.3 ความสัมพันธ์ระหว่าง Diagnosis กับ Treatment Plan

การวินิจฉัยและแผนการรักษาเป็นข้อมูลที่เกี่ยวข้องกัน แต่ไม่ควรรวมเป็นข้อมูลเดียวกัน

- Diagnosis คือข้อสรุปหรือการประเมินทางการแพทย์
- Treatment Plan คือแนวทางที่กำหนดเพื่อจัดการกับปัญหาสุขภาพ
- Treatment Plan Item คือกิจกรรมย่อยในแผน
- Treatment Record คือข้อมูลการดำเนินการจริง

ตัวอย่างเช่น สัตวแพทย์วินิจฉัยว่าเจ้าดำมีปัญหาสุขภาพที่ต้องติดตาม และกำหนดแผนให้ยา ตรวจเพิ่มเติม และนัดตรวจซ้ำ

แต่ละรายการต้องสามารถติดตามสถานะและผลการดำเนินการได้แยกกัน

## 6.4 ความสัมพันธ์ระหว่าง Clinical กับ Pharmacy

ควรกำหนดขอบเขตให้ชัดเจนดังนี้

| Clinical & Medical      | Pharmacy                |
| ----------------------- | ----------------------- |
| สัตวแพทย์ตัดสินใจใช้ยา  | บริหารข้อมูลยา          |
| สร้างใบสั่งยา           | ตรวจสอบรายการยา         |
| ระบุขนาดและวิธีใช้      | ตรวจสอบความพร้อมของยา   |
| ส่งคำสั่งยา             | จ่ายยา                  |
| ติดตามสถานะคำสั่ง       | บันทึกการจ่ายจริง       |
| บันทึกการรักษาทางคลินิก | จัดการล็อตและวันหมดอายุ |

Clinical ต้องได้รับข้อมูลผลการจ่ายยาจาก Pharmacy เพื่อให้ทราบว่ารายการยาที่สั่งสามารถดำเนินการได้ครบถ้วนหรือไม่

## 6.5 ความสัมพันธ์ระหว่าง Clinical กับ Laboratory & Diagnostic Imaging

ควรแบ่งความรับผิดชอบดังนี้

- Clinical สร้างคำสั่งตรวจ
- Laboratory รับคำสั่งและดำเนินการตรวจทางห้องปฏิบัติการ
- Diagnostic Imaging รับคำสั่งและดำเนินการตรวจวินิจฉัยด้วยภาพ
- Laboratory หรือ Imaging บันทึกผลตรวจที่เป็นแหล่งข้อมูลหลัก
- Clinical นำผลตรวจมาใช้ประกอบการประเมินและวินิจฉัย

ต้องรองรับกรณีที่มีผลตรวจหลายรายการในหนึ่งคำสั่ง และกรณีที่ผลตรวจบางส่วนออกก่อนผลตรวจส่วนที่เหลือ

## 6.6 ความสัมพันธ์ระหว่าง Clinical กับ Surgery & Treatment

Clinical เป็นผู้กำหนดความจำเป็นทางการแพทย์และส่งคำสั่งหรือแผนการรักษา ส่วน Surgery & Treatment รับผิดชอบกระบวนการดำเนินการผ่าตัดและหัตถการตามขอบเขตของ Domain นั้น

ตัวอย่างเช่น

- Clinical ประเมินว่าต้องผ่าตัด
- Clinical บันทึกข้อบ่งชี้และแผนการรักษา
- ส่งข้อมูลไปยัง Surgery & Treatment
- Surgery รับผิดชอบการเตรียมผ่าตัดและบันทึกการผ่าตัดจริง
- Clinical รับผลการดำเนินงานกลับมาเชื่อมโยงกับเวชระเบียน

# 7. ผู้ใช้งานที่เกี่ยวข้องกับโดเมนนี้

การออกแบบระบบต้องกำหนดสิทธิ์ของผู้ใช้งานตามหน้าที่และความรับผิดชอบทางการแพทย์

| ผู้ใช้งาน                       | หน้าที่และสิทธิ์                               |
| ------------------------------- | ---------------------------------------------- |
| สัตวแพทย์                       | ตรวจรักษา วินิจฉัย วางแผน และรับรองเวชระเบียน  |
| สัตวแพทย์ผู้เชี่ยวชาญ           | ให้คำปรึกษาและตรวจรักษาตามความเชี่ยวชาญ        |
| ผู้ช่วยสัตวแพทย์                | บันทึกข้อมูลตรวจวัดและช่วยดำเนินงานตามหน้าที่  |
| พยาบาลสัตว์หรือบุคลากรดูแลสัตว์ | บันทึกข้อมูลการดูแลและติดตามตามขอบเขตหน้าที่   |
| พนักงานต้อนรับ                  | ตรวจสอบสถานะการเข้ารับบริการและข้อมูลที่จำเป็น |
| เจ้าหน้าที่ห้องปฏิบัติการ       | รับคำสั่งและส่งผลตรวจจาก Laboratory            |
| เจ้าหน้าที่เภสัชกรรม            | รับคำสั่งยาและบันทึกการจ่ายยา                  |
| ผู้จัดการคลินิก                 | ตรวจสอบรายงานและคุณภาพการดำเนินงาน             |
| ผู้ดูแลระบบ                     | ตั้งค่าระบบและสิทธิ์การใช้งานตามนโยบาย         |

ตัวอย่างการกำหนดสิทธิ์

- สัตวแพทย์สามารถสร้างและรับรองการวินิจฉัยได้ตามสิทธิ์
- ผู้ช่วยสัตวแพทย์สามารถบันทึกข้อมูลตรวจวัดได้ตามขอบเขตหน้าที่
- เจ้าหน้าที่ต้อนรับไม่ควรมีสิทธิ์แก้ไขผลวินิจฉัย
- เจ้าหน้าที่เภสัชกรรมสามารถดูข้อมูลใบสั่งยาที่จำเป็นต่อการจ่ายยา แต่ไม่ควรแก้ไขการวินิจฉัย
- ผู้จัดการคลินิกสามารถดูรายงานภาพรวมได้ แต่การเข้าถึงรายละเอียดเวชระเบียนต้องเป็นไปตามสิทธิ์
- การรับรองหรือแก้ไขเวชระเบียนต้องจำกัดเฉพาะผู้มีอำนาจตามนโยบาย

ควรใช้หลักการกำหนดสิทธิ์ตามบทบาท (Role-Based Access Control) ร่วมกับการกำหนดขอบเขตสาขาและความจำเป็นในการเข้าถึงข้อมูล

# 9. ข้อกำหนดที่สำคัญในการพัฒนาระบบ

ผมขอเน้นข้อกำหนดทางธุรกิจและเทคนิค 18 ประการที่ควรให้ความสำคัญเป็นพิเศษ

1. มีรหัสรายการตรวจรักษาเฉพาะ: การตรวจรักษาแต่ละครั้งต้องมีรหัสอ้างอิงของตนเอง
2. เชื่อมโยงกับสัตว์เลี้ยง: ต้องอ้างอิงสัตว์เลี้ยงจาก Customer & Pet Management
3. เก็บเวชระเบียนต่อเนื่อง: ต้องแสดงประวัติการรักษาทั้งหมดของสัตว์แต่ละตัว
4. แยกข้อมูลแต่ละเหตุการณ์: ต้องแยกประวัติการเจ็บป่วย ผลตรวจ การวินิจฉัย และการรักษา
5. แยกข้อมูลจากเจ้าของกับข้อมูลทางการแพทย์: ต้องระบุแหล่งที่มาของข้อมูล
6. รองรับการวินิจฉัยหลายรายการ: การตรวจรักษาหนึ่งครั้งอาจมีหลายการวินิจฉัย
7. รองรับการวินิจฉัยที่ยังไม่ยืนยัน: ไม่บังคับให้ทุกกรณีต้องมีโรคที่ยืนยันแล้ว
8. เก็บประวัติการตรวจวัด: เช่น น้ำหนัก อุณหภูมิ และสัญญาณชีพ
9. รองรับแผนการรักษา: ต้องแยกแผนออกจากผลการดำเนินการจริง
10. แยกคำสั่งยาออกจากการจ่ายยา: Clinical สั่งยา ส่วน Pharmacy จ่ายยา
11. แยกคำสั่งตรวจออกจากผลตรวจ: Clinical สั่งตรวจ ส่วน Laboratory หรือ Imaging บันทึกผล
12. รองรับการให้วัคซีนจริง: ต้องบันทึกวันที่ ผู้ให้ และข้อมูลวัคซีนที่ใช้
13. แสดงประวัติแพ้ยาอย่างชัดเจน: ต้องช่วยป้องกันความเสี่ยงระหว่างการรักษา
14. รองรับการรักษาฉุกเฉิน: ต้องไม่บังคับใช้ขั้นตอนปกติจนทำให้การช่วยเหลือล่าช้า
15. ตรวจสอบย้อนหลังได้: การแก้ไขและรับรองเวชระเบียนต้องมีประวัติ
16. กำหนดสิทธิ์ทางการแพทย์: ต้องจำกัดการสร้าง แก้ไข และรับรองข้อมูลตามหน้าที่
17. รองรับหลายสาขา: ต้องเชื่อมโยงเวชระเบียนของสัตว์ตัวเดียวกันข้ามสาขาตามสิทธิ์
18. เชื่อมต่อ Domain อื่นได้: ต้องเชื่อมโยง Appointment, Pharmacy, Laboratory, Surgery, Billing และ Domain ที่เกี่ยวข้อง

## 10.1 ตัวอย่างการกำหนด Data Ownership

เพื่อให้เข้าใจขอบเขตการทำงานของแต่ละ Domain ชัดเจนขึ้น ผมขอยกตัวอย่างข้อมูลสำคัญ 5 ประเภท

กรณีที่ 1: ข้อมูลสัตว์เลี้ยง

- Customer & Pet เป็นเจ้าของข้อมูลประจำตัวสัตว์เลี้ยง
- Clinical ใช้ข้อมูลสัตว์เลี้ยงเพื่อสร้างเวชระเบียน
- Appointment ใช้ข้อมูลสัตว์เลี้ยงเพื่อสร้างนัดหมาย
- Pharmacy ใช้ข้อมูลสัตว์เลี้ยงเพื่อประกอบการจ่ายยา

Clinical ไม่ควรสร้างข้อมูลประจำตัวสัตว์เลี้ยงซ้ำอีกชุดหนึ่ง

กรณีที่ 2: ข้อมูลการวินิจฉัยโรค

- Clinical เป็นเจ้าของข้อมูลการวินิจฉัย
- Clinical บันทึกผลการประเมินและสถานะการวินิจฉัย
- ระบบรายงานนำข้อมูลไปวิเคราะห์
- Domain อื่นสามารถเรียกดูข้อมูลตามสิทธิ์ได้

กรณีที่ 3: ข้อมูลยา

- Pharmacy เป็นเจ้าของข้อมูลรายการยาและคลังยา
- Clinical เป็นเจ้าของข้อมูลคำสั่งใช้ยา
- Pharmacy เป็นเจ้าของข้อมูลการจ่ายยาจริง
- Clinical สามารถเรียกดูประวัติการจ่ายยาเพื่อประกอบการรักษาได้

กรณีที่ 4: ผลตรวจทางห้องปฏิบัติการ

- Clinical เป็นเจ้าของคำสั่งตรวจ
- Laboratory เป็นเจ้าของผลตรวจ
- Clinical เป็นผู้รับทราบและนำผลตรวจไปประกอบการวินิจฉัย

กรณีที่ 5: การรักษาโดยการผ่าตัด

- Clinical เป็นผู้ประเมินและกำหนดความจำเป็นในการผ่าตัด
- Surgery & Treatment เป็นเจ้าของกระบวนการผ่าตัด
- Surgery บันทึกผลการผ่าตัดจริง
- Clinical นำผลการผ่าตัดมาเชื่อมโยงกับเวชระเบียน

หลักการสำคัญคือ แต่ละข้อมูลควรมีแหล่งข้อมูลหลักเพียงแหล่งเดียว (Single Source of Truth) ส่วน Domain อื่นสามารถนำข้อมูลมาใช้งานหรือแสดงผลได้โดยอ้างอิงจากแหล่งข้อมูลนั้น

## ข้อสรุปของ Domain นี้

Domain Clinical & Medical Management ควรทำหน้าที่เป็น ศูนย์กลางการดำเนินงานทางการแพทย์และเวชระเบียนของสัตว์เลี้ยง โดยมีหน้าที่ตั้งแต่การเปิดรายการตรวจรักษา การบันทึกอาการ การตรวจร่างกาย การวินิจฉัย การวางแผนการรักษา การสร้างคำสั่งทางการแพทย์ ไปจนถึงการสรุปผลและติดตามการรักษา

สิ่งสำคัญที่สุดคือ ต้องแยกความหมายของข้อมูลและเหตุการณ์แต่ละประเภทให้ชัดเจน

| สิ่งที่ต้องแยก                              | ความหมาย                                      |
| ------------------------------------------- | --------------------------------------------- |
| Pet Profile ≠ Medical Record                | ข้อมูลประจำตัวสัตว์ไม่ใช่เวชระเบียน           |
| Appointment ≠ Clinical Encounter            | การจองนัดไม่ใช่การตรวจรักษา                   |
| Symptom ≠ Diagnosis                         | อาการไม่ใช่ข้อวินิจฉัย                        |
| Diagnosis ≠ Treatment Plan                  | การวินิจฉัยไม่ใช่แผนการรักษา                  |
| Treatment Plan ≠ Treatment Execution        | แผนการรักษาไม่ใช่การรักษาที่เกิดขึ้นจริง      |
| Medication Order ≠ Medication Dispensing    | การสั่งยาไม่ใช่การจ่ายยา                      |
| Diagnostic Order ≠ Diagnostic Result        | คำสั่งตรวจไม่ใช่ผลตรวจ                        |
| Clinical Discharge ≠ Payment Completion     | การจำหน่ายสัตว์กลับไม่ใช่การชำระเงินเสร็จสิ้น |
| Encounter Closure ≠ Medical Record Deletion | การปิดรายการตรวจรักษาไม่ใช่การลบเวชระเบียน    |

หากออกแบบความแตกต่างเหล่านี้ได้ถูกต้อง จะช่วยลดปัญหาข้อมูลซ้ำซ้อน ลดความสับสนระหว่างหน่วยงาน และทำให้สามารถขยายระบบไปสู่โรงพยาบาลสัตว์หรือธุรกิจหลายสาขาได้ง่ายขึ้น

# 12. ลำดับการออกแบบขั้นต่อไป

หากจะนำ Domain นี้ไปพัฒนาระบบ ERP สำหรับคลินิกสัตวแพทย์ ผมแนะนำให้ลงรายละเอียดต่ออีก 4 ระดับ โดยใช้แนวทางเดียวกับ Domain 01 และ Domain 02

ขั้นที่ 1: Business Capability Breakdown

แตกความสามารถทั้ง 21 กลุ่มออกเป็นความสามารถย่อย พร้อมกำหนดขอบเขต หน้าที่ และผู้รับผิดชอบ

ตัวอย่างเช่น การบริหารรายการตรวจรักษา อาจแตกออกเป็น

- การสร้างรายการตรวจรักษา
- การกำหนดสัตวแพทย์ผู้รับผิดชอบ
- การเชื่อมโยงกับการเข้ารับบริการ
- การเปลี่ยนสถานะรายการตรวจ
- การยกเลิกรายการตรวจ
- การปิดรายการตรวจรักษา

ออกแบบขั้นตอนปฏิบัติงานจริง เงื่อนไข กฎทางธุรกิจ และกรณีผิดปกติ เช่น

- กระบวนการตรวจรักษาทั่วไป
- กระบวนการตรวจรักษาฉุกเฉิน
- กระบวนการวินิจฉัยโรค
- กระบวนการสั่งยา
- กระบวนการสั่งตรวจทางห้องปฏิบัติการ
- กระบวนการติดตามผล
- กระบวนการรับรองและแก้ไขเวชระเบียน

ขั้นที่ 3: Database Architecture & Complete ERD

ออกแบบตารางทั้งหมด พร้อมรายละเอียด

- Primary Key

- Data Types

- หน้าจอรายการตรวจรักษา
- หน้าจอบันทึกประวัติการเจ็บป่วย
- หน้าจอตรวจร่างกาย
- หน้าจอวินิจฉัยโรค

## ข้อเสนอแนะเพิ่มเติมก่อนออกแบบฐานข้อมูล

สำหรับ Domain นี้ ผมแนะนำให้ให้ความสำคัญกับ 6 เรื่องเป็นพิเศษ

1. Clinical Encounter Lifecycle: กำหนดวงจรชีวิตของรายการตรวจรักษา ตั้งแต่เปิดรายการจนถึงปิดรายการ
2. Medical Record Structure: กำหนดโครงสร้างเวชระเบียนและรูปแบบการบันทึกทางคลินิก
3. Diagnosis & Problem List: แยกการวินิจฉัยในแต่ละครั้งออกจากรายการปัญหาสุขภาพระยะยาว
4. Clinical Orders Lifecycle: กำหนดวงจรชีวิตของคำสั่งยา คำสั่งตรวจ และคำสั่งทางการแพทย์
5. Clinical Sign-off & Audit Trail: กำหนดการรับรองและการแก้ไขเวชระเบียน
6. Cross-Domain Integration: กำหนดการเชื่อมต่อกับ Pharmacy, Laboratory, Surgery และ Billing

ทั้ง 6 เรื่องนี้มีผลโดยตรงต่อโครงสร้างฐานข้อมูล การกำหนดสิทธิ์ การออกแบบ API และความถูกต้องของข้อมูลทางการแพทย์ในระยะยาว

ข้อเสนอแนะของผม: ควรออกแบบ Clinical Encounter Lifecycle และ Medical Record Structure ให้ชัดเจนก่อนเริ่มสร้างตารางฐานข้อมูล เพราะทั้งสองส่วนเป็นแกนหลักที่เชื่อมโยงความสามารถอื่น ๆ เกือบทั้งหมดของ Domain นี้ครับ
