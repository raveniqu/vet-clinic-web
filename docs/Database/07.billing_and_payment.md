# Domain 07 — Billing & Payment Management

เจ้าของข้อมูล: Domain 07

รับผิดชอบกระบวนการทางการเงินฝั่งการเรียกเก็บเงินและการรับชำระเงินของคลินิกและโรงพยาบาลสัตว์อย่างครบวงจร ตั้งแต่การบริหารสกุลเงินและลำดับเลขที่เอกสารทางการเงิน การกำหนดนโยบายอนุมัติและเงื่อนไขการคืนเงิน การบริหารราคาขายปลีกสินค้า/ยา กลุ่มราคาเฉพาะลูกค้า และแพ็กเกจเหมาจ่าย การจัดทำใบเสนอราคาและใบประมาณการค่ารักษา การรวบรวมรายการค่าบริการและสินค้าเรียกเก็บจากทุก Domain ต้นทาง (Clinical, Pharmacy, Laboratory & Imaging, Surgery & Treatment, Appointment, Inpatient Care และการขายปลีกหน้าร้าน) การบริหารส่วนลดและภาษีมูลค่าเพิ่ม/ภาษีหัก ณ ที่จ่าย การออกใบแจ้งหนี้และการควบคุมวงจรสถานะ การรับชำระเงินหลายช่องทางและหลายใบแจ้งหนี้ การบริหารแผนแบ่งชำระ การบริหารเงินมัดจำและเงินรับล่วงหน้า การออกใบเสร็จรับเงินและเอกสารกำกับภาษี (ใบกำกับภาษีอย่างย่อ เต็มรูป ใบลดหนี้ ใบเพิ่มหนี้) การปรับปรุงและยกเลิกรายการเรียกเก็บ กระบวนการขออนุมัติและจ่ายคืนเงิน การบริหารวงเงินเครดิตและบัญชีลูกหนี้ การกระทบยอดกับธนาคาร/Payment Gateway การปิดยอดเงินประจำวัน และการส่งออกข้อมูล Subledger ไปยังระบบบัญชีและการเงิน

ทั้งนี้ Domain 07 ยึดหลัก **Single Source of Truth (SSOT)** โดยเป็นเจ้าของข้อมูลราคาขายปลีกสินค้า/ยา สมุดราคาเฉพาะกลุ่ม ใบเสนอราคา รายการรอเรียกเก็บ ใบแจ้งหนี้ ส่วนลดจริงในธุรกรรม ภาษีขาย เอกสารรับชำระ เงินมัดจำ ใบเสร็จรับเงิน ใบกำกับภาษี การคืนเงิน บัญชีลูกหนี้ การกระทบยอด และการปิดยอดประจำวัน ส่วนข้อมูลสาขา ทะเบียนบริการกลาง และราคามาตรฐานบริการอยู่ที่ Domain 00 (`core`), ข้อมูลเจ้าของสัตว์ ที่อยู่วางบิล และสิทธิ์รับผิดชอบค่าใช้จ่ายอยู่ที่ Domain 01 (`owner`), การนัดหมายและลงทะเบียนอยู่ที่ Domain 02 (`appointment`), การตรวจรักษาและหัตถการห้องตรวจอยู่ที่ Domain 03 (`clinical`), ทะเบียนสินค้า ล็อต ยอดคงคลัง การจ่ายยาจริง และการรับคืนยาอยู่ที่ Domain 04 (`pharmacy`), รายการสั่งตรวจแล็บและภาพวินิจฉัยอยู่ที่ Domain 05 (`laboratory`), การผ่าตัดและวัสดุสิ้นเปลืองผ่าตัดอยู่ที่ Domain 06 (`surgery`), โปรโมชั่น คูปอง สมาชิก และคะแนนสะสมอยู่ที่ Domain 08 (`crm` — เชื่อมด้วย External UUID โดยไม่สร้างซ้ำ), การจัดซื้อและต้นทุนจัดซื้ออยู่ที่ Domain 09 (`procurement`), ข้อมูลพนักงานและผู้อนุมัติอยู่ที่ Domain 10 (`hr`), การดูแลผู้ป่วยในอยู่ที่ระบบ `Inpatient Care`, และการบันทึกบัญชีแยกประเภท GL อยู่ที่ระบบ `Finance & Accounting`

## กลุ่ม Master Config, Currencies, Document Sequences & Governance Policies

### ตาราง `billing.currencies`

**หน้าที่**: จัดเก็บทะเบียนสกุลเงินที่ระบบคลินิกรองรับสำหรับกำหนดราคา ออกใบแจ้งหนี้ และรับชำระเงิน พร้อมกติกาจำนวนทศนิยมและหลักเกณฑ์การปัดเศษตามข้อ 3.5 และหมวด 9 ข้อ 15

#### โครงสร้าง Field:

| Column | Data Type | Constraint |
| --- | --- | --- |
| `currency_id` | UUID | PK, NOT NULL |
| `currency_code` | CHAR(3) | UNIQUE, NOT NULL |
| `currency_name` | VARCHAR(100) | NOT NULL |
| `currency_symbol` | VARCHAR(10) | NOT NULL |
| `decimal_places` | SMALLINT | NOT NULL DEFAULT 2 |
| `rounding_mode` | ENUM | NOT NULL DEFAULT 'ROUND_HALF_UP' |
| `rounding_step` | NUMERIC(10,4) | NOT NULL DEFAULT 0.0100 |
| `is_base_currency` | BOOLEAN | NOT NULL DEFAULT FALSE |
| `status` | ENUM | NOT NULL |
| `created_at` | TIMESTAMPTZ | NOT NULL |
| `created_by` | UUID | FK → hr.employees, NOT NULL |
| `updated_at` | TIMESTAMPTZ | NULL |
| `updated_by` | UUID | FK → hr.employees, NULL |

#### ข้อกำหนด:

- `currency_id`: รหัสประจำสกุลเงินภายในระบบ ใช้เป็น Primary Key
- `currency_code`: รหัสสกุลเงินมาตรฐาน ISO 4217 3 ตัวอักษร (เช่น `THB`, `USD`, `SGD`) ต้องไม่ซ้ำกัน
- `currency_name`: ชื่อสกุลเงิน (เช่น `Thai Baht`, `US Dollar`)
- `currency_symbol`: สัญลักษณ์สกุลเงินสำหรับแสดงบนเอกสาร (เช่น `฿`, `$`)
- `decimal_places`: จำนวนตำแหน่งทศนิยมที่ใช้แสดงผลและคำนวณสุทธิ (0–4)
- `rounding_mode`: หลักเกณฑ์การปัดเศษตามนโยบายคลินิก (§3.5) ค่าที่เป็นไปได้ คือ `ROUND_HALF_UP` (ปัดครึ่งขึ้น), `ROUND_HALF_EVEN` (ปัดแบบ Banker), `ROUND_DOWN` (ปัดลง), `ROUND_UP` (ปัดขึ้น), `SATANG_25_STEP` (ปัดตามหน่วย 0.25 บาทกรณีเงินสด)
- `rounding_step`: ขนาดขั้นต่ำในการปัดเศษของสกุลเงินนี้ (เช่น `0.0100` หรือ `0.2500`)
- `is_base_currency`: ระบุว่าเป็นสกุลเงินหลักทางบัญชีของกิจการหรือไม่
- `status`: สถานะการใช้งาน (`ACTIVE`, `INACTIVE`)
- `created_at` / `created_by` / `updated_at` / `updated_by`: ข้อมูล Audit อ้างอิง `hr.employees`

#### หมายเหตุ:

1. ระบบต้องมีสกุลเงินที่ `is_base_currency = TRUE` และ `status = 'ACTIVE'` เพียง 1 รายการ (ใช้ Partial UNIQUE Index บน `is_base_currency` WHERE `is_base_currency = TRUE`)
2. `decimal_places` ต้องอยู่ระหว่าง `0` ถึง `4` และ `rounding_step > 0`

### ตาราง `billing.exchange_rates`

**หน้าที่**: จัดเก็บอัตราแลกเปลี่ยนเงินตราต่างประเทศเทียบกับสกุลเงินหลักตามช่วงเวลาที่มีผลบังคับใช้ เพื่อใช้อ้างอิงเมื่อมีลูกค้าชำระหรือออกบิลเป็นสกุลเงินอื่นและแปลงมูลค่ากลับเป็นสกุลเงินหลัก

#### โครงสร้าง Field:

| Column | Data Type | Constraint |
| --- | --- | --- |
| `exchange_rate_id` | UUID | PK, NOT NULL |
| `from_currency_id` | UUID | FK → billing.currencies, NOT NULL |
| `to_currency_id` | UUID | FK → billing.currencies, NOT NULL |
| `exchange_rate` | NUMERIC(18,8) | NOT NULL |
| `effective_from` | TIMESTAMPTZ | NOT NULL |
| `effective_to` | TIMESTAMPTZ | NULL |
| `rate_source` | ENUM | NOT NULL |
| `status` | ENUM | NOT NULL |
| `created_at` | TIMESTAMPTZ | NOT NULL |
| `created_by` | UUID | FK → hr.employees, NOT NULL |
| `updated_at` | TIMESTAMPTZ | NULL |
| `updated_by` | UUID | FK → hr.employees, NULL |

#### ข้อกำหนด:

- `exchange_rate_id`: รหัสประจำรายการอัตราแลกเปลี่ยน ใช้เป็น Primary Key
- `from_currency_id` / `to_currency_id`: สกุลเงินต้นทางและสกุลเงินปลายทาง อ้างอิง `billing.currencies`
- `exchange_rate`: อัตราแลกเปลี่ยน (1 หน่วยของ `from_currency_id` เท่ากับกี่หน่วยของ `to_currency_id`)
- `effective_from` / `effective_to`: วันเวลาที่เริ่มและสิ้นสุดการใช้อัตรานี้
- `rate_source`: แหล่งที่มาของอัตราแลกเปลี่ยน (`BOT_REFERENCE` ธนาคารแห่งประเทศไทย, `COMMERCIAL_BANK` ธนาคารพาณิชย์, `CLINIC_MANUAL` กำหนดเองตามนโยบาย)
- `status`: สถานะ (`ACTIVE`, `EXPIRED`, `CANCELLED`)
- `created_at` / `created_by` / `updated_at` / `updated_by`: ข้อมูล Audit

#### หมายเหตุ:

1. `from_currency_id <> to_currency_id` และ `exchange_rate > 0`
2. ห้ามแก้ไขทับอัตราแลกเปลี่ยนที่ถูกนำไปใช้ Snapshot บนใบแจ้งหนี้หรือรายการรับชำระแล้ว

### ตาราง `billing.document_sequences`

**หน้าที่**: บริหารประเภทเอกสารทางการเงินและรูปแบบเลขที่เอกสาร (Running Number Pattern) แยกตามสาขาและงวดเวลา เพื่อรับรองว่าเลขที่ใบแจ้งหนี้ ใบเสร็จรับเงิน ใบกำกับภาษี ใบลดหนี้ และใบเพิ่มหนี้ไม่ซ้ำกันและเรียงลำดับถูกต้องตามข้อ 3.8, 3.15, 3.16 และหมวด 9 ข้อ 10–11

#### โครงสร้าง Field:

| Column | Data Type | Constraint |
| --- | --- | --- |
| `sequence_id` | UUID | PK, NOT NULL |
| `branch_id` | UUID | FK → core.branches, NOT NULL |
| `document_type` | ENUM | NOT NULL |
| `document_prefix` | VARCHAR(20) | NOT NULL |
| `number_format_pattern` | VARCHAR(100) | NOT NULL |
| `reset_frequency` | ENUM | NOT NULL |
| `current_period_key` | VARCHAR(20) | NOT NULL |
| `last_running_number` | INTEGER | NOT NULL DEFAULT 0 |
| `padding_length` | SMALLINT | NOT NULL DEFAULT 4 |
| `is_tax_document` | BOOLEAN | NOT NULL DEFAULT FALSE |
| `effective_from` | DATE | NOT NULL |
| `effective_to` | DATE | NULL |
| `status` | ENUM | NOT NULL |
| `created_at` | TIMESTAMPTZ | NOT NULL |
| `created_by` | UUID | FK → hr.employees, NOT NULL |
| `updated_at` | TIMESTAMPTZ | NULL |
| `updated_by` | UUID | FK → hr.employees, NULL |

#### ข้อกำหนด:

- `sequence_id`: รหัสประจำชุดรันเลขที่เอกสาร ใช้เป็น Primary Key
- `branch_id`: สาขาที่เป็นเจ้าของชุดเลขที่เอกสาร อ้างอิง `core.branches`
- `document_type`: ประเภทเอกสารทางการเงิน ค่าที่เป็นไปได้ คือ `QUOTATION` (ใบเสนอราคา), `TREATMENT_ESTIMATE` (ใบประมาณการค่ารักษา), `BILLABLE_CHARGE` (รายการเรียกเก็บ), `INVOICE` (ใบแจ้งหนี้), `RECEIPT` (ใบเสร็จรับเงิน), `TAX_INVOICE_ABB` (ใบกำกับภาษีอย่างย่อ), `TAX_INVOICE_FULL` (ใบกำกับภาษีเต็มรูป), `RECEIPT_TAX_INVOICE` (ใบเสร็จรับเงิน/ใบกำกับภาษี), `CREDIT_NOTE` (ใบลดหนี้), `DEBIT_NOTE` (ใบเพิ่มหนี้), `DEPOSIT_RECEIPT` (ใบรับเงินมัดจำ), `PAYMENT_VOUCHER` (ใบรับชำระเงิน), `REFUND_REQUEST` (คำขอคืนเงิน), `REFUND_EXECUTION` (ใบคืนเงิน), `BILLING_ADJUSTMENT` (ใบปรับปรุงรายการเรียกเก็บ), `WHT_RECORD` (ทะเบียนรับหนังสือรับรองหัก ณ ที่จ่าย), `AR_WRITE_OFF` (คำขอตัดหนี้สูญ), `DAILY_CLOSING` (ใบสรุปปิดยอดประจำวัน)
- `document_prefix`: คำนำหน้าเลขที่เอกสาร เช่น `INV`, `RCP`, `TAX`, `ABB`, `CDN`, `DBN`, `DEP`
- `number_format_pattern`: รูปแบบ Template เช่น `{PREFIX}-{BRANCH}-{YYYY}{MM}{DD}-{NNNN}` หรือ `{PREFIX}-{TAX_BRANCH}-{YY}{MM}-{NNNNN}`
- `reset_frequency`: รอบการรีเซ็ตเลขที่รัน (`DAILY`, `MONTHLY`, `YEARLY`, `FISCAL_YEAR`, `NEVER`)
- `current_period_key`: คีย์งวดเวลาปัจจุบันที่กำลังรันเลขอยู่ (เช่น `202611` หรือ `20261120`)
- `last_running_number`: เลขลำดับล่าสุดที่ออกไปแล้ว (ใช้ Transaction Lock `SELECT ... FOR UPDATE` ขณะออกเลขจริง)
- `padding_length`: จำนวนหลักของเลขรัน (เช่น `4` -> `0001`)
- `is_tax_document`: ระบุว่าเป็นเอกสารที่มีผลทางภาษีซึ่งต้องรักษาลำดับเลขที่ต่อเนื่องห้ามข้ามหรือลบโดยพลการหรือไม่
- `effective_from` / `effective_to` / `status`: วันที่มีผลบังคับใช้และสถานะ (`ACTIVE`, `INACTIVE`)
- `created_at` / `created_by` / `updated_at` / `updated_by`: ข้อมูล Audit

#### หมายเหตุ:

1. กำหนด Unique Constraint `(branch_id, document_type, current_period_key)` สำหรับชุดที่ `status = 'ACTIVE'`
2. การสร้างเลขที่เอกสารภาษี (`is_tax_document = TRUE`) ต้องเกิดใน Database Transaction เดียวกับการออกเอกสารและห้ามนำไปสร้างเลขซ้ำหรือย้อนหลังข้ามวันทำการ

### ตาราง `billing.approval_policies`

**หน้าที่**: กำหนดนโยบายและวงเงินอำนาจอนุมัติสำหรับธุรกรรมทางการเงินที่มีความเสี่ยงสูง (การให้ส่วนลดพิเศษ การแก้ราคา การคืนเงิน การยกเลิกใบแจ้งหนี้ การปรับปรุงยอด การอนุมัติวงเงินเครดิต การแบ่งชำระ และการตัดหนี้สูญ) เพื่อบังคับใช้หลักการแบ่งแยกหน้าที่ (Segregation of Duties) ตามข้อ 6.1, หมวด 7, หมวด 9 ข้อ 13 และ BR-018

#### โครงสร้าง Field:

| Column | Data Type | Constraint |
| --- | --- | --- |
| `approval_policy_id` | UUID | PK, NOT NULL |
| `policy_code` | VARCHAR(50) | UNIQUE, NOT NULL |
| `policy_name` | VARCHAR(200) | NOT NULL |
| `branch_id` | UUID | FK → core.branches, NULL |
| `action_type` | ENUM | NOT NULL |
| `min_amount` | NUMERIC(14,2) | NOT NULL DEFAULT 0 |
| `max_amount` | NUMERIC(14,2) | NULL |
| `max_discount_pct` | NUMERIC(6,2) | NULL |
| `required_approver_role_code` | VARCHAR(50) | NOT NULL |
| `disallow_self_approval` | BOOLEAN | NOT NULL DEFAULT TRUE |
| `requires_reason_attachment` | BOOLEAN | NOT NULL DEFAULT FALSE |
| `priority_order` | SMALLINT | NOT NULL DEFAULT 1 |
| `effective_from` | DATE | NOT NULL |
| `effective_to` | DATE | NULL |
| `status` | ENUM | NOT NULL |
| `created_at` | TIMESTAMPTZ | NOT NULL |
| `created_by` | UUID | FK → hr.employees, NOT NULL |
| `updated_at` | TIMESTAMPTZ | NULL |
| `updated_by` | UUID | FK → hr.employees, NULL |

#### ข้อกำหนด:

- `approval_policy_id`: รหัสประจำนโยบายการอนุมัติ ใช้เป็น Primary Key
- `policy_code` / `policy_name`: รหัสและชื่อนโยบาย (เช่น `APV-REFUND-TIER1`, `APV-DISC-MANAGER`)
- `branch_id`: สาขาที่บังคับใช้นโยบาย (เป็น `NULL` หากใช้เป็นนโยบายกลางทุกสาขา)
- `action_type`: ประเภทธุรกรรมที่ต้องขออนุมัติ ค่าที่เป็นไปได้ คือ `SPECIAL_DISCOUNT`, `PRICE_OVERRIDE`, `REFUND_APPROVAL`, `INVOICE_CANCELLATION`, `BILLING_ADJUSTMENT`, `CREDIT_LIMIT_ASSIGNMENT`, `PAYMENT_PLAN_APPROVAL`, `AR_WRITE_OFF`, `DAILY_CLOSING_VARIANCE`, `DEPOSIT_FORFEITURE`, `TAX_INVOICE_REISSUE`
- `min_amount` / `max_amount`: ช่วงมูลค่าธุรกรรมตามนโยบาย (`max_amount IS NULL` หมายถึงไม่จำกัดเพดานบนสำหรับผู้มีอำนาจระดับสูงสุด)
- `max_discount_pct`: เพดานเปอร์เซ็นต์ส่วนลดที่เกี่ยวข้อง (กรณี `SPECIAL_DISCOUNT` หรือ `PRICE_OVERRIDE`)
- `required_approver_role_code`: รหัสบทบาท/ตำแหน่งผู้มีอำนาจอนุมัติ (เช่น `FINANCE_SUPERVISOR`, `BRANCH_MANAGER`, `FINANCE_MANAGER`, `EXECUTIVE`) เชื่อมโยงสิทธิ์กับ Domain HR / IT & Security
- `disallow_self_approval`: บังคับห้ามผู้ขออนุมัติเป็นผู้อนุมัติรายการของตนเอง (ค่าเริ่มต้น `TRUE` ตามหลัก Segregation of Duties หมวด 7)
- `requires_reason_attachment`: บังคับแนบเอกสารหรือหลักฐานประกอบคำขอหรือไม่

- `notes` / `created_at` / `created_by` / `updated_at` / `updated_by`: หมายเหตุและข้อมูล Audit

#### หมายเหตุ:

1. กำหนด Partial UNIQUE Index บน `(source_domain, source_record_type, source_record_id)` WHERE `charge_status <> 'CANCELLED'` และ `source_domain <> 'BILLING_MANUAL'` เพื่อป้องกัน BR-002 (ห้ามนำรายการต้นทางเดียวกันมาเรียกเก็บซ้ำ) 100%
2. รายการยาจากห้องยาต้องรับจำนวนที่จ่ายจริงจาก `pharmacy.dispensing_items.dispensed_qty_in_uom` เท่านั้น ห้ามดึงจาก `clinical.prescription_items` โดยตรง (กฎ §3.2 และ §5.3)
3. การสั่งตรวจแบบชุดตรวจใน `laboratory.diagnostic_order_items` (`source_panel_id IS NOT NULL`) ที่คิดราคาเหมาชุด ให้สร้าง `charge` เดียวจาก `DIAGNOSTIC_PANEL` (`panel_id`) หรือสร้างรายตัวตามนโยบายโดยไม่คิดเงินซ้ำซ้อน
4. ต้องไม่แก้ไขข้อมูลการให้บริการจริงใน Domain ต้นทางจากตารางนี้ (กฎ §3.4)

- `version_number` / `locked_at`: เลขเวอร์ชันเอกสารและเวลาล็อกหลังยืนยัน (ห้ามแก้ไขตรงหลังมีค่า `locked_at` ต้องใช้ `billing_adjustments`)

- `created_by` / `approved_by` / `approved_at` / `created_at` / `updated_at` / `updated_by`: ข้อมูลผู้ออก ผู้อนุมัติ และ Audit

- `payer_type`: ประเภทผู้ชำระเงินตาม BR-010 และข้อ 3.10 (`OWNER` เจ้าของสัตว์, `CO_OWNER` เจ้าของร่วม, `THIRD_PARTY_INDIVIDUAL` บุคคลอื่นจ่ายแทน, `CORPORATE` บริษัท/องค์กรจ่ายแทน, `INSURANCE_COMPANY` บริษัทประกัน, `WALK_IN_GUEST` ลูกค้าปลีกหน้าร้าน)

- `total_allocated_amount`: ยอดเงินที่นำไปตัดชำระใบแจ้งหนี้หรือมัดจำ
- `wht_deducted_amount`: ยอดภาษีหัก ณ ที่จ่ายที่ผู้จ่ายหักไว้ (เชื่อมกับ `billing.withholding_tax_certificates`)
- `overpayment_amount` / `overpayment_handling`: ยอดเงินส่วนเกินกรณีลูกค้าจ่ายเกินยอดบิล และนโยบายจัดการยอดส่วนเกิน (`NONE` ไม่มียอดเกิน, `CONVERT_TO_ADVANCE` เก็บเป็นเงินรับล่วงหน้าใน `billing.deposits`, `PENDING_REFUND` รอดำเนินการคืนเงิน)
- `payment_date` / `received_at` / `received_by`: วันที่ เวลาที่รับชำระ และพนักงานผู้รับเงิน
- `payment_status`: สถานะธุรกรรม (`INITIATED`, `PENDING_VERIFICATION`, `CONFIRMED`, `PARTIALLY_REFUNDED`, `REFUNDED`, `FAILED`, `CANCELLED`, `VOIDED`)
- `void_reason` / `voided_by` / `voided_at`: เหตุผล ผู้ยกเลิก และเวลาที่ยกเลิก (ห้ามลบธุรกรรมจริง)
- `notes` / `created_at` / `updated_at` / `updated_by`: หมายเหตุและข้อมูล Audit

#### หมายเหตุ:

1. `total_tender_amount > 0` และต้องไม่บันทึก `payment_status = 'CONFIRMED'` จนกว่าทุก `payment_tenders` ที่บังคับตรวจหลักฐานจะผ่านการตรวจสอบจริง (กฎ §3.10–3.11)
2. เมื่อ `overpayment_handling = 'CONVERT_TO_ADVANCE'` ระบบต้องสร้างรายการเงินรับล่วงหน้าใน `billing.deposits` (`deposit_type = 'OVERPAYMENT_CREDIT'`) ใน Transaction เดียวกัน

- `deposit_status`: สถานะตามข้อ 3.14 (`PENDING_PAYMENT`, `ACTIVE_HELD`, `PARTIALLY_APPLIED`, `FULLY_APPLIED`, `REFUNDED`, `FORFEITED`, `EXPIRED`, `CANCELLED`)
- `forfeiture_reason` / `approved_by`: เหตุผลและผู้อนุมัติกรณีริบเงินมัดจำ (เช่น ไม่มาตามนัดตามเงื่อนไขที่แจ้งลูกค้าไว้)
- `notes` / `created_at` / `created_by` / `updated_at` / `updated_by`: หมายเหตุและข้อมูล Audit

1. `deposit_amount > 0` และต้องรักษาสมการ `remaining_balance = deposit_amount - applied_amount - refunded_amount - forfeited_amount >= 0` เสมอเพื่อป้องกันการนำเงินมัดจำก้อนเดียวไปหักซ้ำ (กฎ §3.14)
2. เงินมัดจำในตารางนี้ถือเป็นหนี้สิน/เงินรับล่วงหน้า ห้ามบันทึกเป็นรายได้บริการจนกว่าจะถูกนำไปหักใน `billing.deposit_applications` (BR-005)
