# Domain 08 — Marketing & Customer Relationship Management

เจ้าของข้อมูล: Domain 08

รับผิดชอบกระบวนการบริหารการตลาดและการสร้างความสัมพันธ์กับลูกค้าของคลินิกและโรงพยาบาลสัตว์อย่างครบวงจร ตั้งแต่การบริหารช่องทางการตลาด การจัดเก็บและติดตามผู้มุ่งหวัง (Lead Management) การวางแผนและติดตามแคมเปญการตลาด กิจกรรมส่งเสริมการขาย โอกาสทางการขาย การบริหารข้อเสนอโปรโมชั่น คูปองและสิทธิประโยชน์ ระบบสมาชิก (Membership) บัญชีและประวัติคะแนนสะสมแบบตรวจสอบย้อนหลังได้ การแบ่งกลุ่มลูกค้า (Customer Segmentation) โปรไฟล์และประวัติความสัมพันธ์ลูกค้า งานดูแลลูกค้า การสื่อสารหลายช่องทางแยกจากแคมเปญ ระบบส่งข้อความอัตโนมัติ การแจ้งเตือนเชิงสัมพันธ์ การรับฟังความคิดเห็น แบบสำรวจความพึงพอใจ การบริหารข้อร้องเรียนและการส่งต่อเคสทางการแพทย์ ไปจนถึงการวัดผลตอบแทนทางการตลาด (Marketing Attribution / ROI) และการวิเคราะห์มูลค่าลูกค้าตลอดความสัมพันธ์ (Customer Lifetime Value — CLV)

ทั้งนี้ Domain 08 ยึดหลัก **Single Source of Truth (SSOT)** โดยเป็นเจ้าของข้อมูลช่องทางการตลาด ผู้มุ่งหวัง แคมเปญ กิจกรรมส่งเสริมการขาย โอกาสขาย ข้อเสนอโปรโมชั่น แม่แบบและใบคูปอง ระดับสมาชิก คะแนนสะสม กลุ่มลูกค้า ประวัติความสัมพันธ์ การสื่อสาร งานดูแลลูกค้า แบบสำรวจ ความคิดเห็น และข้อร้องเรียนด้านบริการ ส่วนข้อมูลลูกค้า สัตว์เลี้ยง ช่องทางติดต่อ (`do_not_contact`) และความยินยอม PDPA (`owner.owner_consents`) อยู่ที่ Domain 01 (`owner`), ตารางนัดหมายจริงและการแจ้งเตือนนัดหมายอยู่ที่ Domain 02 (`appointment`), เวชระเบียน แผนวัคซีน การติดตามผลทางคลินิก และเหตุการณ์ไม่พึงประสงค์ทางคลินิก (`clinical.adverse_events`) อยู่ที่ Domain 03 (`clinical`), ทะเบียนสินค้าอยู่ที่ Domain 04 (`pharmacy`), การติดตามหลังผ่าตัดอยู่ที่ Domain 06 (`surgery`), การคำนวณและบันทึกส่วนลดจริงบนใบแจ้งหนี้ รวมถึงยอดรายได้และยอดชำระเงินจริงอยู่ที่ Domain 07 (`billing`), และข้อมูลพนักงานอยู่ที่ Domain 10 (`hr`)

## กลุ่ม Marketing Channels, Leads, Campaigns, Events & Sales Opportunities

### ตาราง `crm.marketing_channels`

**หน้าที่**: จัดเก็บทะเบียนช่องทางการตลาดและประชาสัมพันธ์ทั้งหมดของคลินิก (เช่น Facebook, LINE OA, Instagram, TikTok, เว็บไซต์คลินิก, Google Business Profile, โฆษณาออนไลน์, การแนะนำจากลูกค้าเดิม, การประชาสัมพันธ์ในคลินิก, กิจกรรมชุมชน) เพื่อใช้ติดตามแหล่งที่มา ต้นทุน และประสิทธิภาพการสร้างลูกค้าใหม่โดยสามารถปิดใช้งานช่องทางเดิมได้โดยไม่ลบประวัติตามข้อ 4.2

#### โครงสร้าง Field:

| Column | Data Type | Constraint |
| --- | --- | --- |
| `channel_id` | UUID | PK, NOT NULL |
| `channel_code` | VARCHAR(50) | UNIQUE, NOT NULL |
| `channel_name` | VARCHAR(150) | NOT NULL |
| `channel_type` | ENUM | NOT NULL |
| `description` | TEXT | NULL |
| `responsible_employee_id` | UUID | FK → hr.employees, NULL |
| `operating_cost_budget` | NUMERIC(14,2) | NULL |
| `external_account_ref` | VARCHAR(200) | NULL |
| `effective_from` | DATE | NOT NULL |
| `effective_to` | DATE | NULL |
| `status` | ENUM | NOT NULL |
| `created_at` | TIMESTAMPTZ | NOT NULL |
| `created_by` | UUID | FK → hr.employees, NOT NULL |
| `updated_at` | TIMESTAMPTZ | NULL |
| `updated_by` | UUID | FK → hr.employees, NULL |

#### ข้อกำหนด:

- `channel_id`: รหัสประจำช่องทางการตลาด ใช้เป็น Primary Key
- `channel_code`: รหัสช่องทางที่ไม่ซ้ำกัน (เช่น `CH-LINE-OA`, `CH-FB-ADS`, `CH-GOOGLE-BP`, `CH-REFERRAL`)
- `channel_name`: ชื่อช่องทางการตลาดที่ใช้แสดงในระบบและรายงาน
- `channel_type`: ประเภทช่องทางตามข้อ 4.2 (`FACEBOOK`, `LINE_OA`, `INSTAGRAM`, `TIKTOK`, `CLINIC_WEBSITE`, `GOOGLE_BUSINESS_PROFILE`, `ONLINE_PAID_ADS`, `CUSTOMER_REFERRAL`, `IN_CLINIC_MEDIA`, `COMMUNITY_EVENT`, `CALL_PHONE`, `EMAIL`, `OTHER`)
- `description`: รายละเอียดลักษณะและวัตถุประสงค์ของช่องทาง
- `responsible_employee_id`: พนักงานหรือผู้ดูแลช่องทาง อ้างอิง `hr.employees`
- `operating_cost_budget`: งบประมาณค่าใช้จ่ายในการดำเนินการของช่องทางโดยรวม (สำหรับประกอบการวิเคราะห์ CAC)
- `external_account_ref`: รหัสบัญชีหรือ Page ID / OA ID จากแพลตฟอร์มภายนอก
- `effective_from` / `effective_to`: วันที่เริ่มใช้งานและวันที่สิ้นสุดการใช้งานช่องทาง
- `status`: สถานะการใช้งาน (`ACTIVE`, `INACTIVE`, `ARCHIVED`)
- `created_at` / `created_by` / `updated_at` / `updated_by`: ข้อมูล Audit อ้างอิง `hr.employees`

#### หมายเหตุ:

1. ห้ามลบช่องทางที่มีประวัติผู้มุ่งหวัง แคมเปญ หรือการติดต่อแล้ว ให้เปลี่ยน `status = 'INACTIVE'` หรือ `ARCHIVED` เพื่อรักษาประวัติการวิเคราะห์ย้อนหลัง (กฎ §4.2)

### ตาราง `crm.customer_channel_attributions`

**หน้าที่**: จัดเก็บความสัมพันธ์แบบหลายต่อหลาย (M:N) ระหว่างลูกค้า (`owner.owners`) หรือผู้มุ่งหวัง (`crm.leads`) กับช่องทางการตลาด เพื่อให้ระบบสามารถแยกระหว่างช่องทางที่ลูกค้ารู้จักคลินิกออกจากช่องทางที่ลูกค้าใช้ติดต่อจริง และรองรับให้ลูกค้าหนึ่งรายรู้จักคลินิกจากหลายช่องทางได้ตามข้อ 4.2

#### โครงสร้าง Field:

| Column | Data Type | Constraint |
| --- | --- | --- |
| `attribution_record_id` | UUID | PK, NOT NULL |
| `owner_id` | UUID | FK → owner.owners, NULL |
| `lead_id` | UUID | FK → crm.leads, NULL |
| `channel_id` | UUID | FK → crm.marketing_channels, NOT NULL |
| `attribution_role` | ENUM | NOT NULL |
| `campaign_id` | UUID | FK → crm.marketing_campaigns, NULL |
| `utm_source` | VARCHAR(100) | NULL |
| `utm_medium` | VARCHAR(100) | NULL |
| `utm_campaign` | VARCHAR(150) | NULL |
| `referral_source_owner_id` | UUID | FK → owner.owners, NULL |
| `is_primary` | BOOLEAN | NOT NULL DEFAULT FALSE |
| `observed_at` | TIMESTAMPTZ | NOT NULL |
| `notes` | TEXT | NULL |
| `created_at` | TIMESTAMPTZ | NOT NULL |
| `created_by` | UUID | FK → hr.employees, NULL |

#### ข้อกำหนด:

- `attribution_record_id`: รหัสประจำข้อมูลแหล่งที่มาช่องทาง ใช้เป็น Primary Key
- `owner_id` / `lead_id`: ลูกค้าจริงหรือผู้มุ่งหวังที่เกี่ยวข้อง (ต้องระบุอย่างน้อย 1 แหล่ง)
- `channel_id`: ช่องทางการตลาดที่เกี่ยวข้อง อ้างอิง `crm.marketing_channels`
- `attribution_role`: บทบาทของช่องทางต่อบุคคลรายนี้ ค่าที่เป็นไปได้ คือ `DISCOVERY_KNOWN_FROM` (ช่องทางที่ลูกค้ารู้จักคลินิก เช่น Google Search) และ `CONTACT_CHANNEL` (ช่องทางที่ลูกค้าทักหรือติดต่อเข้ามาจริง เช่น LINE OA) ตามกฎ §4.2
- `campaign_id`: แคมเปญการตลาดที่ดึงดูดเข้ามา (ถ้ามี)
- `utm_source` / `utm_medium` / `utm_campaign`: พารามิเตอร์ติดตามจากลิงก์โฆษณาหรือเว็บไซต์
- `referral_source_owner_id`: รหัสลูกค้าผู้แนะนำ (กรณีมาจากการแนะนำเพื่อน `CUSTOMER_REFERRAL`) อ้างอิง `owner.owners`
- `is_primary`: ระบุว่าเป็นช่องทางหลักในบทบาทนั้นหรือไม่
- `observed_at` / `notes` / `created_at` / `created_by`: วันเวลาที่พบข้อมูล หมายเหตุ และข้อมูล Audit

#### หมายเหตุ:

1. กำหนด CHECK Constraint: `owner_id IS NOT NULL OR lead_id IS NOT NULL`
2. สำหรับการสร้าง SQL DDL จริง ควรเพิ่ม FK `lead_id → crm.leads` และ `campaign_id → crm.marketing_campaigns` ด้วยคำสั่ง `ALTER TABLE` ภายหลัง

### ตาราง `crm.leads`

**หน้าที่**: จัดเก็บข้อมูลบุคคลที่สอบถามหรือแสดงความสนใจในบริการของคลินิก (ผู้มุ่งหวัง) โดยแยกออกจากทะเบียนลูกค้าจริง (`owner.owners`) จนกว่าจะตกลงเข้ารับบริการจริง พร้อมแยกช่องทางที่รู้จักคลินิกออกจากช่องทางที่ติดต่อจริง และเก็บจุดเชื่อมโยงเมื่อ Convert เป็นลูกค้าใน Domain 01 ตามข้อ 4.1 และ 4.2

#### โครงสร้าง Field:

| Column | Data Type | Constraint |
| --- | --- | --- |
| `lead_id` | UUID | PK, NOT NULL |
| `lead_code` | VARCHAR(30) | UNIQUE, NOT NULL |
| `branch_id` | UUID | FK → core.branches, NULL |
| `contact_name` | VARCHAR(150) | NOT NULL |
| `phone_number` | VARCHAR(30) | NULL |
| `email` | VARCHAR(255) | NULL |
| `line_user_id` | VARCHAR(100) | NULL |
| `discovery_channel_id` | UUID | FK → crm.marketing_channels, NULL |
| `contact_channel_id` | UUID | FK → crm.marketing_channels, NOT NULL |
| `campaign_id` | UUID | FK → crm.marketing_campaigns, NULL |
| `interested_service_catalog_id` | UUID | FK → core.service_catalogs, NULL |
| `interested_service_summary` | VARCHAR(255) | NULL |
| `pet_species_summary` | VARCHAR(150) | NULL |
| `pet_details_notes` | TEXT | NULL |
| `inquired_at` | TIMESTAMPTZ | NOT NULL |
| `assigned_employee_id` | UUID | FK → hr.employees, NULL |
| `lead_status` | ENUM | NOT NULL |
| `lost_reason` | TEXT | NULL |
| `duplicate_of_lead_id` | UUID | FK → crm.leads, NULL |
| `converted_owner_id` | UUID | FK → owner.owners, NULL |
| `converted_at` | TIMESTAMPTZ | NULL |
| `notes` | TEXT | NULL |
| `created_at` | TIMESTAMPTZ | NOT NULL |
| `created_by` | UUID | FK → hr.employees, NULL |
| `updated_at` | TIMESTAMPTZ | NULL |
| `updated_by` | UUID | FK → hr.employees, NULL |

#### ข้อกำหนด:

- `lead_id`: รหัสประจำผู้มุ่งหวัง ใช้เป็น Primary Key
- `lead_code`: รหัสอ้างอิงผู้มุ่งหวังที่ไม่ซ้ำกัน รูปแบบ `LEAD-{YYYY}{MM}{DD}-{NNNN}` (สอดคล้องกับตัวอย่าง `LEAD-000001` ใน §4.1)
- `branch_id`: สาขาที่ผู้มุ่งหวังสนใจติดต่อ (ถ้ามี)
- `contact_name` / `phone_number` / `email` / `line_user_id`: ชื่อผู้ติดต่อและช่องทางติดต่อสำหรับตรวจสอบข้อมูลซ้ำก่อนสร้างรายการใหม่
- `discovery_channel_id` / `contact_channel_id`: แยกช่องทางที่ผู้มุ่งหวังรู้จักคลินิก (เช่น Google) ออกจากช่องทางที่ใช้ทักหรือโทรเข้ามาจริง (เช่น LINE OA) ตามกฎ §4.2
- `campaign_id`: แคมเปญที่ผู้มุ่งหวังตอบรับเข้ามา (ถ้ามี)
- `interested_service_catalog_id` / `interested_service_summary`: บริการที่สอบถาม (เช่น ตรวจสุขภาพ วัคซีน ทำหมัน)
- `pet_species_summary` / `pet_details_notes`: ข้อมูลสัตว์เลี้ยงเบื้องต้นที่สอบถามเข้ามา
- `inquired_at` / `assigned_employee_id`: วันเวลาที่เริ่มติดต่อสอบถาม และพนักงานผู้รับผิดชอบติดตาม
- `lead_status`: สถานะผู้มุ่งหวัง (`NEW`, `CONTACTED`, `IN_FOLLOW_UP`, `QUALIFIED`, `CONVERTED`, `LOST_NOT_INTERESTED`, `DUPLICATE`, `CLOSED`)
- `lost_reason` / `duplicate_of_lead_id`: เหตุผลที่ไม่ใช้บริการ (กรณี `LOST_NOT_INTERESTED`) หรือรหัสผู้มุ่งหวังหลัก (กรณีตรวจพบว่าซ้ำซ้อน)
- `converted_owner_id` / `converted_at`: รหัสลูกค้าจริงใน `owner.owners` และวันเวลาที่เปลี่ยนสถานะเป็นลูกค้าจริง
- `notes` / `created_at` / `created_by` / `updated_at` / `updated_by`: หมายเหตุและข้อมูล Audit

#### หมายเหตุ:

1. ห้ามถือว่าผู้มุ่งหวังในตารางนี้เป็นลูกค้าที่ใช้บริการแล้ว จนกว่าจะลงทะเบียนใน `owner.owners` และเชื่อมโยง `converted_owner_id` พร้อมตั้ง `lead_status = 'CONVERTED'` (กฎ §4.1)
2. สำหรับการสร้าง SQL DDL จริง ควรเพิ่ม FK `campaign_id → crm.marketing_campaigns` ด้วยคำสั่ง `ALTER TABLE` ภายหลัง

### ตาราง `crm.lead_activities`

**หน้าที่**: จัดเก็บประวัติการติดต่อ ติดตาม และให้ข้อมูลบริการแก่ผู้มุ่งหวังแต่ละรายใน `crm.leads` ตามลำดับเวลาตามข้อ 4.1

#### โครงสร้าง Field:

| Column | Data Type | Constraint |
| --- | --- | --- |
| `lead_activity_id` | UUID | PK, NOT NULL |
| `lead_id` | UUID | FK → crm.leads, NOT NULL |
| `activity_type` | ENUM | NOT NULL |
| `channel_id` | UUID | FK → crm.marketing_channels, NULL |
| `performed_by` | UUID | FK → hr.employees, NOT NULL |
| `activity_at` | TIMESTAMPTZ | NOT NULL |
| `summary` | TEXT | NOT NULL |
| `outcome` | ENUM | NOT NULL |
| `next_follow_up_at` | TIMESTAMPTZ | NULL |
| `created_at` | TIMESTAMPTZ | NOT NULL |

#### ข้อกำหนด:

- `lead_activity_id`: รหัสประจำกิจกรรมการติดตามผู้มุ่งหวัง ใช้เป็น Primary Key
- `lead_id`: ผู้มุ่งหวังที่ติดตาม อ้างอิง `crm.leads`
- `activity_type`: ประเภทกิจกรรม (`INBOUND_INQUIRY`, `OUTBOUND_CALL`, `CHAT_REPLY`, `SENT_PACKAGE_INFO`, `BOOKING_ASSISTANCE`, `STATUS_NOTE`)

#### หมายเหตุ:

1. ตารางนี้เก็บข้อมูลแบบ Append-only เพื่อตรวจสอบประวัติการติดตามผู้มุ่งหวังย้อนหลัง

- `points_delta` / `balance_before` / `balance_after`: จำนวนคะแนนที่เปลี่ยนแปลง (+ เพิ่ม / - ลด), ยอดก่อนทำรายการ และยอดหลังทำรายการ
- `rule_id` / `campaign_id` / `branch_id`: กติกา แคมเปญ และสาขาที่เกิดรายการ
- `source_table` / `source_record_id`: ชื่อตารางและ Primary Key ต้นทาง (เช่น `billing.payments`, `billing.invoices`, `billing.refund_requests`) เพื่อใช้ตรวจสอบแหล่งที่มาและป้องกันการเพิ่มคะแนนซ้ำ
- `invoice_id` / `payment_id` / `refund_request_id` / `loyalty_redemption_id`: จุดเชื่อมตรงไปยังใบแจ้งหนี้ รายการรับชำระ การคืนเงินใน Billing และรายการแลกคะแนน
- `expires_at` / `reason` / `performed_by` / `occurred_at` / `created_at`: วันหมดอายุคะแนน (กรณีได้รับคะแนน) เหตุผล ผู้ดำเนินการ วันเวลาเกิดรายการ และเวลาบันทึก

#### หมายเหตุ:

1. ตารางนี้เป็น Append-only Ledger ห้ามแก้ไขหรือลบแถวเดิม และต้องรักษาสมการ `balance_after = balance_before + points_delta >= 0`
2. กำหนด Partial UNIQUE Index บน `(transaction_type, source_table, source_record_id)` WHERE `source_table IS NOT NULL AND source_record_id IS NOT NULL` เพื่อป้องกันการเพิ่มคะแนนซ้ำจากธุรกรรม Billing เดียวกัน (กฎ §4.8)
3. สำหรับการสร้าง SQL DDL จริง ควรเพิ่ม FK `loyalty_redemption_id → crm.loyalty_redemptions` ด้วยคำสั่ง `ALTER TABLE` ภายหลัง

### ตาราง `crm.customer_value_snapshots`

**หน้าที่**: จัดเก็บข้อมูลสรุปการวิเคราะห์ความสัมพันธ์ พฤติกรรมการกลับมาใช้บริการ RFM และมูลค่าลูกค้าตลอดความสัมพันธ์ (Customer Lifetime Value — CLV) ตามช่วงเวลาและสาขา โดยอ้างอิงธุรกรรมจริงจาก Domain 07 รองรับการวิเคราะห์แยกทั้งระดับลูกค้า (`OWNER`) และระดับสัตว์เลี้ยง (`PET`) และแยกสถานะลูกค้าที่ห่างหายชั่วคราวออกจากการเลิกเป็นลูกค้าถาวรตามข้อ 4.20

#### โครงสร้าง Field:

| Column | Data Type | Constraint |
| --- | --- | --- |
| `snapshot_id` | UUID | PK, NOT NULL |
| `snapshot_scope` | ENUM | NOT NULL |
| `owner_id` | UUID | FK → owner.owners, NOT NULL |
| `pet_id` | UUID | FK → owner.pets, NULL |
| `branch_id` | UUID | FK → core.branches, NULL |
| `analysis_period_start` | DATE | NOT NULL |
| `analysis_period_end` | DATE | NOT NULL |
| `visit_count` | INTEGER | NOT NULL DEFAULT 0 |
| `realized_net_revenue_amount` | NUMERIC(14,2) | NOT NULL DEFAULT 0 |
| `realized_paid_amount` | NUMERIC(14,2) | NOT NULL DEFAULT 0 |
| `avg_revenue_per_visit` | NUMERIC(14,2) | NOT NULL DEFAULT 0 |
| `first_visit_date` | DATE | NULL |
| `last_visit_date` | DATE | NULL |
| `days_since_last_visit` | INTEGER | NULL |
| `avg_days_between_visits` | NUMERIC(8,2) | NULL |
| `rfm_recency_score` | SMALLINT | NULL |
| `rfm_frequency_score` | SMALLINT | NULL |
| `rfm_monetary_score` | SMALLINT | NULL |
| `clv_historical_amount` | NUMERIC(14,2) | NOT NULL DEFAULT 0 |

#### ข้อกำหนด:

- `snapshot_id`: รหัสประจำข้อมูลวิเคราะห์มูลค่าลูกค้า ใช้เป็น Primary Key
- `snapshot_scope`: ขอบเขตการวิเคราะห์ตามกฎข้อ 4.20 (`OWNER` วิเคราะห์รวมระดับลูกค้า 1 รายที่มีสัตว์หลายตัว, `PET` วิเคราะห์แยกเฉพาะสัตว์เลี้ยงแต่ละตัวโดยไม่ปะปนกัน)
- `owner_id` / `pet_id` / `branch_id`: ลูกค้า สัตว์เลี้ยง (บังคับเมื่อ `snapshot_scope = 'PET'`, เป็น `NULL` เมื่อ `OWNER`) และสาขาที่วิเคราะห์ (`NULL` = รวมทุกสาขา)
- `analysis_period_start` / `analysis_period_end`: ช่วงเวลาที่ใช้วิเคราะห์ตามกฎข้อ 4.20
- `visit_count` / `realized_net_revenue_amount` / `realized_paid_amount` / `avg_revenue_per_visit`: จำนวนครั้งที่ใช้บริการ ยอดรายได้จริงจาก `billing.invoices` ยอดชำระจริงจาก `billing.payments` (แยกยอดรายได้จากยอดกำไรตามกฎ §4.20) และค่าเฉลี่ยต่อครั้ง
- `first_visit_date` / `last_visit_date` / `days_since_last_visit` / `avg_days_between_visits`: วันที่มาครั้งแรกล่าสุด จำนวนวันที่ห่างจากครั้งล่าสุด และความถี่เฉลี่ยระหว่างการเข้าใช้บริการ
- `rfm_recency_score` / `rfm_frequency_score` / `rfm_monetary_score`: คะแนนวิเคราะห์ RFM (1–5)
- `clv_historical_amount` / `clv_projected_amount`: มูลค่าที่ลูกค้าสร้างจริงจนถึงปัจจุบัน และมูลค่าที่คาดการณ์ในอนาคต
- `lifecycle_activity_status`: สถานะกิจกรรมของความสัมพันธ์ (`NEW_CUSTOMER`, `ACTIVE_REGULAR`, `COOLING_AT_RISK`, `DORMANT_LAPSED` ห่างหายชั่วคราวยังไม่ถือว่าเลิกเป็นลูกค้าโดยอัตโนมัติ, `CHURNED_CONFIRMED`)
- `computed_at` / `created_at`: วันเวลาประมวลผลและเวลาบันทึก

#### หมายเหตุ:

1. กำหนด CHECK Constraint: เมื่อ `snapshot_scope = 'PET'` ต้องมี `pet_id IS NOT NULL` และเมื่อ `snapshot_scope = 'OWNER'` ต้องมี `pet_id IS NULL` (กฎ §4.20)
2. ตัวเลข `realized_net_revenue_amount` และ `realized_paid_amount` ต้องคำนวณจากข้อมูลธุรกรรมจริงใน Domain 07 (`billing`) เท่านั้น และไม่ถือว่า `DORMANT_LAPSED` เป็น `CHURNED_CONFIRMED` โดยอัตโนมัติ (กฎ §4.20)
