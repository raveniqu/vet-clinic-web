# Domain 03 — Clinical & Medical Management

เจ้าของข้อมูล: Domain 03

รับผิดชอบ

- ตรวจรักษาและเวชระเบียนทางการแพทย์ของสัตว์เลี้ยง
- เปิดรายการตรวจรักษา (Clinical Encounter)
- บันทึกประวัติการเจ็บป่วยที่เจ้าของแจ้ง
- ตรวจร่างกายและสัญญาณชีพ
- ประเมินและวินิจฉัยโรค
- บริหารรายการปัญหาสุขภาพระยะยาว
- วางแผนการรักษา
- สร้างคำสั่งทางการแพทย์และใบสั่งยา
- บันทึกการให้ยาจริงและหัตถการในห้องตรวจ
- วางแผนและบันทึกการให้วัคซีน ข้อมูลแพ้ยาและข้อควรระวัง
- การรับทราบคำเตือนทางคลินิก
- การรับทราบผลตรวจจากห้องปฏิบัติการและภาพวินิจฉัย
- การปรึกษาและส่งต่อผู้ป่วย
- การติดตามผล
- การจำหน่ายสัตว์กลับบ้าน
- การออกเอกสารทางการแพทย์
- การลงนามรับรองและบันทึกแก้ไขเวชระเบียนย้อนหลัง

Domain 03 เป็นเจ้าของข้อมูลการตัดสินใจทางการแพทย์ เวชระเบียน และคำสั่งทางการแพทย์ แต่ไม่สร้างข้อมูลลูกค้า สัตว์เลี้ยง นัดหมาย คลังยา ผลตรวจห้องปฏิบัติการ หรือการผ่าตัดซ้ำกับ Domain ที่เป็นเจ้าของข้อมูลหลัก (Single Source of Truth)

## กลุ่ม Clinical Encounter Management

### ตาราง `clinical.clinical_encounters`

**หน้าที่**: จัดเก็บข้อมูลหลักของเหตุการณ์การตรวจรักษาแต่ละครั้ง ตั้งแต่สัตว์เลี้ยงเข้าสู่กระบวนการตรวจจนกระทั่งสิ้นสุดและปิดรายการตรวจรักษา โดยแยกจากรายการนัดหมายและการลงทะเบียนเข้ารับบริการ แม้จะเป็นสัตว์เลี้ยงตัวเดิมที่กลับมารักษาหลายครั้งก็ต้องสร้างรายการตรวจรักษาใหม่ทุกครั้ง

#### โครงสร้าง Field:

| Column                    | Data Type   | Constraint                                   |
| ------------------------- | ----------- | -------------------------------------------- |
| `encounter_id`            | UUID        | PK, NOT NULL                                 |
| `encounter_number`        | VARCHAR(30) | UNIQUE, NOT NULL                             |
| `branch_id`               | UUID        | FK → core.branches, NOT NULL                 |
| `pet_id`                  | UUID        | FK → owner.pets, NOT NULL                    |
| `presenting_owner_id`     | UUID        | FK → owner.owners, NULL                      |
| `registration_id`         | UUID        | FK → appointment.service_registrations, NULL |
| `appointment_id`          | UUID        | FK → appointment.appointments, NULL          |
| `primary_veterinarian_id` | UUID        | FK → hr.employees, NOT NULL                  |
| `encounter_type`          | ENUM        | NOT NULL                                     |
| `is_emergency`            | BOOLEAN     | NOT NULL DEFAULT FALSE                       |
| `chief_complaint`         | TEXT        | NULL                                         |
| `started_at`              | TIMESTAMPTZ | NOT NULL                                     |
| `closed_at`               | TIMESTAMPTZ | NULL                                         |
| `closed_by`               | UUID        | FK → hr.employees, NULL                      |
| `closure_reason`          | TEXT        | NULL                                         |
| `cancellation_reason`     | TEXT        | NULL                                         |
| `encounter_status`        | ENUM        | NOT NULL                                     |
| `notes`                   | TEXT        | NULL                                         |
| `created_at`              | TIMESTAMPTZ | NOT NULL                                     |
| `created_by`              | UUID        | FK → hr.employees, NOT NULL                  |
| `updated_at`              | TIMESTAMPTZ | NULL                                         |
| `updated_by`              | UUID        | FK → hr.employees, NULL                      |

#### ข้อกำหนด:

- `encounter_id`: รหัสประจำรายการตรวจรักษาภายในระบบ ใช้เป็น Primary Key
- `encounter_number`: เลขที่รายการตรวจรักษาสำหรับอ้างอิงทางธุรกิจ กำหนดรูปแบบเป็น `ENC-{YYYY}{MM}{DD}-{NNNN}` โดยที่:
  - `{YYYY}{MM}{DD}` คือวันที่เริ่มตรวจรักษาตามปฏิทิน ค.ศ.
  - `{NNNN}` คือตัวเลขลำดับที่เพิ่มขึ้นอัตโนมัติในวันนั้น เช่น 0001 - 9999
- `branch_id`: รหัสสาขาที่ให้บริการตรวจรักษา อ้างอิงจาก `core.branches`
- `pet_id`: รหัสสัตว์เลี้ยงที่เข้ารับการตรวจรักษา อ้างอิงจาก `owner.pets`
- `presenting_owner_id`: รหัสเจ้าของหรือผู้เกี่ยวข้องที่พาสัตว์เลี้ยงมาเข้ารับบริการในครั้งนี้ อ้างอิงจาก `owner.owners` (สามารถเป็น `NULL` ได้ในกรณีฉุกเฉินเร่งด่วนที่ยังไม่สามารถระบุตัวตนเจ้าของได้ทันที แต่สัตว์เลี้ยงต้องถูกลงทะเบียนใน `owner.pets` แล้ว)
- `registration_id`: รหัสการลงทะเบียนเข้ารับบริการต้นทาง อ้างอิงจาก `appointment.service_registrations` สามารถเป็น `NULL` ได้ในกรณีที่มีการเปิด Encounter พิเศษที่ไม่ได้เริ่มผ่านขั้นตอน Registration ตามนโยบายคลินิก หรือกรณีฉุกเฉินที่ต้องช่วยเหลือทันทีแล้วเชื่อมโยงภายหลัง
- `appointment_id`: รหัสนัดหมายอ้างอิง (ถ้ามี) จาก `appointment.appointments` กรณี Walk-in ให้เป็น `NULL`
- `primary_veterinarian_id`: รหัสสัตวแพทย์ผู้รับผิดชอบหลักของการตรวจรักษาครั้งนี้ อ้างอิงจาก `hr.employees`
- `encounter_type`: ประเภทการตรวจรักษา ค่าที่เป็นไปได้ คือ
  - `GENERAL_CONSULTATION`: ตรวจรักษาและให้คำปรึกษาทั่วไป
  - `HEALTH_CHECK`: ตรวจสุขภาพประจำปีหรือตรวจคัดกรองสุขภาพ
  - `VACCINATION`: ตรวจประเมินและฉีดวัคซีน
  - `FOLLOW_UP`: ตรวจติดตามอาการหลังการรักษาหรือหลังผ่าตัด
  - `EMERGENCY`: ตรวจรักษาสัตว์ป่วยฉุกเฉิน
  - `PRE_SURGERY_EVAL`: ตรวจประเมินความพร้อมก่อนผ่าตัด
  - `DENTAL`: ตรวจและดูแลสุขภาพช่องปากและฟัน
  - `PROCEDURE`: การตรวจและทำหัตถการทางคลินิก
  - `OTHER`: การตรวจรักษาประเภทอื่น
- `is_emergency`: ระบุว่าเป็นการตรวจรักษาเร่งด่วน/ฉุกเฉินหรือไม่ (`TRUE`, `FALSE`) หากเป็น `TRUE` ระบบต้องอนุญาตให้บันทึกข้อมูลการช่วยชีวิตก่อนและเติมข้อมูลประกอบภายหลังได้
- `chief_complaint`: อาการสำคัญหรือเหตุผลหลักที่นำสัตว์เลี้ยงมาตรวจรักษาในครั้งนี้
- `started_at`: วันและเวลาที่เริ่มเปิดรายการตรวจรักษาจริง
- `closed_at`: วันและเวลาที่ปิดรายการตรวจรักษา
- `closed_by`: รหัสบุคลากรผู้ดำเนินการปิดรายการตรวจรักษา อ้างอิงจาก `hr.employees`
- `closure_reason`: เหตุผลหรือสรุปการปิดรายการตรวจรักษา
- `cancellation_reason`: เหตุผลในการยกเลิกรายการตรวจรักษา (ต้องระบุเมื่อ `encounter_status` เป็น `CANCELLED`)
- `encounter_status`: สถานะของรายการตรวจรักษา ค่าที่เป็นไปได้ คือ
  - `IN_PROGRESS`: อยู่ระหว่างการตรวจรักษาหรือบันทึกข้อมูลทางคลินิก
  - `WAITING_RESULTS`: รอผลตรวจเพิ่มเติม เช่น ผลเลือดหรือผลภาพวินิจฉัย
  - `READY_FOR_DISCHARGE`: ตรวจรักษาเสร็จสิ้น พร้อมสรุปผลและจำหน่ายสัตว์กลับ
  - `PENDING_SIGN_OFF`: รอสัตวแพทย์ตรวจสอบความครบถ้วนและลงนามรับรองเวชระเบียน
  - `CLOSED`: ปิดรายการตรวจรักษาเรียบร้อยแล้ว
  - `CANCELLED`: ยกเลิกรายการตรวจรักษาตามเงื่อนไข (เช่น เปิดรายการผิดตัว)
- `notes`: หมายเหตุทั่วไปของรายการตรวจรักษา
- `created_at`: วันและเวลาที่สร้างรายการ
- `created_by`: รหัสพนักงานผู้สร้างรายการ อ้างอิงจาก `hr.employees`
- `updated_at`: วันและเวลาที่แก้ไขล่าสุด
- `updated_by`: รหัสพนักงานผู้แก้ไขล่าสุด อ้างอิงจาก `hr.employees`

#### หมายเหตุ:

1. `encounter_number` ต้องไม่ซ้ำกันทั้งระบบ
2. สัตว์เลี้ยงหนึ่งตัวสามารถมีรายการตรวจรักษาได้หลายรายการ แต่ละครั้งที่กลับมารักษาหรือตรวจติดตามต้องสร้าง `encounter_id` ใหม่ ห้ามเขียนทับรายการเดิม
3. หากระบุ `presenting_owner_id` ต้องตรวจสอบความสัมพันธ์ตาม `owner.pet_ownerships` (`PRIMARY`, `CO_OWNER`, `CAREGIVER`, `AUTHORIZED_PERSON`) ที่ยัง `ACTIVE` อยู่ และตรวจสอบ `can_consent_treatment` เมื่อต้องขอความยินยอมทางการแพทย์
4. ต้องแยก `clinical_encounters` ออกจาก `appointment.appointments` และ `appointment.service_registrations` ไม่ใช้ `appointment_id` เป็น Primary Key ของเวชระเบียน
5. สถานะ `CLOSED` ของ Encounter แสดงถึงการสิ้นสุดกระบวนการทางคลินิก ไม่ได้หมายความว่าเจ้าของชำระเงินใน Domain Billing เสร็จสิ้นแล้ว
6. กรณี `encounter_status = 'CLOSED'` ต้องมี `closed_at` และ `closed_by` และกรณี `CANCELLED` ต้องมี `cancellation_reason`
7. ห้ามลบรายการตรวจรักษาที่มีข้อมูลทางการแพทย์เกิดขึ้นแล้ว ให้เปลี่ยนสถานะเป็น `CANCELLED` พร้อมบันทึกประวัติใน `clinical_encounter_status_histories`
8. การเปลี่ยนสถานะ `encounter_status` ทุกครั้งต้องบันทึกประวัติใน `clinical.clinical_encounter_status_histories` ภายใน Transaction เดียวกัน
9. หากระบุทั้ง `registration_id` และ `appointment_id` ค่า `appointment_id` ต้องสอดคล้องกับ `appointment.service_registrations.appointment_id` ของรายการลงทะเบียนนั้น และหากลงทะเบียนแบบ `WALK_IN` ค่า `appointment_id` ต้องเป็น `NULL`

### ตาราง `clinical.clinical_encounter_veterinarians`

**หน้าที่**: จัดเก็บรายชื่อสัตวแพทย์และบุคลากรทางการแพทย์ทั้งหมดที่เข้าร่วมในรายการตรวจรักษาหนึ่งครั้ง รองรับกรณีที่มีสัตวแพทย์มากกว่าหนึ่งคนร่วมตรวจ ปรึกษา หรือดูแลต่อเนื่องภายใน Encounter เดียวกัน

#### โครงสร้าง Field:

| Column                      | Data Type   | Constraint                                  |
| --------------------------- | ----------- | ------------------------------------------- |
| `encounter_veterinarian_id` | UUID        | PK, NOT NULL                                |
| `encounter_id`              | UUID        | FK → clinical.clinical_encounters, NOT NULL |
| `employee_id`               | UUID        | FK → hr.employees, NOT NULL                 |
| `role_type`                 | ENUM        | NOT NULL                                    |
| `joined_at`                 | TIMESTAMPTZ | NOT NULL                                    |
| `left_at`                   | TIMESTAMPTZ | NULL                                        |
| `notes`                     | TEXT        | NULL                                        |
| `created_at`                | TIMESTAMPTZ | NOT NULL                                    |
| `created_by`                | UUID        | FK → hr.employees, NOT NULL                 |

#### ข้อกำหนด:

- `encounter_veterinarian_id`: รหัสประจำรายการผู้ร่วมตรวจรักษา
- `encounter_id`: รายการตรวจรักษาที่เข้าร่วม อ้างอิงจาก `clinical.clinical_encounters`
- `employee_id`: รหัสสัตวแพทย์หรือบุคลากรทางการแพทย์ที่เข้าร่วม อ้างอิงจาก `hr.employees`
- `role_type`: บทบาทในการตรวจรักษาครั้งนี้ ค่าที่เป็นไปได้ คือ
  - `PRIMARY`: สัตวแพทย์ผู้รับผิดชอบหลัก
  - `CO_VETERINARIAN`: สัตวแพทย์ผู้ร่วมตรวจรักษา
  - `CONSULTANT`: สัตวแพทย์ผู้ให้คำปรึกษาเฉพาะทาง
  - `SUPERVISOR`: สัตวแพทย์ผู้ควบคุมดูแลหรือตรวจรับรอง
  - `ASSISTANT`: ผู้ช่วยสัตวแพทย์หรือพยาบาลสัตว์ที่ร่วมบันทึกข้อมูลตามสิทธิ์
- `joined_at`: วันและเวลาที่เริ่มเข้าร่วมดูแลในการตรวจรักษา
- `left_at`: วันและเวลาที่สิ้นสุดการเข้าร่วม (หากยังคงดูแลจนจบเป็น `NULL`)
- `notes`: หมายเหตุเกี่ยวกับขอบเขตการเข้าร่วม
- `created_at`: วันและเวลาที่สร้างข้อมูล
- `created_by`: ผู้บันทึกข้อมูล อ้างอิงจาก `hr.employees`

#### หมายเหตุ:

1. กำหนด Unique Constraint `(encounter_id, employee_id, role_type)` เพื่อป้องกันการเพิ่มบุคคลเดิมในบทบาทซ้ำภายใน Encounter เดียวกัน
2. ต้องมีผู้ที่มี `role_type = 'PRIMARY'` อย่างน้อยหนึ่งรายซึ่งสอดคล้องกับ `clinical_encounters.primary_veterinarian_id`
3. หากมีการเปลี่ยนสัตวแพทย์ผู้รับผิดชอบหลักระหว่างการรักษา ให้บันทึก `left_at` ของผู้เดิมและเพิ่มรายการใหม่โดยไม่ลบประวัติเดิม
4. `left_at` ต้องไม่ก่อน `joined_at`

### ตาราง `clinical.clinical_encounter_status_histories`

**หน้าที่**: จัดเก็บประวัติการเปลี่ยนแปลงสถานะของรายการตรวจรักษาตามลำดับเวลา เพื่อใช้ตรวจสอบย้อนหลังและวิเคราะห์ระยะเวลาการทำงานในแต่ละขั้นตอนทางคลินิก

#### โครงสร้าง Field:

| Column                        | Data Type   | Constraint                                  |
| ----------------------------- | ----------- | ------------------------------------------- |
| `encounter_status_history_id` | UUID        | PK, NOT NULL                                |
| `encounter_id`                | UUID        | FK → clinical.clinical_encounters, NOT NULL |
| `previous_status`             | ENUM        | NULL                                        |
| `new_status`                  | ENUM        | NOT NULL                                    |
| `changed_at`                  | TIMESTAMPTZ | NOT NULL                                    |
| `changed_by`                  | UUID        | FK → hr.employees, NULL                     |
| `change_reason`               | TEXT        | NULL                                        |
| `notes`                       | TEXT        | NULL                                        |
| `created_at`                  | TIMESTAMPTZ | NOT NULL                                    |

#### ข้อกำหนด:

- `encounter_status_history_id`: รหัสประจำประวัติการเปลี่ยนสถานะ
- `encounter_id`: รายการตรวจรักษาที่มีการเปลี่ยนสถานะ อ้างอิงจาก `clinical.clinical_encounters`
- `previous_status`: สถานะก่อนเปลี่ยนแปลง ใช้ชุดค่าเดียวกับ `clinical_encounters.encounter_status` (หากเป็นประวัติแรกเมื่อเปิด Encounter ให้เป็น `NULL`)
- `new_status`: สถานะใหม่หลังเปลี่ยนแปลง ใช้ชุดค่าเดียวกับ `clinical_encounters.encounter_status` ได้แก่ `IN_PROGRESS`, `WAITING_RESULTS`, `READY_FOR_DISCHARGE`, `PENDING_SIGN_OFF`, `CLOSED`, `CANCELLED`
- `changed_at`: วันและเวลาที่เปลี่ยนสถานะ
- `changed_by`: รหัสพนักงานผู้เปลี่ยนสถานะ อ้างอิงจาก `hr.employees` (กรณีระบบอัตโนมัติสามารถเป็น `NULL`)
- `change_reason`: เหตุผลในการเปลี่ยนสถานะ
- `notes`: หมายเหตุเพิ่มเติม
- `created_at`: วันและเวลาที่สร้างประวัติ

#### หมายเหตุ:

1. ตารางนี้เป็นข้อมูลแบบ Append-only ห้ามแก้ไขหรือลบประวัติเดิม
2. การปรับปรุง `clinical_encounters.encounter_status` และการเพิ่มแถวในตารางนี้ต้องเกิดใน Transaction เดียวกัน
3. ต้องกำหนด Transition Rule ที่เหมาะสม เช่น `IN_PROGRESS` → `WAITING_RESULTS` / `READY_FOR_DISCHARGE` / `PENDING_SIGN_OFF` / `CANCELLED` และไม่ให้เปลี่ยนจาก `CLOSED` หรือ `CANCELLED` กลับเป็น `IN_PROGRESS` โดยตรง (หากต้องแก้ไขข้อมูลหลังปิดต้องผ่านกระบวนการ Amendment)

- `encounter_service_id`: รหัสประจำรายการบริการในห้องตรวจ ใช้เป็น Primary Key
- `encounter_id`: รายการตรวจรักษาต้นทาง อ้างอิงจาก `clinical.clinical_encounters`
- `registration_service_id`: รายการบริการที่เลือกมาตั้งแต่จุดลงทะเบียน/Check-in อ้างอิง `appointment.registration_services` (เป็น `NULL` ได้กรณีแพทย์เพิ่มรายการบริการใหม่ระหว่างตรวจ)
- `service_catalog_id`: รหัสบริการมาตรฐาน อ้างอิง `core.service_catalogs`
- `service_name_snapshot`: ชื่อบริการ ณ วันที่ให้บริการ เพื่อป้องกันผลกระทบเมื่อแก้ไขชื่อใน Master Data
- `service_code_snapshot`: รหัสบริการ ณ วันที่ให้บริการ
- `performed_by`: สัตวแพทย์หรือบุคลากรผู้ให้บริการรายการนี้ อ้างอิง `hr.employees`
- `quantity`: จำนวนหน่วยบริการที่ดำเนินการจริง (ต้องมากกว่า 0)
- `performed_at`: วันและเวลาที่ให้บริการจริง
- `service_status`: สถานะการให้บริการ ค่าที่เป็นไปได้คือ

  - `COMPLETED`: ให้บริการเสร็จสิ้นแล้วและพร้อมส่งต่อคิดเงิน (หาก `is_billable = TRUE`)
  - `CANCELLED`: ยกเลิกบริการ
  - `WAIVED`: ยกเว้นการคิดค่าบริการ (เช่น แถมในแพ็กเกจหรือยกเว้นตามดุลพินิจ)
- `is_billable`: ระบุว่ารายการนี้ต้องนำไปเรียกเก็บค่าบริการใน Domain 07 (Billing) หรือไม่ (กรณี `WAIVED` หรือรายการที่คิดเงินรวมไว้ในหัตถการ/วัคซีนอื่นแล้ว ให้เป็น `FALSE`)
- `notes`: หมายเหตุเพิ่มเติมเกี่ยวกับบริการ
- `created_at`: วันและเวลาที่สร้างรายการ
- `created_by`: ผู้สร้างรายการ อ้างอิง `hr.employees`
- `updated_at`: วันและเวลาที่แก้ไขล่าสุด
- `updated_by`: ผู้แก้ไขล่าสุด อ้างอิง `hr.employees`

#### หมายเหตุ:

1. ตารางนี้ทำหน้าที่ปิดช่องว่างระหว่างการลงทะเบียนรับบริการใน Domain 02 (`appointment.registration_services`) กับการเรียกเก็บเงินใน Domain 07 สำหรับค่าบริการตรวจ OPD หรือบริการมาตรฐานที่ไม่ได้ออกใบสั่งยาหรือหัตถการแยก
2. หากบริการใดถูกดำเนินการและส่งคิดเงินผ่านตารางเฉพาะแล้ว (เช่น `clinical.procedure_records` หรือ `clinical.pet_vaccinations` หรือ `Domain 06`) ต้องกำหนดกฎไม่ให้คิดเงินซ้ำซ้อนกับ Domain 07 โดยระบุ `is_billable = FALSE` หรือใช้เป็นรายการอ้างอิงร่วมเพียงแหล่งเดียว
3. ไม่เก็บราคาขายหรือส่วนลดในตารางนี้ แต่ให้ Domain 07 ดึงราคาตามสาขาจาก `core.service_prices` ณ เวลาที่ออกใบแจ้งหนี้
4. `quantity` ต้องมากกว่า 0 และกรณี `WAIVED` ควรกำหนด `is_billable = FALSE`

## กลุ่ม Medical Record, History & Clinical Notes Management

### ตาราง `clinical.medical_records`

**หน้าที่**: จัดเก็บข้อมูลหัวเวชระเบียนประจำรายการตรวจรักษาแต่ละครั้ง ทำหน้าที่ควบคุมสถานะทางกฎหมาย/วิชาชีพของเวชระเบียน การล็อกข้อมูลหลังการรับรอง และการติดตามรอบการแก้ไขเพิ่มเติมหลังลงนาม

#### โครงสร้าง Field:

| Column              | Data Type   | Constraint                                          |
| ------------------- | ----------- | --------------------------------------------------- |
| `medical_record_id` | UUID        | PK, NOT NULL                                        |
| `encounter_id`      | UUID        | FK → clinical.clinical_encounters, UNIQUE, NOT NULL |
| `pet_id`            | UUID        | FK → owner.pets, NOT NULL                           |
| `record_number`     | VARCHAR(30) | UNIQUE, NOT NULL                                    |
| `record_status`     | ENUM        | NOT NULL                                            |
| `is_locked`         | BOOLEAN     | NOT NULL DEFAULT FALSE                              |
| `locked_at`         | TIMESTAMPTZ | NULL                                                |
| `first_signed_at`   | TIMESTAMPTZ | NULL                                                |
| `first_signed_by`   | UUID        | FK → hr.employees, NULL                             |
| `last_amended_at`   | TIMESTAMPTZ | NULL                                                |
| `last_amended_by`   | UUID        | FK → hr.employees, NULL                             |
| `created_at`        | TIMESTAMPTZ | NOT NULL                                            |
| `created_by`        | UUID        | FK → hr.employees, NOT NULL                         |
| `updated_at`        | TIMESTAMPTZ | NULL                                                |
| `updated_by`        | UUID        | FK → hr.employees, NULL                             |

#### ข้อกำหนด:

- `medical_record_id`: รหัสประจำเวชระเบียนหลัก ใช้เป็น Primary Key
- `encounter_id`: รายการตรวจรักษาที่เป็นเจ้าของเวชระเบียน อ้างอิงจาก `clinical.clinical_encounters` โดยกำหนดเป็น `UNIQUE` (1 Encounter ต่อ 1 Medical Record)
- `pet_id`: รหัสสัตว์เลี้ยงเจ้าของเวชระเบียน อ้างอิงจาก `owner.pets`
- `record_number`: เลขที่เวชระเบียน กำหนดรูปแบบเป็น `MR-{YYYY}{MM}{DD}-{NNNN}` โดยที่:
  - `{YYYY}{MM}{DD}` คือวันที่สร้างเวชระเบียนตามปฏิทิน ค.ศ.
  - `{NNNN}` คือตัวเลขลำดับที่เพิ่มขึ้นอัตโนมัติในวันนั้น เช่น 0001 - 9999
- `record_status`: สถานะของเวชระเบียน (แยกจาก `encounter_status`) ค่าที่เป็นไปได้ คือ
  - `DRAFT`: ฉบับร่าง อยู่ระหว่างบันทึกข้อมูลทางคลินิก ยังแก้ไขได้ตามสิทธิ์
  - `PENDING_REVIEW`: ส่งตรวจสอบเพื่อรอสัตวแพทย์ลงนามรับรอง
  - `SIGNED`: ได้รับการรับรองความถูกต้องโดยสัตวแพทย์แล้วและถูกล็อกไม่ให้แก้ทับ
  - `AMENDED`: มีการบันทึกแก้ไขเพิ่มเติมย้อนหลังผ่านกระบวนการ Amendment หลังการลงนาม
- `is_locked`: ระบุว่าเวชระเบียนถูกล็อกห้ามแก้ไขข้อมูลเดิมโดยตรงแล้วหรือไม่ (`TRUE` เมื่อ `record_status` เป็น `SIGNED` หรือ `AMENDED`)
- `locked_at`: วันและเวลาที่เวชระเบียนถูกล็อกครั้งแรก
- `first_signed_at`: วันและเวลาที่ลงนามรับรองเวชระเบียนครั้งแรก
- `first_signed_by`: รหัสสัตวแพทย์ผู้ลงนามรับรองครั้งแรก อ้างอิงจาก `hr.employees`
- `last_amended_at`: วันและเวลาที่มีการแก้ไขเพิ่มเติมครั้งล่าสุด
- `last_amended_by`: รหัสผู้ดำเนินการแก้ไขเพิ่มเติมครั้งล่าสุด อ้างอิงจาก `hr.employees`
- `created_at`: วันและเวลาที่สร้างเวชระเบียน
- `created_by`: ผู้สร้างเวชระเบียน อ้างอิงจาก `hr.employees`
- `updated_at`: วันและเวลาที่แก้ไขล่าสุด
- `updated_by`: ผู้แก้ไขล่าสุด อ้างอิงจาก `hr.employees`

#### หมายเหตุ:

1. `record_number` และ `encounter_id` ต้องไม่ซ้ำกัน และ `pet_id` ต้องตรงกับ `clinical_encounters.pet_id`
2. ต้องแยก `medical_records.record_status` ออกจาก `clinical_encounters.encounter_status` เพื่อรองรับกรณีจำหน่ายสัตว์กลับแล้วแต่สัตวแพทย์ยังไม่เซ็นรับรองเวชระเบียน หรือเซ็นรับรองแล้วแต่มีการเพิ่มเติมข้อมูลภายหลัง
3. เมื่อ `is_locked = TRUE` (`SIGNED` / `AMENDED`) ห้ามทำการ `UPDATE` หรือ `DELETE` ข้อมูลเดิมในตารางลูกของ Encounter โดยตรง การแก้ไขหรือเพิ่มเติมต้องทำผ่าน `clinical.medical_record_amendments` หรือการเพิ่มบันทึก `ADDENDUM` ใน `clinical.clinical_notes` เท่านั้น
4. ห้ามลบเวชระเบียนที่มีประวัติการตรวจรักษาออกจากฐานข้อมูลโดยพลการ

#### ข้อกำหนด:

- `medical_history_id`: รหัสประจำรายการประวัติการเจ็บป่วย
- `encounter_id`: รายการตรวจรักษาที่เกี่ยวข้อง อ้างอิงจาก `clinical.clinical_encounters`
- `pet_id`: สัตว์เลี้ยงที่เข้ารับการตรวจ อ้างอิงจาก `owner.pets`
- `chief_complaint`: อาการสำคัญหรือปัญหาหลักที่นำสัตว์มาพบสัตวแพทย์
- `symptom_onset_date`: วันที่เริ่มสังเกตพบอาการ (สามารถเป็น `NULL` ได้หากผู้ให้ข้อมูลไม่ทราบ)
- `symptom_duration_text`: ระยะเวลาที่มีอาการ เช่น 3 วัน, 2 สัปดาห์, ไม่ทราบแน่ชัด
- `symptom_description`: รายละเอียดลักษณะอาการที่เจ้าของสังเกตพบ เช่น อาเจียนเป็นน้ำสีเหลืองหลังกินอาหาร
- `symptom_frequency`: ความถี่ของการเกิดอาการ เช่น วันละ 3 ครั้ง, เป็นพัก ๆ
- `symptom_severity`: ระดับความรุนแรงตามข้อมูลที่ประเมิน ค่าที่เป็นไปได้ คือ
  - `MILD`: อาการเล็กน้อย
  - `MODERATE`: อาการปานกลาง
  - `SEVERE`: อาการรุนแรง
  - `CRITICAL`: อาการวิกฤต
  - `UNKNOWN`: ไม่ทราบหรือไม่สามารถประเมินได้จากข้อมูลที่มี
- `symptom_progression`: แนวโน้มการเปลี่ยนแปลงของอาการ ค่าที่เป็นไปได้ คือ
  - `IMPROVING`: อาการดีขึ้น
  - `STABLE`: อาการทรงตัว
  - `WORSENING`: อาการแย่ลง
  - `FLUCTUATING`: อาการขึ้น ๆ ลง ๆ

- `current_medications`: ยาหรืออาหารเสริมที่สัตว์เลี้ยงกำลังได้รับอยู่ในปัจจุบัน
- `diet_history`: ประวัติอาหาร พฤติกรรมการกิน การเปลี่ยนแปลงอาหารหรือน้ำ
- `elimination_history`: ประวัติการขับถ่ายปัสสาวะและอุจจาระ ลักษณะและความผิดปกติ
- `behavior_changes`: การเปลี่ยนแปลงพฤติกรรม เช่น ซึม ก้าวร้าว กระสับกระส่าย
- `data_source`: แหล่งที่มาของข้อมูลประวัติ ค่าที่เป็นไปได้ คือ
  - `OWNER_REPORTED`: เจ้าของหลักแจ้งข้อมูล
  - `CO_OWNER_REPORTED`: เจ้าของร่วมแจ้งข้อมูล
  - `CAREGIVER_REPORTED`: ผู้ดูแลหรือผู้พาสัตว์มาแจ้งข้อมูล
  - `PREVIOUS_CLINIC_RECORD`: ข้อมูลจากเวชระเบียนเดิมของคลินิก
  - `REFERRED_RECORD`: ข้อมูลจากเอกสารส่งต่อของสถานพยาบาลอื่น
  - `OTHER`: แหล่งข้อมูลอื่น
- `informant_owner_id`: รหัสลูกค้าผู้ให้ข้อมูล (กรณีมีทะเบียนใน `owner.owners`)
- `informant_name`: ชื่อผู้ให้ข้อมูล (กรณีผู้พามาไม่ใช่ลูกค้าที่ลงทะเบียนหรือเป็นข้อมูลจากบุคคลภายนอก)
- `informant_relationship`: ความสัมพันธ์ของผู้ให้ข้อมูลกับสัตว์เลี้ยง เช่น เจ้าของ, สมาชิกครอบครัว, พี่เลี้ยงสัตว์
- `is_copied_from_previous`: ระบุว่าข้อมูลบางส่วนถูกคัดลอกมาจากประวัติครั้งก่อนหรือไม่ (ต้องแสดงสถานะให้สัตวแพทย์ทบทวน ไม่ถือว่าเป็นข้อมูลใหม่ที่ยืนยันแล้วโดยอัตโนมัติ)
- `source_history_id`: อ้างอิง `medical_history_id` ต้นทางกรณีคัดลอกข้อมูลจากครั้งก่อนมาทบทวน
- `reported_at`: วันและเวลาที่ให้ข้อมูลประวัติ
- `recorded_by`: รหัสเจ้าหน้าที่หรือสัตวแพทย์ผู้ซักประวัติและบันทึกข้อมูล อ้างอิงจาก `hr.employees`
- `created_at`: วันและเวลาที่สร้างข้อมูล
- `updated_at`: วันและเวลาที่แก้ไขล่าสุด
- `updated_by`: ผู้แก้ไขล่าสุด อ้างอิงจาก `hr.employees`

#### หมายเหตุ:

1. ต้องแยกข้อมูลในตารางนี้ (ข้อมูลจากผู้ให้ข้อมูล) ออกจากการตรวจร่างกายและข้อวินิจฉัยของสัตวแพทย์ ไม่ถือว่าคำบอกเล่าของเจ้าของเป็นการวินิจฉัยโรค
2. ระบบต้องรองรับกรณีที่ผู้ให้ข้อมูลไม่ทราบรายละเอียดบางส่วน (เช่น `symptom_onset_date IS NULL` หรือ `UNKNOWN`)
3. หาก `is_copied_from_previous = TRUE` ระบบต้องระบุ `source_history_id` และต้องให้ผู้ปฏิบัติงานยืนยันข้อมูลปัจจุบันทุกครั้ง
4. เมื่อ `medical_records.is_locked = TRUE` ห้ามแก้ไขทับข้อมูลเดิม ต้องดำเนินการผ่าน `medical_record_amendments`

#### ข้อกำหนด:

- `clinical_note_id`: รหัสประจำบันทึกทางคลินิก
- `encounter_id`: รายการตรวจรักษาที่เกี่ยวข้อง อ้างอิงจาก `clinical.clinical_encounters`
- `medical_record_id`: เวชระเบียนต้นสังกัด อ้างอิงจาก `clinical.medical_records`
- `note_type`: ประเภทบันทึกทางคลินิก ค่าที่เป็นไปได้ คือ
  - `SOAP`: บันทึกโครงสร้างมาตรฐาน Subjective / Objective / Assessment / Plan
  - `INITIAL_ASSESSMENT`: บันทึกการประเมินอาการแรกรับ
  - `PROGRESS`: บันทึกติดตามความคืบหน้าอาการระหว่างการตรวจรักษา
  - `NURSING`: บันทึกการดูแลโดยผู้ช่วยสัตวแพทย์หรือพยาบาลสัตว์
  - `CONSULTATION`: บันทึกการปรึกษาความเห็นระหว่างสัตวแพทย์
  - `DISCHARGE`: บันทึกสรุปก่อนจำหน่ายสัตว์กลับบ้าน
  - `ADDENDUM`: บันทึกเพิ่มเติมภายหลังการรับรองเวชระเบียนโดยไม่เขียนทับบันทึกเดิม
  - `OTHER`: บันทึกทางคลินิกประเภทอื่น
- `note_title`: หัวข้อบันทึก (ถ้ามี)
- `subjective`: ข้อมูลอาการและประวัติที่ได้รับจากเจ้าของ (สำหรับบันทึกแบบ SOAP)
- `objective`: ข้อมูลจากการตรวจร่างกาย สัญญาณชีพ และผลตรวจประกอบ (สำหรับบันทึกแบบ SOAP)
- `assessment`: การประเมินปัญหาและข้อสรุปทางการแพทย์ (สำหรับบันทึกแบบ SOAP)
- `plan`: แผนการรักษา การให้ยา การตรวจเพิ่มเติม และการติดตามผล (สำหรับบันทึกแบบ SOAP)
- `note_content`: ข้อความบันทึกแบบอิสระ (ใช้สำหรับประเภทที่ไม่ใช่ SOAP หรือบันทึกเพิ่มเติมประกอบ)
- `note_status`: สถานะของบันทึก ค่าที่เป็นไปได้ คือ
  - `DRAFT`: ฉบับร่าง ยังสามารถแก้ไขได้ก่อนรับรอง
  - `FINALIZED`: บันทึกเสร็จสมบูรณ์และพร้อมส่งให้สัตวแพทย์ตรวจสอบ
  - `SIGNED`: ได้รับการรับรองแล้ว ห้ามแก้ไขทับโดยตรง
  - `SUPERSEDED`: ถูกแทนที่ด้วยบันทึกใหม่ตามขั้นตอนที่กำหนด (ยังเก็บข้อมูลเดิมไว้ตรวจสอบ)
- `parent_note_id`: อ้างอิง `clinical_note_id` เดิม กรณีบันทึกนี้เป็น `ADDENDUM` หรือบันทึกขยายความจากบันทึกก่อนหน้า
- `noted_at`: วันและเวลาทางคลินิกของเหตุการณ์ที่บันทึก
- `created_by`: รหัสผู้บันทึกข้อมูล อ้างอิงจาก `hr.employees`
- `created_at`: วันและเวลาที่สร้างบันทึก
- `updated_at`: วันและเวลาที่แก้ไขล่าสุด (เฉพาะขณะที่ยังไม่ `SIGNED`)
- `updated_by`: รหัสผู้แก้ไขล่าสุด อ้างอิงจาก `hr.employees`
- `signed_at`: วันและเวลาที่รับรองบันทึก
- `signed_by`: รหัสสัตวแพทย์ผู้รับรองบันทึก อ้างอิงจาก `hr.employees`

#### หมายเหตุ:

1. หนึ่ง Encounter สามารถมีบันทึกทางคลินิกได้หลายรายการ (เช่น มีทั้ง `SOAP`, `NURSING`, `PROGRESS` และ `ADDENDUM`)
2. บันทึกที่มี `note_status = 'SIGNED'` ห้ามแก้ไขหรือลบข้อมูลเดิม หากต้องเพิ่มเติมหรือแก้ไขหลังรับรองให้สร้างบันทึกประเภท `ADDENDUM` โดยอ้างอิง `parent_note_id` และ/หรือสร้างรายการใน `medical_record_amendments`
3. หาก `note_type = 'SOAP'` ต้องมีข้อมูลอย่างน้อยหนึ่งส่วนใน `subjective`, `objective`, `assessment`, `plan`
4. เมื่อเวชระเบียนหลักถูกล็อก (`medical_records.is_locked = TRUE`) อนุญาตให้เพิ่มเฉพาะบันทึกประเภท `ADDENDUM` พร้อมเหตุผลเท่านั้น

### ตาราง `clinical.clinical_attachments`

#### ข้อกำหนด:

- `attachment_id`: รหัสประจำไฟล์แนบทางคลินิก
- `encounter_id`: รายการตรวจรักษาต้นทาง อ้างอิงจาก `clinical.clinical_encounters`
- `pet_id`: รหัสสัตว์เลี้ยงเจ้าของไฟล์แนบ อ้างอิงจาก `owner.pets`
- `examination_id`: การตรวจร่างกายที่เกี่ยวข้อง (ถ้ามี) อ้างอิงจาก `clinical.physical_examinations`
- `clinical_note_id`: บันทึกทางคลินิกที่เกี่ยวข้อง (ถ้ามี) อ้างอิงจาก `clinical.clinical_notes`
- `diagnostic_result_review_id`: รายการรับทราบผลตรวจจากภายนอกที่เกี่ยวข้อง (ถ้ามี) อ้างอิงจาก `clinical.diagnostic_result_reviews`
- `attachment_type`: ประเภทของไฟล์แนบทางคลินิก ค่าที่เป็นไปได้ คือ
  - `CLINICAL_PHOTO`: ภาพถ่ายอาการหรือลักษณะภายนอกทั่วไป
  - `WOUND_PHOTO`: ภาพถ่ายบาดแผลเพื่อติดตามการหายของแผล
  - `SKIN_LESION`: ภาพถ่ายรอยโรคผิวหนัง
  - `EXTERNAL_LAB_RESULT`: เอกสารผลตรวจทางห้องปฏิบัติการจากสถานพยาบาลภายนอก
  - `EXTERNAL_IMAGING`: ภาพวินิจฉัยหรือรายงานภาพจากสถานพยาบาลภายนอก
  - `VIDEO`: วิดีโอประกอบอาการ (เช่น ท่าเดิน อาการชัก)
  - `DOCUMENT`: เอกสารประกอบการรักษาอื่น ๆ (เช่น สมุดวัคซีนเดิม ใบส่งตัวจากคลินิกอื่น)
  - `OTHER`: ไฟล์แนบประเภทอื่น
- `title`: ชื่อเรื่องหรือคำอธิบายสั้นของไฟล์แนบ
- `description`: รายละเอียดเพิ่มเติม เช่น ตำแหน่งแผล มุมกล้อง ข้อสังเกต
- `file_reference`: Path หรือ Object Key / URL ของไฟล์ใน Object Storage
- `file_name`: ชื่อไฟล์ต้นฉบับ
- `mime_type`: ชนิดไฟล์มาตรฐาน เช่น `image/jpeg`, `image/png`, `application/pdf`, `video/mp4`
- `file_size_bytes`: ขนาดไฟล์เป็นไบต์
- `captured_at`: วันและเวลาที่ถ่ายภาพหรือวันที่ของเอกสารต้นฉบับ
- `uploaded_by`: รหัสพนักงานผู้อัปโหลด อ้างอิงจาก `hr.employees`
- `uploaded_at`: วันและเวลาที่อัปโหลดเข้าระบบ
- `status`: สถานะไฟล์แนบ ค่าที่เป็นไปได้ คือ
  - `ACTIVE`: ใช้งานและแสดงในเวชระเบียน
  - `ARCHIVED`: จัดเก็บเข้าคลังข้อมูลเก่า
  - `VOIDED`: ยกเลิกการใช้งาน (เช่น อัปโหลดผิดตัว แต่ไม่ลบประวัติ)

#### หมายเหตุ:

1. ห้ามเก็บ Binary Data ของภาพหรือไฟล์ขนาดใหญ่ไว้ในคอลัมน์ฐานข้อมูลโดยตรง ให้เก็บเฉพาะ `file_reference` และ Metadata
2. ภาพวินิจฉัยที่ถ่ายจากเครื่องเอกซเรย์/อัลตราซาวด์ของคลินิกเอง ต้องเก็บใน `laboratory.medical_images` (Domain 05) ไม่นำมาสร้างซ้ำในตารางนี้ เว้นแต่เป็นไฟล์จากภายนอกที่นำเข้าประกอบเวชระเบียน
3. ไฟล์ที่อัปโหลดเข้าเวชระเบียนแล้วไม่ควรลบจริงเมื่อเกิดความผิดพลาด ให้เปลี่ยน `status` เป็น `VOIDED` เพื่อคงหลักฐานการตรวจสอบย้อนหลัง
4. สำหรับการสร้าง SQL DDL จริง ควรสร้างตาราง `clinical.physical_examinations` และ `clinical.diagnostic_result_reviews` ให้เสร็จก่อน หรือเพิ่ม Foreign Key Constraint ของ `examination_id` และ `diagnostic_result_review_id` ภายหลังด้วยคำสั่ง `ALTER TABLE` เนื่องจากตารางดังกล่าวนิยามไว้ในหมวดถัดไปของเอกสารนี้

## กลุ่ม Clinical Sign-off & Record Amendment Management

#### ข้อกำหนด:

- `sign_off_id`: รหัสประจำเหตุการณ์การลงนามรับรอง
- `medical_record_id`: เวชระเบียนที่ได้รับการตรวจสอบหรือลงนาม อ้างอิงจาก `clinical.medical_records`
- `encounter_id`: รายการตรวจรักษาที่เกี่ยวข้อง อ้างอิงจาก `clinical.clinical_encounters`

  - `INITIAL_SIGN_OFF`: การลงนามรับรองเวชระเบียนหลักครั้งแรกโดยสัตวแพทย์ผู้รับผิดชอบ
  - `CO_SIGN`: การลงนามร่วมของสัตวแพทย์ร่วมตรวจหรือผู้ตรวจร่วม
  - `SUPERVISOR_REVIEW`: การตรวจสอบและรับรองโดยสัตวแพทย์ผู้ควบคุมดูแลหรือผู้ตรวจสอบคุณภาพ
  - `AMENDMENT_SIGN_OFF`: การลงนามรับรองรายการแก้ไขเพิ่มเติมเวชระเบียนหลังปิดบันทึก
- `sign_off_status`: ผลการพิจารณาในการรับรอง ค่าที่เป็นไปได้ คือ
  - `APPROVED`: ผ่านการตรวจสอบและรับรองความถูกต้องครบถ้วน
  - `RETURNED_FOR_CORRECTION`: ส่งกลับให้ผู้บันทึกปรับปรุงข้อมูลที่ยังไม่ครบถ้วนก่อนรับรอง
  - `REJECTED`: ปฏิเสธการรับรองตามเงื่อนไข
- `signed_by`: รหัสสัตวแพทย์หรือผู้มีอำนาจลงนามรับรอง อ้างอิงจาก `hr.employees`
- `signed_at`: วันและเวลาที่ดำเนินการตรวจสอบ/ลงนาม
- `completeness_checked`: ระบุว่าระบบได้ผ่านการตรวจสอบความครบถ้วนของข้อมูลขั้นต่ำก่อนลงนามแล้วหรือไม่
- `missing_items_note`: รายการข้อมูลที่ยังไม่ครบถ้วน (เช่น กรณี `RETURNED_FOR_CORRECTION` หรือกรณีฉุกเฉินที่มีข้อยกเว้น)
- `review_notes`: ความเห็นประกอบการตรวจรับรอง
- `signature_reference`: ข้อมูลอ้างอิงลายมือชื่ออิเล็กทรอนิกส์หรือ Token ยืนยันตัวตน (ถ้ามี)
- `created_at`: วันและเวลาที่สร้างรายการ

#### หมายเหตุ:

1. ตารางนี้เป็นบันทึกเหตุการณ์แบบ Append-only ห้ามแก้ไขทับรายการรับรองเดิม
2. ผู้ที่มีสิทธิ์ลงนามรับรองใน `signed_by` ต้องเป็นสัตวแพทย์หรือผู้มีอำนาจหน้าที่ตามทะเบียนคุณสมบัติใน Domain 10 (`hr.employee_licenses`)
3. เมื่อมีรายการ `INITIAL_SIGN_OFF` ที่ `sign_off_status = 'APPROVED'` ระบบต้องอัปเดต `medical_records.record_status = 'SIGNED'`, `is_locked = TRUE` และบันทึก `first_signed_at` / `first_signed_by` ภายใน Transaction เดียวกัน
4. หาก `sign_off_status` เป็น `RETURNED_FOR_CORRECTION` หรือ `REJECTED` ต้องระบุ `missing_items_note` หรือ `review_notes`

  - `ADDITION`: เพิ่มเติมข้อมูลใหม่ที่ตกหล่นหรือเพิ่งได้รับเพิ่มเติมภายหลัง
  - `CLARIFICATION`: ชี้แจงหรือขยายความข้อมูลเดิมให้ชัดเจนขึ้น
  - `ERROR_MARKING`: ระบุว่าข้อมูลรายการเดิมบันทึกผิดพลาดเพื่อให้ระบบแสดงสถานะกำกับโดยไม่ลบทิ้ง
- `target_table`: ชื่อตารางใน Schema `clinical` ที่มีรายการถูกอ้างอิงแก้ไข เช่น `clinical_notes`, `diagnoses`, `medical_histories`, `vital_signs`

- `previous_values`: Snapshot ของค่าข้อมูลเดิมก่อนการแก้ไขในรูปแบบ JSON (กรณี `ADDITION` รายการใหม่สามารถเป็น `NULL`)
- `amended_values`: ค่าข้อมูลใหม่หรือข้อมูลที่เพิ่มเติมในรูปแบบ JSON
- `amendment_reason`: เหตุผลและความจำเป็นในการแก้ไขเพิ่มเติมหลังรับรองเวชระเบียน (บังคับระบุ)
- `requested_by`: รหัสบุคลากรผู้ยื่น/บันทึกการแก้ไขเพิ่มเติม อ้างอิงจาก `hr.employees`
- `amended_at`: วันและเวลาที่บันทึกคำขอแก้ไขเพิ่มเติม
- `approval_status`: สถานะการอนุมัติรายการแก้ไข ค่าที่เป็นไปได้ คือ
  - `PENDING_SIGN_OFF`: รอสัตวแพทย์ผู้มีอำนาจลงนามรับรองการแก้ไข
  - `APPROVED`: ได้รับการรับรองรายการแก้ไขเรียบร้อยแล้ว
  - `REJECTED`: ปฏิเสธรายการแก้ไข
- `approved_by`: รหัสสัตวแพทย์ผู้รับรองการแก้ไข อ้างอิงจาก `hr.employees`
- `approved_at`: วันและเวลาที่รับรองการแก้ไข
- `rejection_reason`: เหตุผลกรณีปฏิเสธคำขอแก้ไข
- `created_at`: วันและเวลาที่สร้างรายการ

#### หมายเหตุ:

1. กำหนด Unique Constraint `(medical_record_id, amendment_number)` เพื่อรักษาลำดับประวัติการแก้ไขที่ชัดเจน
2. ตารางนี้ต้องเป็น Append-only ห้ามลบหรือแก้ไขข้อมูลหลังอนุมัติแล้ว
3. สามารถสร้างรายการในตารางนี้ได้เฉพาะเมื่อ `medical_records.record_status` เป็น `SIGNED` หรือ `AMENDED` เท่านั้น (หากยังเป็น `DRAFT` ให้แก้ไขในตารางหลักตามปกติ)
4. เมื่อ `approval_status = 'APPROVED'` ระบบต้องอัปเดต `medical_records.record_status = 'AMENDED'`, `last_amended_at`, `last_amended_by` และบันทึกรายการ `AMENDMENT_SIGN_OFF` ใน `clinical.clinical_sign_offs`
5. การแสดงผลเวชระเบียนต้องแสดงทั้งข้อมูลฉบับรับรองเดิมและประวัติ `amendment` ควบคู่กัน เพื่อให้เห็นร่องรอยการแก้ไขอย่างโปร่งใส

- `encounter_id`: รายการตรวจรักษาที่เกี่ยวข้อง อ้างอิงจาก `clinical.clinical_encounters`
- `pet_id`: สัตว์เลี้ยงที่ได้รับการตรวจร่างกาย อ้างอิงจาก `owner.pets`

  - `OPHTHALMIC`: การตรวจเฉพาะทางตา
  - `NEUROLOGICAL`: การตรวจเฉพาะทางระบบประสาท
  - `ORTHOPEDIC`: การตรวจเฉพาะทางกระดูกและข้อ
  - `DENTAL`: การตรวจเฉพาะทางช่องปากและฟัน

- `examination_status`: สถานะของบันทึกการตรวจร่างกาย ค่าที่เป็นไปได้ คือ
  - `DRAFT`: ฉบับร่าง ยังอยู่ระหว่างตรวจหรือบันทึกข้อมูล
  - `FINALIZED`: ตรวจและบันทึกเสร็จสมบูรณ์แล้ว
- `examined_by`: รหัสสัตวแพทย์หรือผู้ได้รับมอบหมายผู้ดำเนินการตรวจ อ้างอิงจาก `hr.employees`

- `created_at`: วันและเวลาที่สร้างรายการ
- `updated_at`: วันและเวลาที่แก้ไขล่าสุด

#### ข้อกำหนด:

- `body_system`: ระบบร่างกายหรืออวัยวะที่ตรวจ ค่าที่เป็นไปได้ คือ
  - `GENERAL_APPEARANCE`: สภาพทั่วไปและความตื่นตัว
  - `INTEGUMENTARY`: ผิวหนัง ขน และต่อมข้างเคียง
  - `EYES`: ตาและการมองเห็น
  - `EARS`: หูและช่องหู
  - `ORAL_DENTAL`: ช่องปาก เหงือก และฟัน
  - `LYMPH_NODES`: ต่อมน้ำเหลือง
  - `CARDIOVASCULAR`: ระบบหัวใจและหลอดเลือด (เสียงหัวใจ ชีพจร)
  - `RESPIRATORY`: ระบบทางเดินหายใจ (เสียงปอด ทางเดินหายใจส่วนต้น)
  - `GASTROINTESTINAL`: ช่องท้องและระบบทางเดินอาหาร (การคลำช่องท้อง)
  - `UROGENITAL`: ระบบทางเดินปัสสาวะและระบบสืบพันธุ์

  - `NEUROLOGICAL`: ระบบประสาทและปฏิกิริยาตอบสนอง
  - `OTHER`: ระบบหรือบริเวณอื่น

  - `NORMAL`: ตรวจแล้วไม่พบความผิดปกติ
  - `ABNORMAL`: ตรวจพบความผิดปกติ (ต้องระบุรายละเอียดใน `finding_details`)
  - `NOT_EXAMINED`: ไม่ได้ทำการตรวจระบบนี้ในครั้งนี้
  - `UNABLE_TO_EXAMINE`: ไม่สามารถตรวจได้เนื่องจากข้อจำกัด (เช่น สัตว์ไม่ให้ความร่วมมือหรือมีความเจ็บปวด)
- `finding_details`: รายละเอียดสิ่งที่ตรวจพบ (เช่น พบเสียงหัวใจผิดปกติระดับ 3/6 หรือคลำพบก้อนในช่องท้อง)

- `notes`: หมายเหตุเพิ่มเติม
- `created_at`: วันและเวลาที่สร้างรายการ
- `updated_at`: วันและเวลาที่แก้ไขล่าสุด

#### หมายเหตุ:

1. กำหนด Unique Constraint `(examination_id, body_system)` เพื่อให้หนึ่งการตรวจมีรายการสรุปของแต่ละระบบร่างกายไม่ซ้ำกัน
2. ต้องรองรับค่า `NOT_EXAMINED` และ `UNABLE_TO_EXAMINE` เพื่อไม่ให้ระบบบังคับกรอกเป็นปกติทั้งหมดโดยไม่มีการตรวจจริง
3. หาก `finding_status = 'ABNORMAL'` ต้องระบุ `finding_details`

### ตาราง `clinical.vital_signs`

**หน้าที่**: จัดเก็บค่าสัญญาณชีพและค่าการตรวจวัดทางกายภาพตามช่วงเวลาที่เกิดขึ้นจริงระหว่างการตรวจรักษา โดยแยกค่าที่วัดได้จากอุปกรณ์/การกรอกด้วยมือ/ค่าคาดการณ์ และรองรับการติดตามแนวโน้มตลอดช่วงชีวิตของสัตว์เลี้ยง

#### โครงสร้าง Field:

| Column                  | Data Type     | Constraint                                  |
| ----------------------- | ------------- | ------------------------------------------- |
| `vital_sign_id`         | UUID          | PK, NOT NULL                                |
| `encounter_id`          | UUID          | FK → clinical.clinical_encounters, NOT NULL |
| `examination_id`        | UUID          | FK → clinical.physical_examinations, NULL   |
| `pet_id`                | UUID          | FK → owner.pets, NOT NULL                   |
| `measurement_type`      | ENUM          | NOT NULL                                    |
| `numeric_value`         | NUMERIC(12,3) | NULL                                        |
| `text_value`            | VARCHAR(255)  | NULL                                        |
| `unit`                  | VARCHAR(30)   | NULL                                        |
| `measurement_source`    | ENUM          | NOT NULL                                    |
| `triage_observation_id` | UUID          | FK → appointment.triage_observations, NULL  |
| `is_abnormal`           | BOOLEAN       | NULL                                        |
| `measured_at`           | TIMESTAMPTZ   | NOT NULL                                    |
| `measured_by`           | UUID          | FK → hr.employees, NOT NULL                 |
| `notes`                 | TEXT          | NULL                                        |
| `created_at`            | TIMESTAMPTZ   | NOT NULL                                    |

#### ข้อกำหนด:

- `vital_sign_id`: รหัสประจำรายการวัดสัญญาณชีพ
- `encounter_id`: รายการตรวจรักษาที่เกี่ยวข้อง อ้างอิงจาก `clinical.clinical_encounters`
- `examination_id`: รอบการตรวจร่างกายที่เกี่ยวข้อง (สามารถเป็น `NULL` ได้กรณีตรวจวัดสัญญาณชีพซ้ำแยกจากการตรวจร่างกายเต็มรูปแบบ) อ้างอิงจาก `clinical.physical_examinations`
- `pet_id`: สัตว์เลี้ยงที่ได้รับการตรวจวัด อ้างอิงจาก `owner.pets`
- `measurement_type`: ประเภทค่าที่ตรวจวัด ค่าที่เป็นไปได้ คือ
  - `BODY_TEMPERATURE`: อุณหภูมิร่างกาย (หน่วยมาตรฐาน `°C`)
  - `HEART_RATE`: อัตราการเต้นหัวใจ (หน่วยมาตรฐาน `bpm`)
  - `RESPIRATORY_RATE`: อัตราการหายใจ (หน่วยมาตรฐาน `breaths/min`)
  - `SYSTOLIC_BP`: ความดันโลหิตตัวบน (หน่วยมาตรฐาน `mmHg`)
  - `DIASTOLIC_BP`: ความดันโลหิตตัวล่าง (หน่วยมาตรฐาน `mmHg`)
  - `MEAN_ARTERIAL_BP`: ความดันโลหิตเฉลี่ย (หน่วยมาตรฐาน `mmHg`)
  - `SPO2`: ความอิ่มตัวของออกซิเจนในเลือด (หน่วยมาตรฐาน `%`)
  - `CAPILLARY_REFILL_TIME`: ระยะเวลาการคืนสีของเส้นเลือดฝอย (หน่วยมาตรฐาน `sec`)
  - `MUCOUS_MEMBRANE_COLOR`: สีและลักษณะของเยื่อเมือก (เช่น Pink & Moist, Pale, Cyanotic)
  - `HYDRATION_STATUS`: ระดับภาวะขาดน้ำ (เช่น Euhydrated, 5%, 8%)
  - `BODY_CONDITION_SCORE`: คะแนนประเมินสภาพร่างกาย (BCS เช่น 5/9)
  - `PAIN_SCORE`: คะแนนประเมินความเจ็บปวด
  - `CONSCIOUSNESS_LEVEL`: ระดับความรู้สึกตัว
  - `BODY_WEIGHT`: น้ำหนักตัวสัตว์เลี้ยง (หน่วยมาตรฐาน `kg`)
  - `BLOOD_GLUCOSE`: ระดับน้ำตาลในเลือดปลายนิ้ว/ข้างเตียง (หน่วยมาตรฐาน `mg/dL`)
  - `OTHER`: ค่าตรวจวัดทางกายภาพอื่น ๆ
- `numeric_value`: ค่าตัวเลขที่ตรวจวัดได้ (สำหรับค่าเชิงปริมาณ เช่น 38.6, 110, 12.500)
- `text_value`: ค่าข้อความที่สังเกตหรือประเมินได้ (สำหรับค่าเชิงคุณภาพ เช่น สีเยื่อเมือก ระดับความรู้สึกตัว)
- `unit`: หน่วยวัดของค่านั้น ๆ เช่น `°C`, `bpm`, `breaths/min`, `mmHg`, `%`, `sec`, `kg`, `/9`
- `measurement_source`: แหล่งที่มาของข้อมูลที่บันทึก ค่าที่เป็นไปได้ คือ
  - `MANUAL`: บุคลากรตรวจวัดและบันทึกด้วยตนเอง
  - `DEVICE`: ค่าที่วัดหรือนำเข้าจากเครื่องมือวัดทางการแพทย์
  - `ESTIMATED`: ค่าที่คาดการณ์หรือประมาณการ (ต้องแยกจากค่าที่วัดได้จริง)
  - `TRIAGE_IMPORTED`: ค่าที่อ้างอิง/นำเข้ามาจากกระบวนการคัดกรอง (Triage) ใน Domain 02
- `triage_observation_id`: อ้างอิง `appointment.triage_observations` กรณี `measurement_source = 'TRIAGE_IMPORTED'`
- `is_abnormal`: ระบุว่าค่านี้อยู่นอกเกณฑ์ปกติหรือไม่ (`TRUE`, `FALSE`, หรือ `NULL` หากยังไม่ประเมิน)
- `measured_at`: วันและเวลาที่ตรวจวัดจริง
- `measured_by`: รหัสพนักงานผู้ตรวจวัดหรือผู้บันทึก อ้างอิงจาก `hr.employees`
- `notes`: หมายเหตุเพิ่มเติม เช่น สัตว์ตื่นเต้นระหว่างวัดความดัน
- `created_at`: วันและเวลาที่สร้างรายการ

#### หมายเหตุ:

1. ต้องเก็บสัญญาณชีพและน้ำหนักแบบ Time-series ในตารางนี้ ห้ามเขียนทับค่าเดิมและห้ามเก็บไว้เพียงช่องเดียวใน `owner.pets`
2. หนึ่งแถวต้องกรอกค่าใน `numeric_value` หรือ `text_value` อย่างใดอย่างหนึ่งตามชนิดข้อมูล (กำหนด `CHECK` Constraint ป้องกันการเว้นว่างทั้งสองช่อง)
3. สำหรับ `measurement_type = 'BODY_WEIGHT'` ค่าที่บันทึกในตารางนี้ถือเป็นค่าที่วัดในทางคลินิกของ Encounter และให้ชั้น Application Sync ข้อมูลน้ำหนักไปยัง `owner.pet_weights` (Domain 01) เพื่อใช้เป็นประวัติกลางของสัตว์เลี้ยงโดยไม่สร้างความซ้ำซ้อนในการคำนวณ
4. ต้องไม่ใช้ข้อมูลใน `appointment.triage_observations` แทนที่สัญญาณชีพทางคลินิก หากนำมาใช้ต่อให้สร้างรายการในตารางนี้โดยระบุ `measurement_source = 'TRIAGE_IMPORTED'` และเชื่อม `triage_observation_id`

#### ข้อกำหนด:

- `diagnosis_catalog_id`: รหัสประจำรายการวินิจฉัยมาตรฐาน

- `species_group`: กลุ่มสัตว์ที่เกี่ยวข้อง ค่าที่เป็นไปได้ คือ `ALL`, `CANINE`, `FELINE`, `EXOTIC`
- `description`: คำอธิบายเพิ่มเติมของโรคหรือภาวะ
- `is_notifiable`: ระบุว่าเป็นโรคระบาดหรือโรคที่ต้องรายงานตามกฎหมายหรือไม่ (`TRUE`, `FALSE`)
- `is_active`: สถานะเปิดใช้งานในรายการเลือก (`TRUE`, `FALSE`)
- `created_at`: วันและเวลาที่สร้างข้อมูล
- `created_by`: ผู้สร้างข้อมูล อ้างอิงจาก `hr.employees`
- `updated_at`: วันและเวลาที่แก้ไขล่าสุด
- `updated_by`: ผู้แก้ไขล่าสุด อ้างอิงจาก `hr.employees`

#### หมายเหตุ:

1. `diagnosis_code` ต้องไม่ซ้ำกันทั้งตาราง
2. รายการที่มีการอ้างอิงใน `clinical.diagnoses` แล้วห้ามลบจริง ให้เปลี่ยน `is_active = FALSE` แทน
3. การเปลี่ยนชื่อโรคใน Catalog ต้องไม่ทำให้ข้อความวินิจฉัยเดิมใน `clinical.diagnoses` เปลี่ยนแปลงตาม

### ตาราง `clinical.diagnoses`

**หน้าที่**: จัดเก็บข้อประเมินและการวินิจฉัยโรคของสัตวแพทย์ที่เกิดขึ้นในการตรวจรักษาแต่ละครั้ง โดยรองรับทั้งการวินิจฉัยเบื้องต้น การวินิจฉัยแยกโรค การวินิจฉัยที่ยืนยันแล้ว การวินิจฉัยตามอาการ และภาวะแทรกซ้อน

#### โครงสร้าง Field:

| Column                    | Data Type    | Constraint                                  |
| ------------------------- | ------------ | ------------------------------------------- |
| `diagnosis_id`            | UUID         | PK, NOT NULL                                |
| `encounter_id`            | UUID         | FK → clinical.clinical_encounters, NOT NULL |
| `pet_id`                  | UUID         | FK → owner.pets, NOT NULL                   |
| `diagnosis_catalog_id`    | UUID         | FK → clinical.diagnosis_catalogs, NULL      |
| `diagnosis_code_snapshot` | VARCHAR(50)  | NULL                                        |
| `diagnosis_name`          | VARCHAR(200) | NOT NULL                                    |
| `diagnosis_type`          | ENUM         | NOT NULL                                    |
| `diagnostic_status`       | ENUM         | NOT NULL                                    |
| `confidence_level`        | ENUM         | NOT NULL                                    |
| `is_primary`              | BOOLEAN      | NOT NULL DEFAULT FALSE                      |
| `clinical_evidence`       | TEXT         | NULL                                        |
| `diagnosed_by`            | UUID         | FK → hr.employees, NOT NULL                 |
| `diagnosed_at`            | TIMESTAMPTZ  | NOT NULL                                    |
| `status_updated_at`       | TIMESTAMPTZ  | NULL                                        |
| `status_updated_by`       | UUID         | FK → hr.employees, NULL                     |
| `notes`                   | TEXT         | NULL                                        |
| `created_at`              | TIMESTAMPTZ  | NOT NULL                                    |
| `updated_at`              | TIMESTAMPTZ  | NULL                                        |

#### ข้อกำหนด:

- `diagnosis_id`: รหัสประจำรายการวินิจฉัย
- `encounter_id`: รายการตรวจรักษาที่เกิดการวินิจฉัย อ้างอิงจาก `clinical.clinical_encounters`
- `pet_id`: สัตว์เลี้ยงที่ได้รับการวินิจฉัย อ้างอิงจาก `owner.pets`
- `diagnosis_catalog_id`: อ้างอิงรายการโรคมาตรฐานจาก `clinical.diagnosis_catalogs` (สามารถเป็น `NULL` ได้กรณีสัตวแพทย์กรอกข้อวินิจฉัยตามอาการหรือยังไม่ตรงกับรหัสมาตรฐานในระบบ)
- `diagnosis_code_snapshot`: รหัสโรค ณ เวลาที่บันทึก (หากเลือกจาก Catalog)
- `diagnosis_name`: ชื่อโรค ภาวะ หรือข้อวินิจฉัยที่บันทึกจริง ณ เวลานั้น
- `diagnosis_type`: ประเภทของการวินิจฉัย ค่าที่เป็นไปได้ คือ
  - `PRELIMINARY`: การวินิจฉัยเบื้องต้น (Provisional/Working Diagnosis)
  - `DIFFERENTIAL`: การวินิจฉัยแยกโรค (รายการโรคที่ต้องพิจารณาเปรียบเทียบเพิ่มเติม)
  - `CONFIRMED`: การวินิจฉัยที่ยืนยันแล้ว
  - `SYMPTOMATIC`: การวินิจฉัยตามกลุ่มอาการ (เมื่อยังไม่ทราบสาเหตุเฉพาะ)
  - `CHRONIC`: การวินิจฉัยโรคประจำตัวที่เกี่ยวข้องกับการตรวจครั้งนี้
  - `COMPLICATION`: การวินิจฉัยภาวะแทรกซ้อนที่เกิดขึ้น
- `diagnostic_status`: สถานะความชัดเจนของการวินิจฉัย ค่าที่เป็นไปได้ คือ
  - `SUSPECTED`: สงสัยหรืออยู่ระหว่างรอผลตรวจยืนยัน
  - `CONFIRMED`: ยืนยันข้อวินิจฉัยแล้ว
  - `RULED_OUT`: ตัดออกจากการพิจารณาแล้ว (เช่น หลังผลแล็บออกแล้วพบว่าไม่ใช่)
  - `RESOLVED`: ภาวะหรือโรคในครั้งนี้หายหรือยุติแล้ว
- `confidence_level`: ระดับความมั่นใจตามการประเมินของสัตวแพทย์ ค่าที่เป็นไปได้ คือ `HIGH`, `MODERATE`, `LOW`, `UNDETERMINED`
- `is_primary`: ระบุว่าเป็นการวินิจฉัยหลักของ Encounter นี้หรือไม่ (`TRUE`, `FALSE`)
- `clinical_evidence`: เหตุผล ข้อมูลผลตรวจร่างกาย หรือผลตรวจห้องปฏิบัติการ/ภาพวินิจฉัยที่ใช้ประกอบการวินิจฉัย
- `diagnosed_by`: รหัสสัตวแพทย์ผู้วินิจฉัย อ้างอิงจาก `hr.employees`
- `diagnosed_at`: วันและเวลาที่บันทึกการวินิจฉัย
- `status_updated_at`: วันและเวลาที่ปรับสถานะการวินิจฉัยล่าสุด
- `status_updated_by`: ผู้ปรับสถานะการวินิจฉัยล่าสุด อ้างอิงจาก `hr.employees`
- `notes`: หมายเหตุเพิ่มเติม
- `created_at`: วันและเวลาที่สร้างรายการ
- `updated_at`: วันและเวลาที่แก้ไขล่าสุด

#### หมายเหตุ:

1. หนึ่ง Encounter สามารถมีรายการวินิจฉัยได้หลายรายการ (เช่น มี `PRELIMINARY` 1 รายการ และ `DIFFERENTIAL` หลายรายการ)
2. ต้องไม่บังคับให้ทุก Encounter ต้องมีรหัสโรคที่ยืนยันแล้ว (`diagnosis_catalog_id` เป็น `NULL` ได้ และ `diagnostic_status = 'SUSPECTED'` ได้)
3. ต้องแยกข้อมูลการวินิจฉัยในตารางนี้ออกจากคำบอกเล่าของเจ้าของใน `medical_histories` และแยกออกจากแผนการรักษาใน `treatment_plans`
4. การปรับเปลี่ยนสถานะหลังเวชระเบียนถูกรับรองแล้ว (`SIGNED`) ต้องทำผ่าน `medical_record_amendments` หรือเปิด Encounter ใหม่เมื่อสัตว์กลับมาตรวจครั้งถัดไป
5. ระบบต้องไม่สร้างหรือยืนยันข้อวินิจฉัยโรคโดยอัตโนมัติแทนสัตวแพทย์

### ตาราง `clinical.clinical_problem_lists`

**หน้าที่**: จัดเก็บรายการปัญหาสุขภาพระยะยาวของสัตว์เลี้ยงแต่ละตัว (Longitudinal Problem List) เพื่อให้สัตวแพทย์เห็นภาพรวมปัญหาที่กำลังดำเนินอยู่ ปัญหาที่ต้องเฝ้าระวัง หรือปัญหาที่ยุติแล้วอย่างต่อเนื่องข้ามการมารับบริการหลายครั้ง

#### โครงสร้าง Field:

| Column                        | Data Type    | Constraint                                 |

3. การเปลี่ยนสถานะเป็น `RESOLVED` ต้องระบุ `resolved_at` และ `resolution_reason` และห้ามลบประวัติปัญหาที่สิ้นสุดแล้วออกจากระบบ

### ตาราง `clinical.treatment_plans`

**หน้าที่**: จัดเก็บแผนการรักษาที่สัตวแพทย์กำหนดขึ้นจากการประเมินและวินิจฉัยโรค โดยแยกเป้าหมายและแนวทางการรักษาที่วางแผนไว้ออกจากรายการคำสั่งและการรักษาที่เกิดขึ้นจริง พร้อมรองรับการปรับแผนโดยเก็บประวัติเวอร์ชัน

#### ข้อกำหนด:

- `treatment_plan_id`: รหัสประจำแผนการรักษา

- `plan_name`: ชื่อแผนการรักษา

  - `IN_PROGRESS`: กำลังดำเนินการรักษาตามแผน
  - `COMPLETED`: ดำเนินการตามแผนครบถ้วนแล้ว
  - `SUPERSEDED`: ถูกแทนที่ด้วยแผนเวอร์ชันใหม่ (คงแผนเดิมไว้เป็นประวัติ)

- `encounter_id`: รายการตรวจรักษาต้นทาง อ้างอิงจาก `clinical.clinical_encounters`
- `pet_id`: สัตว์เลี้ยงที่ได้รับคำสั่ง อ้างอิงจาก `owner.pets`
- `treatment_plan_item_id`: รายการกิจกรรมในแผนการรักษาที่เป็นต้นทางของคำสั่ง (ถ้ามี) อ้างอิงจาก `clinical.treatment_plan_items`

  - `VACCINATION`: คำสั่งฉีดวัคซีน (เชื่อมกับ `vaccination_id`)

- `vaccination_id`: อ้างอิง `clinical.pet_vaccinations` (ใช้เมื่อ `order_type = 'VACCINATION'`)

  - `ORDERED`: ยืนยันคำสั่งแล้วและส่งต่อให้ผู้ปฏิบัติงานหรือ Domain ปลายทาง
  - `ACCEPTED`: หน่วยงานหรือผู้ปฏิบัติงานรับคำสั่งแล้ว
  - `IN_PROGRESS`: กำลังดำเนินการตามคำสั่ง
  - `COMPLETED`: ดำเนินการตามคำสั่งเสร็จสิ้น
  - `CANCELLED`: ยกเลิกคำสั่ง
  - `UNABLE_TO_PERFORM`: ไม่สามารถดำเนินการได้ (เช่น สัตว์ไม่ให้ความร่วมมือ หรือยาขาดสต็อก)

- `executed_at` / `executed_by`: วันเวลาและผู้ดำเนินการตามคำสั่งจริง

- `created_at`: วันและเวลาที่สร้างรายการ
- `updated_at`: วันและเวลาที่แก้ไขล่าสุด

#### หมายเหตุ:

1. ต้องกำหนด `CHECK` Constraint ให้มีคอลัมน์ปลายทางสอดคล้องกับ `order_type` และอนุญาตให้ระบุคอลัมน์ FK ปลายทางได้เพียงหนึ่งคอลัมน์ต่อหนึ่งแถว (ไม่ใช้ Polymorphic key แบบไม่มี FK ตรวจสอบ)
2. สำหรับ `FLUID_THERAPY`, `MONITORING`, `NURSING_CARE` และ `OTHER` คอลัมน์ FK ปลายทางทั้งหมดเป็น `NULL` ได้ และสามารถบันทึกผลการดูแลลงใน `execution_notes` หรือตาราง `clinical_notes` / `vital_signs`
3. ต้องแยกคำสั่งออกจากผลการดำเนินการจริง เช่น คำสั่ง `MEDICATION` ที่มี `order_status = 'ORDERED'` ไม่ได้หมายความว่าสัตว์ได้รับยาแล้ว
4. การยกเลิกคำสั่งต้องระบุ `cancellation_reason`, `cancelled_by`, `cancelled_at` และหากเป็นคำสั่งที่ส่งข้ามไป Domain 04, 05, 06 แล้วต้องแจ้งยกเลิกไปยังคำสั่งปลายทางด้วย

**หน้าที่**: จัดเก็บบันทึกการทำหัตถการขนาดเล็กที่สัตวแพทย์หรือผู้ช่วยดำเนินการทันทีภายในห้องตรวจ (OPD Procedures) เช่น การฉีดยา การล้างหู การทำแผลเล็กน้อย การให้สารน้ำใต้ผิวหนัง โดยอ้างอิงบริการจากทะเบียนกลางเพื่อส่งต่อไปคิดค่าบริการใน Billing ได้โดยตรง ส่วนการผ่าตัดและหัตถการซับซ้อนที่ต้องจองห้อง/วางแผน/วางยาสลบ ให้ส่งคำสั่งไปดำเนินการใน Domain 06 (Surgery & Treatment Management)

- `procedure_number`: เลขที่อ้างอิงหัตถการ กำหนดรูปแบบเป็น `PRC-{YYYY}{MM}{DD}-{NNNN}` โดยที่:
  - `{YYYY}{MM}{DD}` คือวันที่ทำหัตถการตามปฏิทิน ค.ศ.
  - `{NNNN}` คือตัวเลขลำดับที่เพิ่มขึ้นอัตโนมัติในวันนั้น เช่น 0001 - 9999
- `encounter_id`: รายการตรวจรักษาที่ทำหัตถการ อ้างอิงจาก `clinical.clinical_encounters`
- `pet_id`: สัตว์เลี้ยงที่รับหัตถการ อ้างอิงจาก `owner.pets`
- `branch_id`: สาขาที่ทำหัตถการ อ้างอิงจาก `core.branches`

- `procedure_category`: ประเภทหัตถการขนาดเล็กในห้องตรวจ ค่าที่เป็นไปได้ คือ
  - `INJECTION`: การฉีดยาเข้าใต้ผิวหนัง กล้ามเนื้อ หรือหลอดเลือดดำในห้องตรวจ
  - `WOUND_CARE`: การทำความสะอาดแผลหรือทำแผลขนาดเล็ก
  - `EAR_CARE`: การล้างหูหรือทำความสะอาดช่องหูทางการแพทย์
  - `FLUID_THERAPY`: การให้สารน้ำใต้ผิวหนังหรือสารน้ำเบื้องต้นในห้องตรวจ
  - `DRAINAGE`: การเจาะระบายหรือดูดของเหลวขนาดเล็กที่ไม่ต้องเข้าห้องผ่าตัด
  - `BANDAGING`: การพันแผลหรือเปลี่ยนผ้าพันแผล
  - `NAIL_CARE_MEDICAL`: การตัดเล็บหรือดูแลเล็บที่เกิดความผิดปกติทางการแพทย์
  - `SAMPLE_ASSIST`: หัตถการช่วยเก็บสิ่งส่งตรวจพิเศษ (เช่น Cystocentesis ในห้องตรวจ)
  - `OTHER`: หัตถการห้องตรวจประเภทอื่น
- `anatomical_site`: ตำแหน่งร่างกายที่ทำหัตถการ เช่น หูซ้าย, ขาหน้าขวา, ผิวหนังบริเวณหลัง
- `indication`: ข้อบ่งชี้ทางการแพทย์ในการทำหัตถการ
- `procedure_details`: รายละเอียดขั้นตอนและวิธีการที่ดำเนินการจริง
- `outcome_notes`: ผลลัพธ์และการตอบสนองของสัตว์หลังทำหัตถการ
- `performed_by`: ผู้ทำหัตถการจริง อ้างอิงจาก `hr.employees`
- `assisted_by`: ผู้ช่วยทำหัตถการ (ถ้ามี) อ้างอิงจาก `hr.employees`
- `performed_at`: วันและเวลาที่เริ่มทำหัตถการ
- `completed_at`: วันและเวลาที่ทำหัตถการเสร็จสิ้น
- `procedure_status`: สถานะของหัตถการ ค่าที่เป็นไปได้ คือ
  - `IN_PROGRESS`: กำลังดำเนินการ
  - `COMPLETED`: ดำเนินการเสร็จสิ้น (พร้อมส่งข้อมูลเรียกเก็บเงินไปยัง Domain 07 Billing ได้)
  - `ABORTED`: ยุติการทำหัตถการกลางคัน (เช่น สัตว์มีอาการผิดปกติระหว่างทำ)
  - `CANCELLED`: ยกเลิกรายการ
- `cancellation_reason`: เหตุผลกรณียุติหรือยกเลิกหัตถการ
- `created_at` / `created_by` / `updated_at` / `updated_by`: ข้อมูล Audit มาตรฐาน

#### หมายเหตุ:

1. ตารางนี้ใช้เฉพาะหัตถการห้องตรวจขนาดเล็ก (OPD) ห้ามนำการผ่าตัด การระงับความรู้สึกทั่วไป หรือหัตถการที่ต้องจัดสรรห้องผ่าตัดและทีมผ่าตัดมาบันทึกซ้ำในตารางนี้ (ต้องส่งไป Domain 06)
2. เมื่อ `procedure_status = 'COMPLETED'` ระบบ Billing (Domain 07) สามารถนำ `procedure_record_id` และ `service_catalog_id` ไปสร้าง `billing.invoice_items` ได้โดยอ้างอิง `source_domain = 'CLINICAL'`, `source_record_type = 'PROCEDURE_RECORD'`, `source_record_id = procedure_record_id`
3. หากมีการใช้ยาหรือเวชภัณฑ์ในหัตถการ การตัดสต็อกยา/วัสดุจริงต้องทำผ่านธุรกรรมของ Domain 04 (Pharmacy & Inventory)

#### ข้อกำหนด:

- `prescription_id`: รหัสประจำใบสั่งยา ใช้เป็น Primary Key
- `prescription_number`: เลขที่ใบสั่งยา กำหนดรูปแบบเป็น `RX-{YYYY}{MM}{DD}-{NNNN}` โดยที่:
  - `{YYYY}{MM}{DD}` คือวันที่สั่งยาตามปฏิทิน ค.ศ.
  - `{NNNN}` คือตัวเลขลำดับที่เพิ่มขึ้นอัตโนมัติในวันนั้น เช่น 0001 - 9999

  - `TAKE_HOME`: ยาสั่งกลับบ้าน (ส่งให้ Pharmacy จ่ายยาให้เจ้าของ)
  - `IN_CLINIC`: ยาสำหรับให้แก่สัตว์ภายในคลินิก (เช่น ยาฉีด สารน้ำ)
  - `MIXED`: ใบสั่งยารวมทั้งรายการยาให้ในคลินิกและยากลับบ้าน
- `prescribed_by`: รหัสสัตวแพทย์ผู้สั่งยา อ้างอิงจาก `hr.employees`
- `prescribed_at`: วันและเวลาที่ยืนยันคำสั่งยา

  - `DRAFT`: ร่างใบสั่งยา ยังไม่ได้ยืนยันส่ง
  - `ORDERED`: สัตวแพทย์ยืนยันคำสั่งยาแล้ว
  - `SENT_TO_PHARMACY`: ส่งคำสั่งยาไปยังระบบ Pharmacy (Domain 04) แล้ว

  - `CANCELLED`: ยกเลิกใบสั่งยา
  - `EXPIRED`: ใบสั่งยาหมดอายุตามนโยบายคลินิกก่อนมีการจ่ายยา
- `clinical_notes`: หมายเหตุทางคลินิกถึงห้องยาหรือผู้บริหารยา
- `cancellation_reason` / `cancelled_by` / `cancelled_at`: เหตุผล ผู้ยกเลิก และวันเวลาที่ยกเลิกใบสั่งยา
- `created_at` / `updated_at` / `updated_by`: ข้อมูล Audit มาตรฐาน

#### หมายเหตุ:

1. `prescription_number` ต้องไม่ซ้ำกัน
2. ผู้สั่งยา (`prescribed_by`) ต้องเป็นสัตวแพทย์ที่มีสิทธิ์และใบอนุญาตประกอบวิชาชีพที่ใช้งานอยู่ตามข้อมูลใน Domain 10
3. ใบสั่งยานี้เป็นคำสั่งทางการแพทย์ ไม่ถือว่าเกิดการจ่ายยาหรือการตัดสต็อกจนกว่าจะเกิดธุรกรรมใน `pharmacy.dispensings`
4. ต้องตรวจสอบประวัติการแพ้ยา (`pet_allergies`) และคำเตือน (`pet_medical_alerts`) ก่อนเปลี่ยนสถานะจาก `DRAFT` เป็น `ORDERED` / `SENT_TO_PHARMACY` และบันทึกการรับทราบคำเตือนใน `clinical_alert_acknowledgements` หากมีคำเตือนความเสี่ยงสูง
5. หากมีการจ่ายยาบางส่วนหรือครบแล้ว ห้ามลบหรือแก้ไขทับใบสั่งยาเดิมโดยไม่มีประวัติ

- `administration_setting`: ลักษณะการใช้ยารายการนี้ ค่าที่เป็นไปได้ คือ
  - `TAKE_HOME`: ให้เจ้าของนำกลับไปป้อนหรือใช้ที่บ้าน
  - `IN_CLINIC`: ให้ยาแก่สัตว์เลี้ยงภายในคลินิก (ต้องนำไปบันทึกการให้ยาจริงใน `medication_administration_records`)
- `pet_weight_kg_snapshot`: น้ำหนักสัตว์เลี้ยง (กก.) ที่ใช้อ้างอิงคำนวณขนาดยาในขณะสั่งยา
- `dose_per_kg`: ขนาดยาต่อกิโลกรัม (ถ้าคำนวณตามน้ำหนัก)
- `dose_amount`: ปริมาณยาต่อหนึ่งครั้งที่ให้ (ต้องมากกว่า 0)
- `dose_unit`: หน่วยของขนาดยาต่อครั้ง เช่น `mg`, `mL`, `tablet`, `drop`
- `route`: ช่องทางหรือวิธีการให้ยา ค่าที่เป็นไปได้ คือ `ORAL`, `SUBCUTANEOUS`, `INTRAMUSCULAR`, `INTRAVENOUS`, `TOPICAL`, `OPHTHALMIC`, `OTIC`, `INHALATION`, `RECTAL`, `OTHER`
- `frequency`: ความถี่ในการให้ยา เช่น `BID (วันละ 2 ครั้ง)`, `SID (วันละ 1 ครั้ง)`, `STAT (ครั้งเดียวทันที)`, `q12h`
- `duration_text`: ระยะเวลาการใช้ยา เช่น `7 วัน`, `14 วัน`, `Single dose`
- `prescribed_quantity`: จำนวนรวมที่สั่งจ่าย/เบิก (ต้องมากกว่า 0)
- `uom_id`: รหัสหน่วยนับมาตรฐานจากคลังยา อ้างอิง `pharmacy.units_of_measure` (Domain 04) เพื่อให้ห้องยาแปลงหน่วยตาม `pharmacy.product_units` ได้แม่นยำ
- `quantity_unit`: ชื่อ/Snapshot หน่วยของจำนวนที่สั่ง เช่น `tablet`, `capsule`, `mL`, `bottle`, `vial`
- `instructions`: คำแนะนำการใช้ยาสำหรับเจ้าของหรือผู้ให้ยา (ใช้พิมพ์บนฉลากยาของ Pharmacy ด้วย)
- `precautions`: ข้อควรระวังเฉพาะของรายการยานี้ เช่น ให้หลังอาหารทันที ห้ามบดเม็ดยา
- `item_status`: สถานะของรายการยา ค่าที่เป็นไปได้ คือ
  - `ORDERED`: สั่งยาแล้ว รอดำเนินการจ่าย
  - `PARTIALLY_DISPENSED`: จ่ายยาแล้วบางส่วน
  - `DISPENSED`: จ่ายยาครบตามจำนวนที่สั่งแล้ว
  - `CANCELLED`: ยกเลิกรายการยานี้
  - `UNABLE_TO_DISPENSE`: Pharmacy แจ้งว่าไม่สามารถจ่ายยาได้ (เช่น สินค้าหมดคลัง ต้องแจ้งกลับสัตวแพทย์พิจารณา)
- `cancellation_reason`: เหตุผลกรณียกเลิกรายการยา
- `created_at` / `updated_at`: วันและเวลาที่สร้างและแก้ไขล่าสุด

#### หมายเหตุ:

1. กำหนด Unique Constraint `(prescription_id, item_sequence)` และ Check Constraint `prescribed_quantity > 0` และ `dose_amount > 0`
2. ห้ามแก้ไขรายการยาที่มีการจ่ายยาใน `pharmacy.dispensing_items` ไปแล้วโดยไม่มีการสร้างคำสั่งเปลี่ยนแปลงหรือยกเลิกที่ตรวจสอบย้อนหลังได้
3. Pharmacy สามารถอ่านรายการนี้เพื่อจัดเตรียมและจ่ายยา แต่ห้ามเปลี่ยนแปลงขนาดยา วิธีใช้ หรือคำสั่งของสัตวแพทย์โดยพลการ

#### ข้อกำหนด:

- `administration_id`: รหัสประจำเหตุการณ์การให้ยาในคลินิก
- `encounter_id`: รายการตรวจรักษาที่ให้ยา อ้างอิงจาก `clinical.clinical_encounters`
- `pet_id`: สัตว์เลี้ยงที่ได้รับยา อ้างอิงจาก `owner.pets`
- `prescription_item_id`: รายการคำสั่งยาต้นทาง อ้างอิงจาก `clinical.prescription_items`
- `product_id`: รหัสยาที่ให้จริง อ้างอิงจาก `pharmacy.products`
- `dispensing_item_id`: อ้างอิงรายการจ่ายยาจากห้องยาใน `pharmacy.dispensing_items` (ถ้ามีการจ่ายยาจากคลังเพื่อนำมาให้สัตว์)
- `lot_id`: อ้างอิงล็อตยาที่นำมาใช้จริงจาก `pharmacy.inventory_lots` (เพื่อ Traceability หากเกิดอาการไม่พึงประสงค์)
- `administered_dose`: ปริมาณยาที่ให้แก่สัตว์จริง
- `dose_unit`: หน่วยของขนาดยาที่ให้จริง
- `route`: ช่องทางการให้ยาจริง ใช้ชุดค่าเดียวกับ `prescription_items.route`
- `administration_site`: ตำแหน่งที่ให้ยา (เช่น สะโพกซ้าย, ขาหน้าขวา IV catheter, ตาซ้าย)
- `scheduled_at`: เวลาที่กำหนดให้ยาตามคำสั่ง (ถ้ามี)
- `administered_at`: วันและเวลาที่ให้ยาแก่สัตว์จริง (บังคับเมื่อ `administration_status = 'ADMINISTERED'`)
- `administered_by`: รหัสบุคลากรผู้ให้ยาจริง อ้างอิงจาก `hr.employees`
- `witnessed_by`: รหัสผู้ตรวจสอบร่วม (กรณีการให้ยาควบคุมหรือยามีความเสี่ยงสูง) อ้างอิงจาก `hr.employees`
- `administration_status`: สถานะการให้ยาจริง ค่าที่เป็นไปได้ คือ
  - `SCHEDULED`: กำหนดตารางให้ยาไว้แล้ว รอถึงเวลาให้ยา
  - `ADMINISTERED`: ให้ยาแก่สัตว์เลี้ยงเรียบร้อยแล้ว
  - `HELD`: งดหรือชะลอการให้ยาตามการประเมินทางคลินิก (เช่น สัตว์มีอาการอาเจียนหรือความดันต่ำ)
  - `REFUSED`: ไม่สามารถให้ยาได้เนื่องจากสัตว์ต่อต้านรุนแรงหรือเจ้าของปฏิเสธ
  - `MISSED`: พลาดรอบเวลาการให้ยา
  - `CANCELLED`: ยกเลิกรายการให้ยา
- `patient_response`: การตอบสนองของสัตว์หลังได้รับยา (เช่น ไม่มีอาการแพ้เฉียบพลัน หรืออาการปวดลดลง)
- `hold_or_miss_reason`: เหตุผลกรณี `HELD`, `REFUSED` หรือ `MISSED`
- `notes`: หมายเหตุเพิ่มเติม
- `created_at` / `created_by` / `updated_at` / `updated_by`: ข้อมูล Audit มาตรฐาน

#### หมายเหตุ:

1. ตารางนี้บันทึกเฉพาะเหตุการณ์ทางคลินิกที่สัตว์ได้รับยาจริงในคลินิก การตัดสต็อกยาออกจากคลังเป็นหน้าที่ของ Domain 04 (`pharmacy.stock_movements` / `pharmacy.dispensings`) ไม่ตัดสต็อกจากตารางนี้โดยตรง
2. หาก `administration_status = 'ADMINISTERED'` ต้องระบุ `administered_at`, `administered_by` และ `administered_dose > 0`
3. หาก `administration_status` เป็น `HELD`, `REFUSED` หรือ `MISSED` ต้องระบุ `hold_or_miss_reason`
4. หากพบปฏิกิริยาไม่พึงประสงค์หลังให้ยา ต้องบันทึกเหตุการณ์ใน `clinical.adverse_events` โดยอ้างอิง `administration_id` นี้ได้

  - `PENDING_REVIEW`: ผลตรวจพร้อมแล้ว รอสัตวแพทย์เปิดดูและรับทราบ
  - `ACKNOWLEDGED`: สัตวแพทย์รับทราบผลตรวจแล้ว
  - `ACTION_REQUIRED`: สัตวแพทย์ประเมินแล้วว่าต้องปรับแผนการรักษาหรือแจ้งเจ้าของ
  - `ACTION_TAKEN`: ได้ดำเนินการตามผลตรวจแล้ว (เช่น ปรับยา นัดตรวจซ้ำ แจ้งเจ้าของ)
- `reviewed_by`: รหัสสัตวแพทย์ผู้ตรวจสอบและรับทราบผล อ้างอิงจาก `hr.employees`
- `reviewed_at`: วันและเวลาที่สัตวแพทย์รับทราบผลตรวจ
- `clinical_interpretation`: การแปลผลและความเห็นทางคลินิกของสัตวแพทย์เมื่อเทียบกับอาการของสัตว์
- `follow_up_action`: แนวทางดำเนินการต่อจากผลตรวจนี้
- `created_at` / `updated_at`: วันและเวลาที่สร้างและแก้ไขล่าสุด

#### หมายเหตุ:

1. ตารางคำสั่งตรวจจริง (`diagnostic_orders`) และผลตรวจฉบับเต็ม (`laboratory_results`, `laboratory_result_items`, `imaging_reports`) อยู่ใน Domain 05 (`laboratory`) ตารางนี้เก็บเฉพาะการรับทราบและความเห็นทางคลินิกของฝั่ง Domain 03
2. ต้องกำหนด `CHECK` Constraint ให้สอดคล้องกับ `source_type`:
   - `INTERNAL_LAB` ต้องมี `laboratory_result_id`
   - `INTERNAL_IMAGING` ต้องมี `imaging_report_id`
   - `EXTERNAL_FACILITY` ต้องมี `external_facility_name` และ `external_test_name`
3. ระบบแจ้งเตือนผลตรวจผิดปกติให้สัตวแพทย์ ต้องไม่ถือว่าการส่งแจ้งเตือนเท่ากับการรับทราบผลแล้ว จนกว่าสัตวแพทย์จะบันทึก `reviewed_by` และ `reviewed_at` ในตารางนี้

- `created_at` / `updated_at`: วันและเวลาที่สร้างและแก้ไขล่าสุด

3. เมื่อมี `fulfilled_vaccination_id` ต้องเปลี่ยน `plan_status = 'COMPLETED'`
4. ข้อมูลกำหนดนัดติดตามวัคซีนในตารางนี้สามารถส่งต่อไปใช้เตือนนัดหมายผ่าน CRM/Appointment ตามความยินยอมของเจ้าของได้ โดยเจ้าของข้อมูลหลักยังเป็น Domain 03

- `verification_status`: สถานะความน่าเชื่อถือของประวัติวัคซีน ค่าที่เป็นไปได้ คือ
  - `VERIFIED_IN_CLINIC`: ยืนยันจากการฉีดจริงในคลินิก
  - `DOCUMENT_VERIFIED`: ตรวจสอบจากสมุดวัคซีนหรือใบรับรองจากคลินิกอื่นแล้ว
  - `UNVERIFIED_OWNER_REPORT`: ข้อมูลตามคำบอกเล่า ยังไม่มีหลักฐานยืนยัน

- `notes`: หมายเหตุเพิ่มเติม
- `created_at` / `updated_at`: วันและเวลาที่สร้างและแก้ไขล่าสุด

#### หมายเหตุ:

1. ตารางนี้เป็น Single Source of Truth สำหรับประวัติวัคซีนของสัตว์เลี้ยง ไม่สร้างตารางประวัติวัคซีนซ้ำใน Domain 01 (`owner`)
2. กรณี `vaccination_source = 'IN_CLINIC'` ต้องระบุ `encounter_id`, `branch_id`, `product_id`, `lot_id` (เมื่อสินค้าควบคุมล็อต), `administered_by` และ `responsible_veterinarian_id`
3. ต้องห้ามใช้วัคซีนที่หมดอายุ (`expiry_date_snapshot < administered_date`) ในการฉีดวัคซีนจริงภายในคลินิก
4. กรณี `vaccination_source = 'EXTERNAL_CLINIC'` ต้องระบุ `external_clinic_name` และควรแนบภาพสมุดวัคซีนใน `clinical.clinical_attachments` หรือ `owner.pet_documents`
5. การออกใบรับรองวัคซีนให้บันทึกใน `clinical.medical_documents` (`document_type = 'VACCINATION_CERTIFICATE'`)
6. การตัดสต็อกวัคซีนที่ฉีดภายในคลินิก (`IN_CLINIC`) ต้องดำเนินการผ่าน Domain 04 (`pharmacy.dispensings` ประเภท `IN_CLINIC_USE` และ `pharmacy.stock_movements`) โดยไม่ตัดสต็อกจากตารางนี้โดยตรง

- `encounter_id`: รายการตรวจรักษาที่ตรวจพบหรือบันทึกประวัติการแพ้ (เป็น `NULL` ได้กรณีบันทึกรับข้อมูลเบื้องต้น) อ้างอิงจาก `clinical.clinical_encounters`
- `allergy_type`: ประเภทของการแพ้ ค่าที่เป็นไปได้ คือ
  - `MEDICATION`: การแพ้ยา
  - `VACCINE`: การแพ้วัคซีนหรือส่วนประกอบของวัคซีน
  - `FOOD`: การแพ้อาหารหรือส่วนประกอบอาหาร
  - `CHEMICAL`: การแพ้สารเคมี น้ำยาฆ่าเชื้อ หรือผลิตภัณฑ์ภายนอก
  - `ENVIRONMENTAL`: การแพ้สิ่งแวดล้อม (เช่น เกสร ไรฝุ่น)
  - `OTHER`: การแพ้สารอื่น ๆ
- `allergen_name`: ชื่อยา สาร อาหาร หรือสิ่งที่แพ้
- `product_id`: อ้างอิงรหัสสินค้ายา/วัคซีนใน `pharmacy.products` (ถ้าสามารถระบุตัวผลิตภัณฑ์ในคลังได้ เพื่อใช้ตรวจสอบอัตโนมัติขณะสั่งยาและจ่ายยา)
- `reaction_description`: อาการแพ้ที่พบ (เช่น ผื่นลมพิษ หน้าบวม อาเจียน หายใจลำบาก Anaphylaxis)
- `severity`: ระดับความรุนแรงของอาการแพ้ ค่าที่เป็นไปได้ คือ `MILD`, `MODERATE`, `SEVERE`, `LIFE_THREATENING`, `UNKNOWN`
- `data_source`: แหล่งที่มาของข้อมูลการแพ้ ค่าที่เป็นไปได้ คือ
  - `OWNER_REPORTED`: เจ้าของสัตว์แจ้งให้ทราบ
  - `CLINICIAN_OBSERVED`: สัตวแพทย์หรือบุคลากรตรวจพบอาการแพ้จริง
  - `TEST_CONFIRMED`: ยืนยันจากการทดสอบทางคลินิกหรือห้องปฏิบัติการ
  - `EXTERNAL_RECORD`: ข้อมูลจากเวชระเบียนหรือเอกสารของสถานพยาบาลอื่น
- `verification_status`: สถานะความน่าเชื่อถือของประวัติแพ้ ค่าที่เป็นไปได้ คือ
  - `SUSPECTED`: สงสัยว่าแพ้ ยังไม่ยืนยันแน่ชัด
  - `CONFIRMED`: ยืนยันแล้วว่ามีภาวะแพ้จริง
  - `REFUTED`: ตรวจสอบแล้วว่าไม่น่าจะแพ้สารนี้ (ห้ามลบประวัติเดิม ให้เปลี่ยนเป็นสถานะนี้แทน)
  - `RESOLVED`: ภาวะแพ้หรือข้อจำกัดนั้นยุติแล้ว (เช่น แพ้อาหารบางชนิดชั่วคราว)
- `identified_date`: วันที่เริ่มพบอาการแพ้
- `recorded_by`: ผู้บันทึกข้อมูล อ้างอิงจาก `hr.employees`
- `verified_by` / `verified_at`: สัตวแพทย์ผู้ตรวจสอบยืนยันหรือเปลี่ยนสถานะ และวันเวลาที่ยืนยัน
- `refuted_or_resolved_reason`: เหตุผลกรณีเปลี่ยนสถานะเป็น `REFUTED` หรือ `RESOLVED`
- `notes`: หมายเหตุเพิ่มเติม
- `created_at` / `updated_at` / `updated_by`: ข้อมูล Audit มาตรฐาน

#### หมายเหตุ:

1. ตารางนี้เป็น Single Source of Truth สำหรับประวัติการแพ้ของสัตว์เลี้ยง Domain 01 (`owner`) และ Domain 04 (`pharmacy`) ให้อ่านข้อมูลจากตารางนี้โดยตรง ไม่สร้างตารางประวัติแพ้ยาซ้ำ
2. ห้ามลบประวัติการแพ้ยาเดิมโดยไม่มีหลักฐาน หากพบว่าข้อมูลเดิมคลาดเคลื่อนให้เปลี่ยน `verification_status` เป็น `REFUTED` พร้อมบันทึก `refuted_or_resolved_reason` และ `verified_by`
3. ต้องแยกข้อมูลที่ `SUSPECTED` (หรือ `OWNER_REPORTED`) ออกจากข้อมูลที่ `CONFIRMED` ให้ชัดเจน

### ตาราง `clinical.pet_medical_alerts`

**หน้าที่**: จัดเก็บข้อมูลแจ้งเตือนและข้อควรระวังสำคัญของสัตว์เลี้ยงที่ต้องแสดงให้สัตวแพทย์และเจ้าหน้าที่เห็นในตำแหน่งที่เด่นชัดก่อนการตรวจ การจับบังคับ การสั่งยา หรือการทำหัตถการ (เช่น ดุร้าย กัด, ความเสี่ยงการวางยาสลบ, ข้อควรระวังในการใช้ยากลุ่ม NSAIDs)

| `deactivated_at`      | TIMESTAMPTZ  | NULL                                    |
| `deactivation_reason` | TEXT         | NULL                                    |

#### ข้อกำหนด:

- `medical_alert_id`: รหัสประจำข้อมูลแจ้งเตือนทางการแพทย์
- `pet_id`: สัตว์เลี้ยงที่เกี่ยวข้อง อ้างอิงจาก `owner.pets`
- `encounter_id`: รายการตรวจรักษาที่สร้างคำเตือนนี้ (ถ้ามี) อ้างอิงจาก `clinical.clinical_encounters`
- `alert_category`: หมวดหมู่ของคำเตือน ค่าที่เป็นไปได้ คือ
  - `ALLERGY`: คำเตือนจากการแพ้ยา/วัคซีน/สารเคมี
  - `CHRONIC_DISEASE`: คำเตือนจากโรคประจำตัวสำคัญ
  - `MEDICATION_PRECAUTION`: ข้อควรระวังหรือข้อห้ามในการใช้ยาบางกลุ่ม
  - `ANESTHESIA_RISK`: ความเสี่ยงสูงต่อการระงับความรู้สึกหรือวางยาสลบ
  - `HANDLING_BEHAVIOR`: ข้อควรระวังในการจับบังคับสัตว์ (เช่น ดุ กัด ข่วน เครียดง่าย)
  - `INFECTIOUS_RISK`: ความเสี่ยงโรคติดต่อที่ต้องแยกห้องตรวจหรือป้องกันการแพร่เชื้อ
  - `HIGH_RISK_PATIENT`: สัตว์ป่วยภาวะเสี่ยงสูงที่ต้องเฝ้าระวังเป็นพิเศษ
  - `OTHER`: ข้อควรระวังประเภทอื่น
- `alert_title`: หัวข้อคำเตือนแบบสั้นเพื่อแสดงเป็นป้ายเตือน (Badge/Banner)
- `alert_description`: คำอธิบายรายละเอียดความเสี่ยงและวิธีปฏิบัติที่แนะนำ
- `severity`: ระดับความสำคัญของคำเตือน ค่าที่เป็นไปได้ คือ `INFO`, `WARNING`, `HIGH`, `CRITICAL`
- `source_table` / `source_record_id`: ชื่อตารางและรหัสอ้างอิงต้นทาง (ถ้าสร้างต่อยอดจาก `pet_allergies`, `pet_chronic_conditions`, `adverse_events`)
- `is_active`: สถานะการแสดงคำเตือน (`TRUE` = แสดงเตือนอยู่, `FALSE` = ปิดคำเตือนแล้ว)
- `effective_from` / `effective_until`: ช่วงวันที่ที่คำเตือนมีผล
- `created_by` / `created_at`: ผู้สร้างและวันเวลาที่สร้างคำเตือน
- `deactivated_by` / `deactivated_at` / `deactivation_reason`: ผู้ปิดคำเตือน วันเวลา และเหตุผลเมื่อเปลี่ยน `is_active = FALSE`

#### หมายเหตุ:

1. ต้องแยกคำเตือนที่ยังใช้งาน (`is_active = TRUE`) กับคำเตือนที่ยกเลิกแล้วโดยห้ามลบประวัติคำเตือนเดิม
2. เมื่อปิดคำเตือน (`is_active = FALSE`) ต้องระบุ `deactivated_by`, `deactivated_at` และ `deactivation_reason`
3. ระบบแจ้งเตือนในตารางนี้เป็นเครื่องมือช่วยเตือนบุคลากรทางการแพทย์ ไม่ใช่เครื่องมือวินิจฉัยหรือสั่งการแทนสัตวแพทย์

- `adverse_event_number`: เลขที่รายงานเหตุการณ์ไม่พึงประสงค์ กำหนดรูปแบบเป็น `AE-{YYYY}{MM}{DD}-{NNNN}` โดยที่:

  - `FLUID_REACTION`: ปฏิกิริยาไม่พึงประสงค์จากการให้สารน้ำ
  - `CONTRAST_REACTION`: ปฏิกิริยาจากสารทึบรังสี
  - `OTHER`: เหตุการณ์ไม่พึงประสงค์ทางคลินิกประเภทอื่น
- `suspected_product_id` / `suspected_lot_id`: อ้างอิงยา/วัคซีนและล็อตสินค้าที่สงสัยว่าเป็นสาเหตุใน `pharmacy.products` และ `pharmacy.inventory_lots`
- `prescription_item_id` / `medication_administration_id` / `vaccination_id`: อ้างอิงรายการสั่งยา รายการให้ยา หรือรายการฉีดวัคซีนต้นทางที่เกี่ยวข้อง (ถ้ามี)
- `occurred_at`: วันและเวลาที่เกิดเหตุการณ์
- `onset_delay_minutes`: ระยะเวลาตั้งแต่ได้รับยา/วัคซีนจนเริ่มเกิดอาการ (นาที)
- `severity`: ระดับความรุนแรง ค่าที่เป็นไปได้ คือ `MILD`, `MODERATE`, `SEVERE`, `LIFE_THREATENING`, `FATAL`
- `symptoms_observed`: อาการผิดปกติที่ตรวจพบ
- `intervention_taken`: การช่วยเหลือหรือการรักษาที่ดำเนินการแก้ไขทันที
- `outcome`: ผลลัพธ์ของเหตุการณ์ ค่าที่เป็นไปได้ คือ `RECOVERED`, `RECOVERING`, `ONGOING`, `SEQUELAE`, `FATAL`, `UNKNOWN`
- `event_status`: สถานะการสอบสวน/ตรวจสอบเหตุการณ์ ค่าที่เป็นไปได้ คือ
  - `REPORTED`: บันทึกรายงานเหตุการณ์แล้ว รอตรวจสอบ
  - `UNDER_REVIEW`: อยู่ระหว่างทบทวนสาเหตุทางคลินิก
  - `CONFIRMED`: ยืนยันเหตุการณ์และสรุปสาเหตุแล้ว
  - `DISMISSED`: ตรวจสอบแล้วไม่เข้าข่ายเหตุการณ์ไม่พึงประสงค์จากการรักษา
- `reported_by`: พนักงานหรือสัตวแพทย์ผู้รายงาน อ้างอิงจาก `hr.employees`
- `reviewed_by` / `reviewed_at`: สัตวแพทย์หรือผู้รับผิดชอบที่ทบทวนเหตุการณ์ และวันเวลาที่ทบทวน
- `notes`: หมายเหตุเพิ่มเติม
- `created_at` / `updated_at`: วันและเวลาที่สร้างและแก้ไขล่าสุด

#### หมายเหตุ:

1. `adverse_event_number` ต้องไม่ซ้ำกัน
2. เหตุการณ์ที่บันทึกแล้วห้ามลบออกจากระบบ
3. หากเหตุการณ์เกี่ยวข้องกับล็อตวัคซีนหรือยา (`suspected_lot_id`) สามารถส่งข้อมูลให้ Pharmacy ตรวจสอบคุณภาพหรือกักกันล็อตที่มีปัญหาได้
4. หาก `event_category` เป็น `DRUG_REACTION` หรือ `VACCINE_REACTION` ที่ได้รับการยืนยัน ควรสร้างหรืออัปเดตข้อมูลใน `clinical.pet_allergies` และ `clinical.pet_medical_alerts` ควบคู่กัน
5. ภาวะแทรกซ้อนที่เกิดจากการผ่าตัดและยาสลบโดยตรงให้บันทึกใน `surgery.surgery_complications` (Domain 06)

### ตาราง `clinical.clinical_alert_acknowledgements`

**หน้าที่**: จัดเก็บประวัติการตอบสนองของสัตวแพทย์ต่อคำเตือนสนับสนุนการตัดสินใจทางคลินิก (Clinical Decision Support - CDS) เช่น คำเตือนแพ้ยา คำเตือนยาซ้ำซ้อน หรือผลแล็บค่าวิกฤต รวมถึงเหตุผลกรณีที่สัตวแพทย์ยืนยันดำเนินการต่อ (Override) เพื่อความโปร่งใสและตรวจสอบย้อนหลังได้

#### ข้อกำหนด:

- `acknowledgement_id`: รหัสประจำประวัติการตอบสนองคำเตือน
- `encounter_id`: รายการตรวจรักษาที่เกิดคำเตือน อ้างอิงจาก `clinical.clinical_encounters`
- `pet_id`: สัตว์เลี้ยงที่เกี่ยวข้อง อ้างอิงจาก `owner.pets`
- `alert_source_type`: ประเภทคำเตือนที่ระบบตรวจพบ ค่าที่เป็นไปได้ คือ
  - `ALLERGY_CONFLICT`: คำเตือนรายการยาที่อาจขัดแย้งกับประวัติแพ้ยา
  - `DUPLICATE_THERAPY`: คำเตือนคำสั่งยาซ้ำซ้อน
  - `CHRONIC_CONTRAINDICATION`: คำเตือนข้อควรระวังจากโรคประจำตัวของสัตว์
  - `ABNORMAL_LAB_CRITICAL`: คำเตือนผลตรวจห้องปฏิบัติการผิดปกติระดับวิกฤต
  - `MEDICAL_ALERT`: คำเตือนจาก `pet_medical_alerts`
  - `INCOMPLETE_ORDER`: คำเตือนข้อมูลคำสั่งยาหรือคำสั่งตรวจไม่ครบถ้วน
  - `OTHER`: คำเตือนทางคลินิกประเภทอื่น
- `pet_medical_alert_id` / `prescription_id` / `prescription_item_id` / `diagnostic_result_review_id`: รายการต้นทางที่ทำให้เกิดคำเตือน (ระบุเท่าที่เกี่ยวข้อง)
- `alert_severity`: ระดับความสำคัญของคำเตือน ค่าที่เป็นไปได้ คือ `INFO`, `WARNING`, `HIGH`, `CRITICAL`
- `alert_message`: ข้อความคำเตือนที่แสดงให้ผู้ปฏิบัติงานเห็น ณ เวลานั้น
- `action_taken`: การตอบสนองของสัตวแพทย์ต่อคำเตือน ค่าที่เป็นไปได้ คือ
  - `ACKNOWLEDGED`: รับทราบคำเตือนแล้ว
  - `MODIFIED_ORDER`: แก้ไขคำสั่งยาหรือแผนการรักษาตามคำเตือน
  - `CANCELLED_ORDER`: ยกเลิกคำสั่งที่เป็นความเสี่ยง
  - `OVERRIDDEN`: ยืนยันดำเนินการต่อแม้มีคำเตือน (ต้องระบุเหตุผลใน `override_reason`)
- `override_reason`: เหตุผลทางคลินิกที่สัตวแพทย์เลือกดำเนินการต่อแม้มีคำเตือน
- `acknowledged_by`: รหัสสัตวแพทย์ผู้รับทราบหรือตัดสินใจ อ้างอิงจาก `hr.employees`
- `acknowledged_at`: วันและเวลาที่ตอบสนองต่อคำเตือน
- `created_at`: วันและเวลาที่สร้างรายการ

#### หมายเหตุ:

1. ตารางนี้เป็นข้อมูลแบบ Append-only ห้ามแก้ไขหรือลบประวัติการรับทราบคำเตือน
2. หาก `action_taken = 'OVERRIDDEN'` และ `alert_severity` เป็น `HIGH` หรือ `CRITICAL` ต้องบังคับกรอก `override_reason`
3. คำเตือนของระบบต้องมีแหล่งข้อมูลรองรับเสมอ และต้องไม่ตัดสินใจแทนสัตวแพทย์

- `consultation_id`: รหัสประจำรายการปรึกษาทางการแพทย์
- `encounter_id`: รายการตรวจรักษาที่ขอคำปรึกษา อ้างอิงจาก `clinical.clinical_encounters`

- `external_consultant_name` / `external_consultant_specialty`: ชื่อและความเชี่ยวชาญของที่ปรึกษาภายนอก (กรณีไม่มี `consultant_employee_id`)
- `consultation_type`: ประเภทการปรึกษา ค่าที่เป็นไปได้ คือ
  - `INTERNAL_SECOND_OPINION`: ขอความเห็นที่สองจากสัตวแพทย์ในคลินิก
  - `SPECIALIST_REVIEW`: ปรึกษาสัตวแพทย์เฉพาะทางภายในองค์กร
  - `CASE_CONFERENCE`: การประชุมปรึกษาร่วมกันหลายฝ่าย
  - `EXTERNAL_EXPERT`: ปรึกษาผู้เชี่ยวชาญภายนอกโดยไม่ได้ส่งตัวสัตว์ไปรักษาต่อ
- `urgency_level`: ระดับความเร่งด่วน ค่าที่เป็นไปได้ คือ `ROUTINE`, `URGENT`, `EMERGENCY`
- `clinical_question`: คำถามหรือประเด็นทางคลินิกที่ต้องการคำปรึกษา
- `clinical_summary`: สรุปอาการและผลตรวจที่ส่งให้ผู้ให้คำปรึกษาพิจารณา
- `consultation_response`: ความเห็นทางการแพทย์ที่ผู้ให้คำปรึกษาตอบกลับ
- `recommendations`: ข้อเสนอแนะในการตรวจเพิ่มเติมหรือแนวทางการรักษา
- `consultation_status`: สถานะการปรึกษา ค่าที่เป็นไปได้ คือ
  - `REQUESTED`: ส่งคำขอปรึกษาแล้ว รอการตอบรับ
  - `IN_REVIEW`: ผู้ให้คำปรึกษากำลังพิจารณาข้อมูล
  - `RESPONDED`: ผู้ให้คำปรึกษาบันทึกความเห็นตอบกลับแล้ว
  - `CLOSED`: ผู้ขอปรึกษารับทราบความเห็นและปิดรายการปรึกษาแล้ว
  - `CANCELLED`: ยกเลิกคำขอปรึกษา
- `requested_at` / `responded_at` / `closed_at`: วันและเวลาในแต่ละขั้นตอน
- `cancellation_reason`: เหตุผลกรณียกเลิกคำขอปรึกษา
- `created_at` / `updated_at`: วันและเวลาที่สร้างและแก้ไขล่าสุด

#### หมายเหตุ:

1. ต้องระบุผู้ให้คำปรึกษาอย่างน้อยหนึ่งทางระหว่าง `consultant_employee_id` หรือ `external_consultant_name`
2. หากสัตวแพทย์ที่ปรึกษาภายในเข้าร่วมตรวจร่างกายหรือบันทึกเวชระเบียนใน Encounter ด้วย ให้เพิ่มใน `clinical.clinical_encounter_veterinarians`
3. การปรึกษาไม่ทำให้ `clinical_encounters` ถูกปิดโดยอัตโนมัติ

- `destination_department` / `destination_veterinarian_name` / `destination_contact_phone` / `destination_email` / `destination_address`: รายละเอียดหน่วยงาน แพทย์ปลายทาง และข้อมูลติดต่อสถานพยาบาลปลายทาง
- `referral_reason`: เหตุผลและความจำเป็นในการส่งต่อ
- `clinical_summary` / `diagnosis_summary` / `treatments_given`: สรุปอาการ ผลวินิจฉัย และการรักษาที่คลินิกได้ดำเนินการไปแล้ว
- `owner_consent_obtained`: ยืนยันการยินยอมและสิทธิ์ในการส่งต่อข้อมูลแก่สถานพยาบาลภายนอก (เชื่อมโยงหลักการ PDPA และสิทธิ์เจ้าของ)
- `consent_notes`: หมายเหตุเกี่ยวกับการส่งมอบเอกสารหรือความยินยอมของเจ้าของ
- `referred_by`: สัตวแพทย์ผู้ส่งต่อ อ้างอิงจาก `hr.employees`
- `referred_at`: วันและเวลาที่สร้างรายการส่งต่อ
- `referral_status`: สถานะการส่งต่อ ค่าที่เป็นไปได้ คือ
  - `DRAFT`: ร่างข้อมูลการส่งต่อ
  - `ISSUED`: ออกใบส่งต่อเรียบร้อยแล้ว
  - `SENT`: ส่งต่อข้อมูลหรือเอกสารไปยังสถานพยาบาลปลายทางแล้ว
  - `ACCEPTED_BY_FACILITY`: สถานพยาบาลปลายทางตอบรับผู้ป่วยแล้ว
  - `COMPLETED`: กระบวนการส่งต่อเสร็จสมบูรณ์
  - `FEEDBACK_RECEIVED`: ได้รับผลตอบกลับการรักษาจากสถานพยาบาลปลายทางแล้ว
  - `CANCELLED`: ยกเลิกการส่งต่อ
- `feedback_summary` / `feedback_received_at`: สรุปผลตอบกลับจากสถานพยาบาลปลายทางและวันที่ได้รับผล
- `cancellation_reason`: เหตุผลกรณียกเลิกการส่งต่อ
- `created_at` / `updated_at` / `updated_by`: ข้อมูล Audit มาตรฐาน

#### หมายเหตุ:

1. `referral_number` ต้องไม่ซ้ำกัน
2. การส่งข้อมูลเวชระเบียนและผลตรวจให้สถานพยาบาลภายนอกต้องตรวจสอบความยินยอมหรือฐานกฎหมายที่เกี่ยวข้องก่อนดำเนินการ
3. เอกสารใบส่งตัวฉบับพิมพ์/PDF ให้จัดเก็บใน `clinical.medical_documents` (`document_type = 'REFERRAL_LETTER'`)
4. ต้องแยกสถานะการส่งต่อออกจากสถานะการปิดรายการตรวจรักษา (`clinical_encounters.encounter_status`)

  - `PHONE_CALL`: ติดตามอาการทางโทรศัพท์
  - `LINE_OA`: ติดตามอาการผ่าน LINE Official Account
  - `VIDEO_CALL`: ติดตามผ่านวิดีโอคอล
  - `OTHER`: ช่องทางอื่น
- `due_date`: วันที่กำหนดให้ติดตามผล

- `linked_appointment_id`: อ้างอิงนัดหมายใน `appointment.appointments` (Domain 02) หากเจ้าของจองนัดติดตามผลแล้ว
- `next_encounter_id`: อ้างอิงรายการตรวจรักษาครั้งใหม่ใน `clinical.clinical_encounters` เมื่อสัตว์เลี้ยงกลับมาตรวจร่างกายจริงตามนัดติดตามนี้

  - `SCHEDULED`: กำหนดวันติดตามผลไว้แล้ว รอถึงกำหนด
  - `REMINDED`: แจ้งเตือนหรือติดต่อเจ้าของแล้ว รอการตอบรับ/เข้ารับบริการ
  - `COMPLETED`: ดำเนินการติดตามผลเรียบร้อยแล้ว
  - `UNABLE_TO_REACH`: ไม่สามารถติดต่อเจ้าของสัตว์ได้
  - `MISSED`: เลยกำหนดติดตามและเจ้าของไม่พาสัตว์มาตามกำหนด
  - `RESCHEDULED`: เลื่อนกำหนดการติดตามผล
  - `CANCELLED`: ยกเลิกการติดตามผล
- `completed_at` / `completed_by`: วันเวลาและผู้บันทึกผลการติดตามจริง
- `follow_up_outcome`: ผลการติดตามหรืออาการที่เจ้าของแจ้ง/ตรวจพบ
- `next_action`: แนวทางดำเนินการต่อหลังทราบผลการติดตาม
- `notes`: หมายเหตุเพิ่มเติม
- `created_at` / `created_by` / `updated_at` / `updated_by`: ข้อมูล Audit มาตรฐาน

2. หาก `follow_up_method = 'IN_CLINIC_VISIT'` และเจ้าของนำสัตว์กลับมาตรวจจริง ระบบต้องสร้าง `clinical_encounters` รายการใหม่และผูกกับ `next_encounter_id` ห้ามนำข้อมูล Encounter เดิมมาเขียนทับ
3. กรณีติดต่อเจ้าของไม่ได้ให้บันทึก `follow_up_status = 'UNABLE_TO_REACH'` เพื่อเก็บประวัติความพยายามติดตาม

#### ข้อกำหนด:

- `medical_document_id`: รหัสประจำเอกสารทางการแพทย์ ใช้เป็น Primary Key
- `document_number`: เลขที่เอกสารที่แสดงบนหัวเอกสาร กำหนดรูปแบบเป็น `DOC-{YYYY}{MM}{DD}-{NNNN}` โดยที่:
  - `{YYYY}{MM}{DD}` คือวันที่ออกเอกสารตามปฏิทิน ค.ศ.
  - `{NNNN}` คือตัวเลขลำดับที่เพิ่มขึ้นอัตโนมัติในวันนั้น เช่น 0001 - 9999
- `document_version`: หมายเลขเวอร์ชันของเอกสารเลขที่เดียวกัน (เริ่มต้นที่ 1 และเพิ่มขึ้นเมื่อออกฉบับแก้ไข)
- `parent_document_id`: อ้างอิง `medical_document_id` ฉบับก่อนหน้า กรณีออกเอกสารฉบับใหม่ทดแทนฉบับเดิม
- `encounter_id`: รายการตรวจรักษาต้นทางที่ใช้ออกเอกสาร (เป็น `NULL` ได้กรณีออกใบรับรองวัคซีนหรือสำเนาประวัติรวมหลายครั้ง) อ้างอิงจาก `clinical.clinical_encounters`
- `pet_id`: สัตว์เลี้ยงเจ้าของเอกสาร อ้างอิงจาก `owner.pets`
- `owner_id`: รหัสเจ้าของที่ขอรับหรือระบุในเอกสาร อ้างอิงจาก `owner.owners`
- `document_type`: ประเภทเอกสารทางการแพทย์ ค่าที่เป็นไปได้ คือ
  - `TREATMENT_SUMMARY`: ใบสรุปผลการรักษา
  - `HEALTH_CERTIFICATE`: ใบรับรองสุขภาพสัตว์
  - `VACCINATION_CERTIFICATE`: ใบรับรองการได้รับวัคซีน
  - `REFERRAL_LETTER`: ใบส่งต่อผู้ป่วยไปยังสถานพยาบาลอื่น
  - `DISCHARGE_INSTRUCTION`: เอกสารคำแนะนำการดูแลหลังจำหน่ายสัตว์กลับบ้าน
  - `MEDICAL_RECORD_EXTRACT`: สำเนาหรือเอกสารสรุปประวัติเวชระเบียน
  - `INSURANCE_CLAIM_REPORT`: เอกสารทางการแพทย์ประกอบการเคลมประกันภัยสัตว์เลี้ยง
  - `DIAGNOSTIC_SUMMARY`: เอกสารรับรองหรือสรุปผลตรวจประกอบ
  - `TRAVEL_CERTIFICATE`: เอกสารรับรองสุขภาพสัตว์สำหรับประกอบการเดินทาง
  - `OTHER`: เอกสารทางการแพทย์ประเภทอื่นตามนโยบายคลินิก
- `title`: ชื่อเอกสาร
- `document_content_summary`: สรุปเนื้อหาหรือข้อมูลสำคัญของเอกสาร ณ เวลาที่ออกเอกสาร
- `file_reference`: Path หรือ Object Key ของไฟล์เอกสาร (เช่น PDF) ใน Object Storage
- `document_status`: สถานะของเอกสาร ค่าที่เป็นไปได้ คือ
  - `DRAFT`: ร่างเอกสาร ยังไม่เป็นทางการ
  - `ISSUED`: ออกเอกสารและรับรองใช้งานอย่างเป็นทางการแล้ว
  - `SUPERSEDED`: ถูกแทนที่ด้วยเอกสารเวอร์ชันใหม่ (`document_version` สูงกว่า)
  - `CANCELLED`: ยกเลิกเอกสารที่ออกผิดพลาด
- `issued_at` / `issued_by`: วันเวลาและผู้จัดทำ/ออกเอกสาร
- `verified_by` / `verified_at`: รหัสสัตวแพทย์ผู้ลงนามรับรองเอกสารและวันเวลารับรอง
- `cancellation_reason` / `cancelled_by` / `cancelled_at`: เหตุผล ผู้ยกเลิก และวันเวลายกเลิกเอกสาร
- `created_at` / `created_by` / `updated_at` / `updated_by`: ข้อมูล Audit มาตรฐาน

#### หมายเหตุ:

1. กำหนด Unique Constraint `(document_number, document_version)` เพื่อป้องกันเลขที่เอกสารและเวอร์ชันซ้ำกัน
2. เอกสารที่มีสถานะ `ISSUED` แล้วห้ามแก้ไขเนื้อหาหรือไฟล์ทับฉบับเดิมโดยไม่มีประวัติ หากพบข้อผิดพลาดให้เปลี่ยนฉบับเดิมเป็น `SUPERSEDED` แล้วสร้างแถวใหม่โดยใช้ `document_number` เดิม เพิ่ม `document_version` และอ้างอิง `parent_document_id`
3. หากยกเลิกเอกสารที่ออกผิดพลาด (`CANCELLED`) ต้องระบุ `cancellation_reason`, `cancelled_by` และ `cancelled_at` และห้ามลบประวัติเอกสารเดิม
4. เอกสารที่มีผลทางกฎหมายหรือรับรองสุขภาพสัตว์ (เช่น `HEALTH_CERTIFICATE`, `VACCINATION_CERTIFICATE`, `TRAVEL_CERTIFICATE`) ต้องระบุ `verified_by` ที่เป็นสัตวแพทย์ผู้มีอำนาจรับรองก่อนเปลี่ยนสถานะเป็น `ISSUED`
